# Cairn 界面文案复审与优化方案

> 复审对象：Cairn v0.2.1 全部用户可见文案（前端 Vue 组件 + 会被透传到界面的后端错误信息）
> 复审日期：2026-11-10 ｜ 复审范围：`frontend/src/**`（39 个 Vue 组件 / 9 个 composable / 2 个 util）+ `backend/app`（错误码与 message）
> 本文档可直接作为逐项评审与落地的工单清单：每条都有编号、文件位置、原文、判定。

---

## 0. 复审说明

### 0.1 判定口径

| 判定 | 含义 | 处理 |
|---|---|---|
| **保留** | 已符合"结论先行、一句话说清、给出下一步"的标准 | 不动 |
| **改写** | 存在冗余、歧义、术语泄漏、语气不符、文案与行为不符 | 见第四节四栏方案 |
| **待核实** | 文案描述的行为与代码不一致，需先确认行为再定文案 | 见第五节 |

### 0.2 统计

统计口径：按"界面元素 × 文案"计条（同一句在两个页面出现算两条）；不含代码注释；aria-label 与 title 计入。数字为逐文件清点后的约数，不追求精确到个位。

| 项 | 数量 |
|---|---|
| 提取到的用户可见文案条目 | 约 400 条 |
| 判定"保留" | 约 310 条 |
| 判定"改写" | **91 条** |
| 判定"待核实（文案与行为不一致）" | **4 条** |
| 其中涉及"术语泄漏" | 约 31 条，是本项目最主要的文案问题 |
| 其中涉及"同一信息重复" | 约 9 条 |
| 其中涉及"指路依赖布局位置/技术前提" | 约 12 条 |

### 0.3 先说结论

**这批文案的基线明显高于同类项目**，不存在"大面积冗余"或"机器翻译腔"。它有明确的写作意识：先说会发生什么，再说怎么办；错误信息区分"网络没成 / 包不对 / 盘不够"；空状态基本都给了下一步；破坏性操作用「已放弃，不计入统计」这类可预期的后果描述。

真正需要改的是四类结构性问题：

1. **术语泄漏（约 31 条，最严重）**：`条目`、`分块`、`库`、`降级`、`就绪`、`环境`、`后端`、`索引`、`组件`、`向量`、`playwright`。这些是开发者的词，不是使用者的词。用户在"我的资料"里想的是"文章 / 笔记 / 题目"，不是"条目"。
2. **文案与行为不符（4 条，风险最高）**：最典型的是采集面板里那个「取消」按钮——它其实只是关掉面板，任务还在后台跑。用户以为取消了，回来发现多了条内容。
3. **指路不可执行（约 12 条）**：`确认 uvicorn 已在 8756 端口启动`、`右上角「开始整理」`、`后端缺 playwright`。前者只有开发者能执行，后两者会随窗口宽度/版本变化而失效。
4. **同一信息说两遍（约 9 条）**：标题留空提示在 label、placeholder、说明里各说一次；空状态在分类树和条目列表各写一遍，措辞还不一样。

行文层面的冗余确实存在，但集中在**长说明块**（采集面板的站点登录、设置页的服务说明、演示横幅），不在按钮和错误信息上。按钮文案普遍已经够短。

## 1. 总体诊断：五个反复出现的模式

### 模式 A｜开发者词替代了用户词

出现 31 次，是最该统一处理的一类。

| 现用词 | 出现场景 | 用户实际会说的词 |
|---|---|---|
| 条目 | 列表计数、空态、按钮、详情、删除确认 | 内容 / 文章 / 资料 / 这条 |
| 分块 | 删除确认、笔记保存提示 | 笔记片段 / 检索片段 |
| 库 / 全库 | "已在库里"、"全库还有" | 知识库（保留，但"全库"改"还有"） |
| 降级 / 降一级 | 检索降级、组件说明 | 只能用关键词搜 / 功能会弱一些 |
| 就绪 | 状态徽标、引导页 | 已整理 / 已配好 |
| 环境 | 顶栏「环境待配置」、引导页「检查本机环境」 | 配置 |
| 后端 | 导图失败、连接失败、登录不可用 | （删掉，用户不关心） |
| 索引 / 向量索引 | 任务中心任务名 | 建立搜索索引 |
| 组件 | 设置-下载、引导页 | 可选功能 / 附加功能 |

**处理原则**：`知识库` 这个词保留（产品名的一部分，且用户已理解）；其余在面向用户的位置换成用户词，技术词只留在「任务中心详情」和日志里。

### 模式 B｜用位置指路，而不是用名字指路

- `点右上角「开始整理」`（SummaryPane）
- `点右上角「开始专注」`（SessionLog）
- `点顶栏「环境待配置」`（client.js）
- `点左栏「全部条目」`（ItemList）

窗口窄于 1100px 时顶栏会收起文字、左栏会自动折叠、出题配置栏会变窄条——**位置会变，名字不会**。同类产品的做法是一律用控件名，必要时补一句"在页面顶部"。

### 模式 C｜技术前提写进了用户提示

- `确认 uvicorn 已在 8756 端口启动`
- `站点登录暂时用不了：后端缺 playwright。装好后重启服务即可。`
- `该服务不支持思考强度参数（发了会 400）`
- `原文超过 50,000 字符，整理时只采样前 40,000 字与末 10,000 字`

用户能做的只有三件事：重试、去设置、重启应用。文案应该只落在这些动作上，技术原因放 `title` 或"详情"里。

### 模式 D｜同一信息重复

| 位置 | 重复内容 |
|---|---|
| 采集面板标题字段 | label「标题（可留空，整理后由模型生成）」+ placeholder「可留空，整理时会自动生成标题」+ maxlength 40 |
| 空状态 | CategoryTree「这里放你的条目。还没有采集过内容。」+ ItemList「这里放你的条目」+「还没有采集过内容。」 |
| 组件体积 | 引导页「向量约 100MB、语音约 500MB」+ 采集面板「small 约 500MB」+ README「92 MB / 539 MB」 |
| 探测说明 | 「探测只读」在 hint、title、卡片说明里出现三次 |

### 模式 E｜文案承诺了界面没做到的事

- 采集面板的「取消」= 关闭面板，任务继续（应改叫「关闭」并说明后台继续）。
- ItemDetail 空态把"没选中"和"库里没内容"两件事写成一段，后者给的动作（去采集）在已经没内容时反而看不到列表。
- Review 的「答对一次往后推一格」——"往后推"既可理解为延后，也可理解为进入下一档。

## 2. 术语与语气基线（先定规则，再改具体句子）

改文案前先统一这 12 条，否则改完还是各写各的。

| # | 规则 | 说明 |
|---|---|---|
| 1 | 对象名统一：**内容 / 文章 / 视频 / 题目 / 笔记** | 界面上不再出现"条目"作为称呼；只在需要指代"一条记录"时用"这条" |
| 2 | 动作名统一：**采集 / 整理 / 生成 / 保存 / 删除** | 不用"入库""落库""写入" |
| 3 | 状态名统一：**待整理 / 整理中 / 已整理 / 失败** | 删掉"就绪" |
| 4 | 不用"降级"，说清"弱在哪" | "只能用关键词搜"优于"降级为全文检索" |
| 5 | 不用"环境/后端/端口/进程"，说"应用/服务" | 用户知道的是"Cairn 这个应用" |
| 6 | 指路用控件名，不用方位词 | 「设置 → 下载」优于"右上角那个" |
| 7 | 错误信息三段式，一句话内 | 发生了什么 + 影响 + 下一步。不道歉、不写"请"字堆砌 |
| 8 | 破坏性确认按钮写动词 | 「删除」/「取消」，不用「确定」/「取消」 |
| 9 | toast 不超过 30 字 | 细节留任务中心 |
| 10 | 数字口径唯一 | 体积、字数、时长在一个地方定义，其它地方引用 |
| 11 | 不用感叹号、不用"哦/啦/呢" | 保持冷静，与产品调性一致 |
| 12 | 括号只用于补充，不用于辩解 | 删掉「（功能不受影响）」「（发了会 400）」这类 |

## 4. 改写方案（逐条：原文 / 诊断 / 优化 / 理由 / 参考做法）

### 4.1 全局框架

**G-02 · 顶栏「环境待配置」的 tooltip**
- 原文：`有必填项还没配好，点开看要补哪一项`
- 诊断："必填项"是表单术语；"点开看"是冗余动作描述（用户点得动就懂）。没有说清**不配会怎样**。
- 优化：`模型 Key 还没配，点了去配`
- 理由：把"必填项"落到唯一真实的阻塞项（Key）；补上"去配"这个动作结果，而不是描述点击过程。
- 参考：VSCode 状态栏的同类提示一律是"当前问题 + 点击后的结果"（如 `No Problems` / `1 error, click to open`），不描述交互。

**G-03 · 顶栏标签「环境待配置」**
- 原文：`环境待配置`
- 诊断：**"环境"是开发者词**。普通用户不知道"环境"指什么，也不知道配的是什么。
- 优化：`还差一步`
- 理由：4 个字，说清"有事没做完"，且不与顶栏其它标签（任务/专注）抢视觉；点进去看到的第一个标题就是"把 Cairn 准备好"，承接自然。
- 参考：Slack 顶部同类条用 `Action needed`（需要处理），不说 "configuration pending"。

**G-05 · 任务按钮 tooltip**
- 原文：`任务中心：采集、整理、索引的执行记录`
- 诊断："索引"用户无感；"执行记录"偏系统日志语气。
- 优化：`任务中心：采集和整理跑到哪了`
- 理由：用户点任务中心只有一个动机——看"我那条采完了没"。用问句式的"跑到哪了"直接对上动机。
- 参考：GitHub Actions 入口文案是 `Actions`（动作），列表页用 `in progress / completed`，全部围绕"跑没跑完"。

**G-08 · 设置按钮 tooltip**
- 原文：`设置：模型、外观、关于`
- 诊断：漏了"下载"页签，与实际四个页签不符（常见的一致性缺陷）。
- 优化：`设置：模型、外观、下载、关于`
- 理由：tooltip 里列全，用户才知道组件装在哪一页；这也是"文案与界面一致"的基本要求。

**G-09 / G-11 · 入库 toast**
- 原文：`「X」已经入库` / `采集完成，已经入库了`
- 诊断：①"入库"是开发者词；②"采集完成，已经入库了"两个完成态叠加，是纯冗余。
- 优化：`「X」已存入知识库` / `已存入知识库`
- 理由：用"存入知识库"这个用户能看见的容器名替代抽象的"库"；成功 toast 只留一个完成信号，不再叠"完成"。
- 参考：Notion 保存提示是 `Saved to Notion`；Google Docs 是 `All changes saved`，都是"位置 + 状态"，不叠加两个动词。

**G-10 · 重复条目的 info toast**
- 原文：`这条已经在库里了（条目 #12），不用再采一次`
- 诊断：暴露内部自增 ID，对用户无意义且像报错；"在库里"不完整。
- 优化：`这条已经在知识库里了，已帮你定位`
- 理由：把 ID 换成用户真正会做的下一步（定位到那条）；"不用再采一次"可由"已经在"自然推出，不必写。
- 参考：在线文档类产品遇到重复导入，提示的是 `Already in your library — showing it now`（已定位），不报主键。

**G-12 · 演示模式横幅**
- 原文：`这里用的是预置样例数据（预先跑了一遍整理、问答、出题后抓下来的）。整理、采集、出题、问答都要本地后端才能用。`
- 诊断：①括号里 24 个字解释数据怎么来的，用户不关心；②"本地后端"是技术词；③两句话说的其实是同一件事（这是假的，真的在桌面版）。
- 优化：`演示数据：这里的内容是预先准备好的，不能新增或生成。装桌面版即可完整使用。`
- 理由：一句话讲清"是什么/不能做什么/怎么办"。横幅是常驻元素，超过 40 字就会在 1280 宽下换行挤压布局。
- 参考：Vercel/Stripe 的 Demo 环境横幅固定三要素：`Demo mode` + 一句限制 + 一个升级链接。

**G-13 · 通用错误兜底**
- 原文：`这次没成功，再试一次；还不行去任务中心看详情`
- 诊断：**并非所有失败都会进任务中心**（设置保存、笔记保存、标题修改都不进）。这句话会在不该出现的地方指错路。
- 优化：`没成功，再试一次。反复失败请到「设置 → 关于」反馈，附上时间点。`
- 理由：兜底文案必须对**所有**调用点都成立。任务中心只承载采集/整理/出题三类异步任务，不能当通用兜底。
- 参考：Stripe 的通用错误兜底是 `Something went wrong. Try again, or contact support if it persists.`——只承诺两件事：重试、找支持。

**G-14 · 后端连接失败**
- 原文：`连不上后端服务。确认 uvicorn 已在 8756 端口启动`
- 诊断：**纯开发者视角**。装机版用户没有 uvicorn，也不知道端口；照做不了，只会觉得产品坏了。
- 优化：`连不上 Cairn 的本地服务。等几秒再试；一直这样请重启 Cairn。`
- 理由：给用户能执行的两个动作（等、重启）。端口号保留在 `detail` 里供反馈排查。
- 参考：桌面应用（Spotify、Figma Desktop）连不上本地代理时，一律是 "Can't connect. Retrying…"，重试按钮 + 自动重连，从不暴露端口。

**G-15 · 轮询超时**
- 原文：`任务超过 20 分钟还没返回，这次不再等了。去任务中心看结果`
- 诊断："这次不再等了"带情绪、像抱怨；用户关心的是"任务死了吗"。
- 优化：`等太久了（超过 20 分钟），已停止等待。任务可能还在后台跑，去任务中心看进度。`
- 理由：区分"停止等待"与"任务失败"——这是两件事，原文没分清，用户会以为任务失败了。
- 参考：GitHub Actions 超时会明确写 `This job has timed out`（作业超时），与"取消失败"分开表述。

**G-16 · 未知错误码**
- 原文：`请求没成功（LLM_HTTP_ERROR）`
- 诊断：把内部错误码直接当前缀，用户读到的是一串大写英文。
- 优化：`出了点问题（错误码 LLM_HTTP_ERROR，反馈时请附上）`
- 理由：保留错误码（排查必需），但给它一个用途说明——用户才知道要不要抄下来。
- 参考：桌面软件常见做法是把错误码放在括号里并标注 `Quote this code when contacting support`。

**G-17 · 缺 Key 的总提示（与 G-03 联动）**
- 原文：`还没配模型 Key，整理、问答、出题都用不了。点顶栏「环境待配置」把 Key 填进去，不用重启`
- 诊断：内容本身写得好（说清影响 + 指路 + 不用重启），但它**引用了 G-03 要改掉的标签名**。若只改标签不改这里，用户就去找一个不存在的「环境待配置」。
- 优化：`还没配模型 Key，整理、问答、出题都用不了。点顶栏的提示把 Key 填进去，不用重启。`
- 理由：改用"顶栏的提示"这种不依赖具体命名的说法，以后再改标签也不会失效；其余部分一字不动。
- 参考：这是"文案互相引用"的通病。GitHub 的错误提示引用设置路径时用 `Settings → Billing`（路径稳定），不引用按钮当下的措辞。

**G-23 · 演示版拦截**
- 原文：`这是静态演示版：生成、采集、整理、问答都要本地后端。下载桌面版就能用`
- 诊断：同 G-12，"本地后端"技术词；"静态"用户不懂。
- 优化：`演示版不能生成内容。装桌面版就能采集、整理、出题。`
- 理由：直接说"不能做什么"，比解释架构有效。
- 参考：SaaS 试用版的只读限制提示统一是 `Read-only in demo. Upgrade to edit.`——限制 + 升级路径，两段式。

### 4.2 采集面板

**C-01 · 三个入口标签**
- 原文：`粘贴文本 / 链接采集 / 拖入文件`
- 诊断：三个标签的构词法不一致（动宾 / 名词+动词 / 动词+宾语），且"拖入文件"与实际的"点击选择 + 拖拽"两种方式不完全对应。
- 优化：`粘贴文本 / 采集链接 / 导入文件`
- 理由：统一成"动词 + 对象"，三者可并列扫读；"导入"覆盖点击与拖拽两种方式。
- 参考：Notion 的导入入口统一用 `Import`，不与 `Drag` 混用；同一组 tab 一律同构。

**C-02 / C-03 · 标题字段（重复三遍）**
- 原文：label `标题（可留空，整理后由模型生成）` + placeholder `可留空，整理时会自动生成标题`
- 诊断：**同一信息说了两遍**，且 label 长达 17 字（标签应短，说明应在 placeholder 或下方 hint）。
- 优化：label `标题`，placeholder `留空则整理时自动生成`
- 理由：label 只承担"这是什么"，placeholder 承担"怎么填"。两处信息不重复，字段高度也不变。
- 参考：GitHub 新建仓库表单：label `Repository name`，helper `Great repository names are short and memorable.`——职责严格分离。

**C-04 · 正文输入提示**
- 原文：`把要整理的段落粘进来，800 字以上效果最好；也可以直接把 .txt 拖到窗口里`
- 诊断：①一句话塞了两件事（粘贴、拖文件），后者与"导入文件"tab 重复；②"要整理的段落"暗示要先自己挑，实际是整篇粘。
- 优化：`粘贴正文。800 字以上整理效果更好`
- 理由：placeholder 只讲这个框怎么用；拖文件由 tab C-01 承担，不再交叉。
- 参考：Medium/Notion 的正文占位是 `Tell your story…`——只讲内容，不讲交互方式。

**C-05 · 转录模型选择**
- 原文：`模型（越大越准，也越慢）`
- 诊断："模型"在此处与设置页的"大模型"重名，用户会误以为是 LLM；"越大"不说明是什么单位。
- 优化：`识别精度`
- 理由：这一项真正的取舍是"准 vs 快"，标签直接写取舍维度；选项里的 tiny/small 保留（是 Whisper 的通用叫法）。
- 参考：语音转写类产品（Descript、飞书妙记）把同类选项叫"识别质量/准确度"，不叫"模型"。

**C-07 · 视频采集说明**
- 原文：`视频会先下音频再转录，1 分钟视频大约 1 分钟。首次使用要下载模型（small 约 500MB）。`
- 诊断：信息有用但三点挤在一句；体积数字与 S-12（"语音约 500MB"）和 README（539 MB）三处不一致。
- 优化：`先下音频再转录，耗时约等于视频长度。首次使用要下载识别模型（约 540MB）。`
- 理由：拆成两个短句；数字统一到 540MB 这一处口径（见第 6 节规则 10）。
- 参考：YouTube 下载类工具的做法是把"预计耗时"和"首次需下载"分两行显示，避免一句话过长导致截断。

**C-08 · 网页采集说明**
- 原文：`只抓正文，导航与版权声明会被过滤。动态渲染的网页可能抓不到，这种情况改用粘贴更稳。`
- 诊断："动态渲染"是前端术语；用户的实际心智是"要登录/要滚动的页面"。
- 优化：`只保留正文，导航和版权声明会被去掉。需要登录或要滚动才出内容的页面可能抓不到，改用粘贴更稳。`
- 理由：把技术原因翻译成用户可判断的特征（要登录、要滚动），这样用户能自己预判成功率。
- 参考：Readwise 的采集说明用 "Some sites (paywalls, logins) can't be saved — paste the text instead."——列举用户可识别的站点类型。

**C-09 · 站点登录说明（长块）**
- 原文：`需要登录才给内容的站点（B 站字幕、知乎受限页）共用这里的登录态。点「登录」会弹出一个独立浏览器窗口，登完自动保存。不碰你日常用的浏览器，也不用手工导出 cookies.txt。`
- 诊断：61 字，三段信息（哪些站点、怎么登、你会担心什么）。在一张 620px 宽的设置面板里会占四行。其中"不用手工导出 cookies.txt"是给老用户的，新用户不知道那是什么。
- 优化：`B 站字幕、知乎受限页这类需要登录的站点，在这里登录一次就行。点「登录」会开一个独立窗口，登完自动保存，不影响你日常用的浏览器。`
- 理由：删掉 cookies.txt（只有从旧版迁移的人才懂，且产品已支持一键登录）；把"不影响日常浏览器"这个真实顾虑留在最后，因为它是用户唯一的阻塞点。
- 参考：1Password 的浏览器扩展授权说明同样把"不影响你现有的登录状态"放在句末作为收尾安抚，而不是放在开头。

**C-10 · 登录不可用**
- 原文：`站点登录暂时用不了：后端缺 playwright。装好后重启服务即可。`
- 诊断：暴露 playwright、"后端"、"服务"三个技术词；且没说**装什么**（哪个组件）。
- 优化：`站点登录现在用不了（缺一个可选功能）。在「设置 → 下载」装上后重启 Cairn 就行。`
- 理由：把"缺 playwright"替换成用户能执行的动作（去下载页装）。若该能力没有对应组件，则应改为"这版还不支持站点登录"。
- 参考：浏览器类产品缺编解码器时提示 "This format needs an additional component. Install it in Settings."——只给安装路径。

**C-11 · 拖放区**
- 原文：`把 .txt / .md 拖到这里` + `或点击选择文件；读入后会转到「粘贴文本」，可先改标题再入库`
- 诊断：第二句 30 字解释了一个跳转机制，用户点一下就知道；"入库"是开发者词。
- 优化：标题 `把 .txt / .md 拖到这里`；副行 `或点击选择。读入后可以改标题再保存。`
- 理由：保留"拖到这里"（这是操作指令），副行只补两种事实：还能点击、还能改标题。
- 参考：Dropbox 上传区的副文案固定是 `or browse your computer`，从不解释上传后跳到哪个界面。

**C-12 / C-14 · 采集完成态**
- 原文：`已入库` / `已入库。可以继续采集下一条，或点「去看看」打开它。`
- 诊断："入库"术语；"继续采集下一条"与下方按钮「继续采集」重复（按钮已经说了）。
- 优化：标题 `已存入知识库`；正文 `点「去看看」打开它。`（字幕来源时补一句 `用的是视频自带字幕，没有跑语音识别。`）
- 理由：完成态只要两个信息：成了、下一步在哪。按钮已经承担"继续采集"，正文不必复述。
- 参考：Linear 创建 issue 成功的 toast 只有 `Issue created`，下一步靠界面本身的按钮，不在提示里重复。

**C-13 · 重复条目（面板内）**
- 原文：`这条已经在知识库里了，没有重复入库。可以继续采集下一条，或点「去看看」打开它。`
- 诊断：三重冗余——"已经在"、"没有重复入库"说的是同一件事；"可以继续采集下一条"与按钮重复。
- 优化：`这条已经在知识库里，没有重复添加。`
- 理由：删掉后半句（按钮已表达），把"没有重复"收紧为一句。
- 参考：同 G-10。

### 4.3 知识库主界面

**K-02 · 今日条末尾**
- 原文：`详情 →`
- 诊断：整条已经是按钮（`aria-label="今日概览，打开完整仪表盘"`），末尾再加"详情 →"是**同一可点区域的第二次暗示**，且在窄屏挤压数字。
- 优化：去掉文字，仅在 hover 时显示（或保留一个纯箭头图标，不占文字宽度）。
- 理由：一个可点区域只给一次可点暗示，是列表/卡片设计的通行做法。
- 参考：Linear 的列表项 hover 才显示操作图标；GitHub 的仓库卡片标题即链接，不额外加"查看详情"。

**K-04 / K-09 · 两处空状态的重复措辞**
- 原文：CategoryTree `这里放你的条目。还没有采集过内容。` + 按钮 `采集第一条`；ItemList `这里放你的条目` + `还没有采集过内容。`
- 诊断：**同一屏出现两次几乎相同的空状态**（左栏与中栏同时为空时），用户会以为界面渲染了两次；且"这里放你的条目"是一句没有信息量的话。
- 优化：左栏 `还没有内容` + 按钮 `采集第一条`；中栏（有筛选时）`没有匹配的内容` + `换个关键词，或清空左栏的筛选`；中栏（无筛选时）不再重复空态，直接展示"最近采集的"引导。
- 理由：空状态是稀缺的引导位，同一屏只应有一次"从零开始"的引导，另一次应退化为补充信息（最近条目）。
- 参考：Notion 侧边栏为空时只显示 `+ New page`；主区为空时显示模板引导，两处不重复同一句话。

**K-08 · 列表加载失败**
- 原文：`列表加载失败` + 重试
- 诊断：没说为什么、也没说不影响什么。用户第一反应是"数据丢了吗"。
- 优化：`列表没加载出来` + `内容还在，重试一次通常就好。` + 重试
- 理由：桌面应用最常见的加载失败是服务重启，先消解"数据丢了"的恐慌，再给动作。
- 参考：Gmail 加载失败提示 `Something went wrong. Reload`，但桌面端更强调"数据仍在本地"。

**K-10 · 筛选为空时的指路**
- 原文：`换个关键词，或点左栏「全部条目」。`
- 诊断：方位指路（左栏折叠后就没有了）；"全部条目"是要用户自己去左栏找的第三层操作。
- 优化：`换个词，或点上面的「清空筛选」。`
- 理由：直接指向当前屏可见的清空按钮（CategoryTree 搜索框旁就有"清空筛选"），少一层寻找。
- 参考：Amazon 搜索无结果时给 `Clear filters` 一键链接，而不是让用户去侧栏逐项取消。

**K-12 · 搜索框 placeholder**
- 原文：`搜索条目标题`
- 诊断："条目"术语。
- 优化：`搜索标题`
- 理由：短两个字符，1280 宽下左栏 260px 能多显示内容；且与 K-09 的"内容"口径一致。

**K-13 · 批量整理 toast**
- 原文：`开始整理了，N 条排队中`
- 诊断："排队中"是任务队列的内部概念；用户不关心排队，只关心什么时候好。
- 优化：`已开始整理 N 条，完成后会在这里更新`
- 理由：给出"在哪看结果"，这是异步操作唯一需要用户知道的事。
- 参考：批量处理类产品（Lightroom 导出、Figma 批量重命名）提示统一是 `Processing N items — you can keep working`。

**K-15 · 切换条目前的确认**
- 原文：`笔记有没保存的修改，切换条目会丢。继续？`
- 诊断：原生 confirm 只有"确定/取消"，标题里没说"不切换"是哪个按钮；"有没保存的修改"语序生硬。
- 优化：标题 `当前笔记还没保存`；正文 `切换后这些修改会丢失。`；按钮 `仍然切换` / `留在这里`
- 理由：把"会发生什么"和"两个选择各自的结果"分开写；按钮用动词，避免用户点错。
- 参考：Figma 未保存离开的对话框是 `Unsaved changes` + `Leave anyway` / `Stay`——按钮名即结果。

**K-16 · 状态徽标「就绪」**
- 原文：`就绪`
- 诊断："就绪"是从 `ready` 直译的技术状态，用户不知道"就绪于什么"。
- 优化：`已整理`
- 理由：与"待整理 / 整理中"构成同一组时间轴，三个状态一眼能排序。
- 参考：任务类产品（Asana、Todoist）状态词一律是动宾结构（Done / In progress / To do），不用 Ready。

### 4.4 条目详情

**D-01 · 详情空态（两场景混写）**
- 原文：`从左侧选一条来读` + `还没有条目时，点右上角「采集内容」加一条。`
- 诊断：**两种完全不同的状态共用一段文案**：库里有条目但没选中 vs 库里一条都没有。后者说"从左侧选"，而左侧根本没有东西可选。
- 优化：
  - 有条目未选中：`从左侧选一条开始读`
  - 完全没有内容：`还没有内容` + `点「采集内容」加第一条。`（并给出采集按钮）
- 理由：空状态必须按"用户此刻的真实状态"分支，否则第一句就是死路。
- 参考：邮件客户端把"未选中邮件"（`Select a message to read`）与"收件箱为空"（`Inbox zero`）分成两个完全不同的空态。

**D-03 · 整理失败**
- 原文：`这次没整理成功：X。再点一次整理；还不行去任务中心看详情。`
- 诊断："点一次整理"指代的是哪个按钮？页面上此时按钮文字是「重新整理」。
- 优化：`这次没整理成功：X。点「重新整理」再试一次；还不行去任务中心看原因。`
- 理由：动作名必须与界面上此刻显示的按钮文字一致，否则用户找不到。
- 参考：错误恢复指引的通行规则是引用控件上的**确切文字**（Stripe Docs 的 `Click Retry` 写法）。

**D-04 · 删除确认**
- 原文：`删除「X」？它的分块和题目会一起删掉，无法恢复。`
- 诊断："分块"是 chunk 的直译，用户不知道那是什么；没说学习记录会不会一起没。
- 优化：标题 `删除「X」？`；正文 `它的笔记片段、题目和作答记录会一起删掉，不能恢复。`；按钮 `删除` / `取消`
- 理由：把级联对象换成用户认识的东西（笔记片段、题目、作答）；"不能恢复"比"无法恢复"更口语。
- 参考：GitHub 删仓库的确认框列出**具体会丢什么**（issues、wikis、stars），而不是统称"相关数据"。

**D-05 · 超长原文提示**
- 原文：`原文超过 50,000 字符，整理时只采样前 40,000 字与末 10,000 字。`
- 诊断：①"采样"是算法词；②"字符"与"字"混用（50,000 字符 / 40,000 字）；③最关键的信息缺失——**原文会不会被截断**？用户看到这句会担心内容丢了。
- 优化：`原文超过 5 万字，整理时只读开头 4 万字和结尾 1 万字；原文完整保留，不受影响。`
- 理由：一个词统一（字）；补上"原文完整保留"，这是用户此刻唯一的真实疑问。
- 参考：Notion AI 处理超长文档时明确写 `Only the first 20,000 words are used — your document is unchanged.`（你的文档不受影响）。

**D-07 · 摘要空态**
- 原文：`还没有整理` + `点右上角「开始整理」，模型会补上分类、摘要和笔记。`
- 诊断：方位指路（"右上角"在窄屏会变，且页面还有"开始专注""删除"挤在一起）。
- 优化：`还没有整理` + `点「开始整理」，自动生成分类、摘要和笔记。`
- 理由：去方位、留控件名；"模型会补上"改为"自动生成"，减少一个需要理解的主体（模型）。
- 参考：同 D-03。

**D-08 / D-09 · 模型漏项**
- 原文：`（模型这次没给摘要，可以重新整理试试）` / `（模型这次没给关键点）`
- 诊断：括号里的话既像错误又像借口；"没给"把责任推给模型，用户不知道该不该重试。
- 优化：`这次没有生成摘要，可以点「重新整理」再试一次。` / `这次没有生成关键点。`
- 理由：去掉括号与拟人化归因，改为陈述事实 + 可选动作；第二条不需要动作就不给动作（避免过度引导）。
- 参考：AI 类产品的部分失败（如 Copilot 只生成了部分建议）用 `No summary was generated.` 陈述，不解释模型行为。

**D-11 · 笔记保存 toast**
- 原文：`笔记已保存，同时更新了 N 个笔记片段`
- 诊断："笔记片段"是检索索引的内部单位，用户无法验证也不需要知道。
- 优化：`笔记已保存，搜索索引已更新`
- 理由：用户真正关心的是"我改的内容以后能不能搜到"，"索引已更新"正好回答这一点。
- 参考：Notion 保存后只显示 `Saved`；Evernote 会说 `Note saved and indexed`（已索引），点明可被搜索。

**D-15 · 导图说明**
- 原文：`按「整理笔记」里的标题层级生成。改完笔记保存就会更新，不缓存旧图。`
- 诊断：末句"不缓存旧图"是在向用户解释实现，用户并不担心缓存。
- 优化：`按笔记里的标题层级生成。改完笔记保存，导图会跟着更新。`
- 理由：把"不缓存"翻译成用户可感知的结果（会跟着更新）。
- 参考：同类功能（XMind、Whimsical 的结构视图）只描述"改动会同步"，不谈缓存策略。

**D-16 · 导图失败**
- 原文：`导图没生成出来。确认后端在运行，再切回来重试。`
- 诊断："后端在运行"用户无法确认（装机版没有这个概念）；也没说最可能的原因（还没整理）。
- 优化：`导图没生成出来。如果这条还没整理，先点「开始整理」；整理过就切回这个页签再试一次。`
- 理由：给出按概率排序的两个原因与对应动作，替代用户无法执行的"确认后端"。
- 参考：错误提示的排查顺序应遵循"最可能 + 用户可操作"（Stripe 的错误文档按发生频率排序）。

**D-17 · 学习记录空态**
- 原文：`还没在这条上专注过` + `点右上角「开始专注」，铃响后写一句笔记，这一轮就会出现在这里。`
- 诊断：①方位指路；②"铃响后"依赖用户开了提示音（若静音则不存在这个时刻）。
- 优化：`还没在这条上专注过` + `点「开始专注」，结束时写一句笔记，这一轮就记在这里。`
- 理由：把"铃响"换成"结束"（无论静音与否都成立）；去方位。
- 参考：同 D-03。

### 4.5 检索问答

**A-04 · 向量不可用**
- 原文：`向量不可用，已降级为全文检索（功能不受影响）`
- 诊断：①"降级"是内部决策词；②"功能不受影响"与"降级"**自相矛盾**，用户会怀疑其中一句。
- 优化：`语义检索暂时不可用，已改成按关键词搜，也能找到大部分内容。`
- 理由：承认能力差异（按意思搜 → 按关键词搜）但不制造恐慌；删掉自相矛盾的括号。
- 参考：Google 搜索服务降级时的提示是 `Some results may be missing`（部分结果可能缺失），不写"功能不受影响"。

**A-05 · 缺向量组件**
- 原文：`现在是纯文字检索，装上向量组件就能按意思搜`
- 诊断："纯文字检索""向量组件"两个术语叠加。
- 优化：`现在只能按关键词搜。装上「向量检索」就能按意思搜。`
- 理由：用"按关键词" vs "按意思"这组用户能直接体感的对比；组件名与下载页的卡片名对齐（`向量检索`）。
- 参考：Algolia/Elastic 的同类开关文案用 `keyword search` / `semantic search` 这一对。

**A-07 · 问答失败的 detail 拼接**
- 原文：`${ev.message}${ev.detail ? `（${ev.detail}）` : ''}`
- 诊断：`detail` 是给排查用的技术串（`provider=deepseek`、`timeout`、`HTTP 429`），直接拼进 toast 会变成"模型调用没成功（provider=deepseek）"这种用户读不懂的句子。
- 优化：只在 detail 属于"人话白名单"时展示；否则只显示 message，detail 写进控制台/任务中心。
- 理由：这是**代码层面的文案策略**，不是单句改写。建议在 `friendlyMessage` 旁加一个 `shouldShowDetail(detail)` 判定。
- 参考：Sentry/Stripe 的错误对象都区分 `user_message` 与 `debug_detail`，界面只渲染前者。

**A-08 · 历史记录标记**
- 原文：`历史记录 · 09:31（不是刚问的，不会重新调模型）`
- 诊断：括号里 12 个字在解释"为什么没有加载动画"，属于防误解，但太长。
- 优化：`历史记录 · 09:31 · 未重新生成`
- 理由：用 5 个字说清同一件事，且"未重新生成"是可以一眼扫过的状态，不是句子。
- 参考：ChatGPT 的历史会话回看只标时间，不解释"为什么没有重新请求"。

**A-09 · 命中统计**
- 原文：`命中 N 段原文 · 来自 M 个条目`
- 诊断："段原文""条目"两个内部计量单位。
- 优化：`找到 N 处原文，来自 M 篇内容`
- 理由：与术语基线一致（内容/文章），"处"比"段"更符合用户对引用的认知。

**A-10 · 问答空态**
- 原文：`问一个库里有答案的问题` + `回答只依据检索到的原文片段，找不到就直接说没有`
- 诊断：标题是"条件句"而不是"行动句"，用户读完不知道自己该做什么；"原文片段"技术化。
- 优化：`问关于你资料的问题` + `回答只依据你的内容，找不到会直接说没有。`
- 理由：标题改为用户动作（问什么），副行改为能力边界（会/不会），与产品的"不硬编"卖点对齐。
- 参考：Perplexity 空态是 `Ask anything…`（行动句），边界说明放在下方小字。

### 4.6 练习 / 复习 / 仪表盘 / 任务中心

**P-02 · 无可出题条目**
- 原文：`还没有能出题的条目，先把它们整理完`
- 诊断："它们"指代不明（指条目？指能出题的条目？）；没说在哪整理。
- 优化：`还没有整理好的内容` + `到知识库点「开始整理」，整理完就能出题。`
- 理由：补上"在哪做"，这是空态唯一的价值。
- 参考：Notion 模板空态一律是 `Get started with a template`（给入口），不是"先准备好内容"。

**P-04 · 出题等待提示**
- 原文：`出完会自动进入作答。60 秒还没出完就点「停止生成」，已收到的题可以照常作答。`
- 诊断：与同页 `estimate`（题数 >10 时"约需 30–60 秒"，否则"约 10–20 秒"）**口径打架**：一处在说 60 秒是阈值，另一处在说 60 秒是正常耗时。
- 优化：`出完会自动开始作答。等太久可以点「停止生成」，已经出的题照样能做。`
- 理由：去掉硬编码的 60 秒，让"等太久"由用户自己判断；避免与上方预估时间冲突。
- 参考：AI 生成类产品（Cursor、v0）的停止按钮旁从不写"超过 N 秒就停"，只写 `Stop generating`。

**R-01 · 复习间隔说明**
- 原文：`答错的题按 1 → 2 → 4 → 7 → 15 天回来，答对一次往后推一格`
- 诊断："往后推一格"歧义：是延后（间隔变长）还是前进到下一档？
- 优化：`答错的题按 1 → 2 → 4 → 7 → 15 天的间隔回来，答对一次就延到下一档。`
- 理由：用"延到下一档"明确方向；补"的间隔"让箭头序列有单位。
- 参考：Anki 的间隔说明用 `the interval increases`（间隔变长），动词直接表明方向。

**R-05 / R-06 · 复习队列状态**
- 原文：`队列中` / `未排期`
- 诊断："队列"是内部数据结构；"未排期"像工程排期表。
- 优化：`等待复习` / `还没安排下次`
- 理由：两个词都改成用户能理解的时间状态。
- 参考：Anki 用 `due` / `new` 这类时间语义词，不用 queue。

**B-02 · 连续学习说明**
- 原文：`今天没学不算断，从昨天算起`
- 诊断：语义含糊——"从昨天算起"是算连续天数从昨天开始，还是判断断没断以昨天为界？两种读法都通。
- 优化：`今天还没学，不算中断`
- 理由：只描述用户当前状态与后果，不解释计算口径。
- 参考：Duolingo 的 streak 说明是 `Keep your streak alive — practice today`，只讲状态与行动。

**B-03 · 待整理总数**
- 原文：`全库还有 N 条待整理`
- 诊断："全库"是内部范围词，且与上方的"今日待整理"数字口径不同，容易让用户以为两个数字矛盾。
- 优化：`共 N 条待整理`
- 理由：去掉"全库"的口径暗示，用"共"表示总量，与卡片的"今日"形成"总量 vs 今日"的自然对照。
- 参考：待办类产品用 `N remaining` 表示总量，不与"今日"混用范围词。

**（以下三条属任务中心）**

**T-02 · 空态**
- 原文：`还没有任务。点顶栏「＋ 采集内容」采一条，这里就有记录了。`
- 诊断：方位指路（"顶栏"在 1280 以下会重排）；"采一条"口语但指向清楚，可留。
- 优化：`还没有任务。点「＋ 采集内容」采一条，这里就有记录了。`
- 理由：删掉方位词，只留控件名，与第 6 节规则 6 一致。
- 参考：同 D-03。

**T-03 · 重试成功**
- 原文：`已重新排队，马上开始`
- 诊断："排队"是任务队列的内部概念；"马上开始"是时间承诺，重试后仍可能排在别的任务后面。
- 优化：`已重新开始，进度会在这里更新`
- 理由：不说"排队"（用户不关心队列），也不承诺"马上"（承诺不了），改说"在哪看进度"。
- 参考：GitHub Actions 重跑按钮（Re-run jobs）成功后只显示状态变为 `Queued`，不做时间承诺。

**T-04 · 任务类型名**
- 原文：`向量索引`
- 诊断："向量"是技术词，用户不知道这步在做什么，只知道"搜得快不快"。
- 优化：`建立搜索索引`
- 理由：描述这步对用户的作用（让内容能被搜到），与 D-11 的"搜索索引已更新"用同一个词。
- 参考：同类产品的后台任务名一律是动宾结构（`Indexing documents`），不用算法名。

### 4.7 引导 / 设置

**S-02 · 引导页副标题**
- 原文：`三件事，缺哪件补哪件。全部就绪后就不用再来了。`
- 诊断："就绪"术语；"就不用再来了"略生硬但意图好（降低焦虑）。
- 优化：`三项，缺哪项补哪项。都配好后就不用再来了。`
- 理由：统一量词（项）；"配好"与页面里的"已配置"呼应。

**S-04 · 检查中**
- 原文：`正在检查本机环境…`
- 诊断："环境"术语（同 G-03）。
- 优化：`正在检查配置…`
- 理由：与页面标题里的"把 Cairn 准备好"、状态里的"已配置"同一条词链。

**S-09 · ffmpeg 说明**
- 原文：`只有「视频链接转录」用它，网页采集和问答都不用。安装包自带，正常情况下这一项本来就是绿的。`
- 诊断：末句用颜色指代状态（"绿的"），对色弱用户与深色模式都不成立。
- 优化：`只有视频转录用它，网页采集和问答都不用。安装包已自带，这里通常是「已就绪」。`
- 理由：用状态文字替代颜色；同时与 S-05 的"已就绪"徽标用词一致。

**S-10 / W-04 · 可选组件说明（同一句话出现两次）**
- 原文：`这三样占了安装包的大头，所以拆出来按需装。不装也能用，只是对应功能降一级。`
- 诊断："降一级"含糊（差多少？）；"占了安装包的大头"是开发者的成本视角，用户只关心"要不要装"。
- 优化：`这三项体积大，所以做成按需安装。不装也能用，只是对应功能会弱一些（下文每张卡片写了差在哪）。`
- 理由：把"降一级"换成用户能接受的表述，并指向具体差异所在（每张卡片的"不装会怎样"）。
- 参考：Chrome 的扩展权限说明把"能做什么/不能做什么"放在每一项上，而不是在总述里含糊带过。

**S-11 · 组件勾选说明**
- 原文：`都可以跳过，之后在 设置 → 下载 里装。勾了的话现在就开始后台下载，不用等它。`
- 诊断：两句话信息重复（"可以跳过"与"之后能装"）；"勾了的话"口语冗余。
- 优化：`都可以跳过，之后在「设置 → 下载」里还能装。现在勾选就开始后台下载，不用等它。`
- 理由：合并重复，统一引号格式（原文 `设置 → 下载` 缺引号，与其它处不一致）。

**S-12 · 模型体积口径**
- 原文：`模型文件（向量约 100MB、语音约 500MB）不在组件包里，第一次真正用到时才下载。`
- 诊断：数字与 README（92 MB / 539 MB）、C-07/C-21（500MB）三处不一致；用户会拿这些数字算流量。
- 优化：`模型文件不在组件包里（向量约 90MB、语音约 540MB），第一次真正用到时才下载。`
- 理由：统一到实测值并四舍五入到 10MB 量级（见第 6 节）。
- 参考：体积类数字必须单一来源，否则用户一旦发现两处不同，就会怀疑所有数字。

**M-01 · 模型页说明**
- 原文：`两套服务够用且界面简单：默认的 DeepSeek 与任意一个「OpenAI 兼容」服务。想换服务商不用改文件，在这里填地址和 Key 就行。`
- 诊断："够用且界面简单"是在替用户做评价（产品自辩）；"不用改文件"假定用户知道有配置文件这回事。
- 优化：`两套服务：DeepSeek 开箱可用；「OpenAI 兼容」可以接任何兼容接口。地址和 Key 填在这里，改完就生效。`
- 理由：删掉自我评价，只留事实（两套、各是什么、填在哪、何时生效）。
- 参考：设置页说明的通行写法是"能力 + 位置 + 生效时机"三要素，不含形容词。

**M-07 · 探测说明（三处重复）**
- 原文：`探测只读：不改地址、不改 Key、不写文件。要留下列表就点「记住」。`（另有 title 与卡片说明重复同样意思）
- 诊断：同一保证说了三遍（title、hint、按钮 title）；"不写文件"是技术保证，用户关心的是"会不会把我的 Key 弄丢/改坏"。
- 优化：保留 hint 一处：`探测不会改动你的地址和 Key。要留下列表，点「记住」。`；删除另两处的重复表述。
- 理由：一处说清，其它两处只留动作名。
- 参考：危险操作旁的"不会修改任何内容"提示，同类产品只出现一次（紧邻按钮）。

**M-09 · 思考强度不可用**
- 原文：`该服务不支持思考强度参数（发了会 400）`
- 诊断："400"是 HTTP 状态码，用户不需要；且没说"那会怎样"。
- 优化：`该服务不支持这个参数，选了也不会生效。`
- 理由：直接回答用户的下一个问题（我选了会怎样）。
- 参考：设置项禁用时的 tooltip 通行写法是 `Not supported by this provider`，不解释协议层原因。

**V-01 · 配色说明**
- 原文：`6 套，全部按对比度硬标准算过`
- 诊断："对比度硬标准"是内部验收口径（WCAG 4.5:1），用户读不出价值。
- 优化：`6 套，文字对比度都做过校验`
- 理由：保留"校验"这个可信信号，去掉"硬标准"这种内部说法。
- 参考：系统级外观设置只说 `Optimized for readability`，不列具体比值。

**W-03 · 本机库状态**
- 原文：`用本机已装的库`
- 诊断："库"指 Python 库，普通用户完全不理解；这句话只在源码运行时出现，但一旦出现就是最困惑的一句。
- 优化：`用本机已安装的版本`
- 理由：在不暴露实现的前提下说明"没走组件包，但能用"。

**W-05 · 演示版不能装组件**
- 原文：`这是静态演示版：装组件要从 GitHub 下载并解压到本机磁盘，演示版做不到。下载桌面版就能装，也能卸载。`
- 诊断：解释了为什么做不到（用户不关心），且 41 字。
- 优化：`演示版不能安装组件。装桌面版后可以安装和卸载。`
- 理由：只留限制与出路。

**U-03 · 校验结果**
- 原文：`已下载 X，校验值一致。/ 这个版本没附 .sha256，只比对了大小。`
- 诊断："校验值""sha256""比对大小"三个技术表述。
- 优化：`已下载 X，文件完整性校验通过。/ 这个版本没有校验值，只确认了文件大小。`
- 理由：说"完整性校验"这个用户能理解的保证；降级情况如实说明但不用哈希算法名。

**U-04 / U-05 · 配置来源**
- 原文：`有没有从老地方拿过配置` / `只读数据目录（严格模式）`
- 诊断：`有没有…` 是疑问句当字段名，与旁边"配置文件"的名词短语不一致；"严格模式"是内部开关名，用户无从理解。
- 优化：`是否从旧位置补过配置` / `只读本机数据目录`
- 理由：与同组字段统一为名词短语；删掉用户无法理解的模式名（需要时在 tooltip 里说明差异）。

### 4.8 后端错误信息

**E-01 · 缺 Key（knowledge 路由）**
- 原文：`未配置 LLM API Key，请在 .env 中设置 LLM_API_KEY`
- 诊断：指导用户去改 `.env` 文件，与界面上的一键配置路径冲突；且 `LLM_API_KEY` 是变量名。
- 优化：`还没配模型 Key。在「设置 → 模型」里填一下就能用。`
- 理由：与 `llm.py:73` 已有的好文案（指明服务 + 指路设置）对齐，全站只保留一条路径。
- 参考：同 E-05，这是项目里已经写对的那一条，应当作为标准。

**E-02 · 原文为空**
- 原文：`原文为空，无法整理`
- 诊断：被动、无出路。用户不知道"原文为空"是因为采集失败还是自己没粘内容。
- 优化：`这条没有正文，整理不了。补上原文再试。`
- 理由：给动作；"正文"比"原文"更贴近用户对内容的称呼。

**E-04 · 题型/难度非法**
- 原文：`题型不合法` / `难度不合法`
- 诊断：这是参数校验错误，正常用户不会触发（除非前端 bug），但一旦触发就是纯技术语言。
- 优化：`题型参数不对，请重新选择题型。` / `难度参数不对，请重新选择难度。`
- 理由：保留"参数不对"的定位信息，同时给出用户动作；这两条主要出现在任务中心，可读性优先。

**E-07 / E-08 · 采集失败 detail**
- 原文：`细节：空链接` / `细节：仅 128 字`
- 诊断：`detail` 会被 `cleanError` 拼到失败卡片上，`空链接` 读起来像断言而非提示。
- 优化：`请填一个链接` / `只抓到 128 字，可能是页面需要登录或内容是图片`
- 理由：把内部度量（字数）翻译成用户能推断的原因。
- 参考：Readability 类工具的失败提示会给"最可能原因"，而不是只报计数。

**E-09 · 组件清单缺失**
- 原文：`清单里没有 xxx，无法下载`
- 诊断："清单"指 `components.json`，用户看不到这个文件。
- 优化：`这个版本没有提供该组件，换最新版再试。`
- 理由：把包内清单翻译成"版本"这个用户能理解的概念。

**E-11 · 导出被拦截**
- 原文：`正文含外部引用：['http://…']`
- 诊断：这是安全校验的拒绝原因，直接展示会让用户以为自己违规了。
- 优化：`这篇内容里有外部图片或链接，为了保证离线可用被拦下了。可以去掉后重新整理。`
- 理由：说明"为什么拦"（离线可用）而非只报"含外部引用"。
- 参考：CSP 类报错的用户侧文案一律先讲"为了安全/离线"，再讲具体元素。

## 6. 跨页面统一规则（落地时按此收敛）

1. **对象称呼**：正文里出现"条目"的地方一律替换为"内容/文章/这条"；`search` 类 placeholder 用"标题"。
2. **动作词**：采集（网页/视频）、导入（本地文件）、整理（模型加工）、生成（学习页/题目）、保存（笔记/配置）。不再出现"入库/落库/写入"。
3. **状态词**：待整理 / 整理中 / 已整理 / 失败；采集任务是 排队中 / 进行中 / 完成 / 失败。
4. **"降级"只用在不面向用户的日志里**；界面上一律说"只能…/会弱一些/暂时用不了"。
5. **不写"后端/端口/进程/环境/playwright/uvicorn/400/sha256/分块/索引"**；技术细节进 `detail` 或任务中心。
6. **指路格式**：`「设置 → 下载」`（带书名号、固定空格、不用"右上角/左栏"）。所有页面同一功能的路径必须一致。
7. **按钮名与文案引用必须逐字一致**：文案里提到按钮时，复制按钮那一刻的真实文字（`重新整理` 不是 `整理`）。
8. **错误三段式**：发生了什么（≤12 字）+ 影响（可选）+ 下一步（一个动作）。不叠两个"请"。
9. **破坏性确认**：标题问句 + 正文列具体后果 + 按钮用动词（`删除`/`仍然切换`），不用"确定/取消"。
10. **数字单一来源**：体积（90MB / 540MB / 262MB / 100MB / 49MB）、字数（5 万字）、时长（20 分钟轮询上限）各只有一处定义，其它地方引用。
11. **空状态分支**：区分"有数据但没选中"与"完全没有数据"，两种状态给不同的动作。
12. **toast ≤ 30 字**，且不要在 toast 里复述按钮文字。
