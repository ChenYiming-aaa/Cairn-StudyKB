# Cairn 发版说明规范（Release 标题与正文）

> **作用域**：GitHub Release 的**标题**与**正文**，以及 `docs/dev/release-notes-vX.Y.Z.md` 里要贴进 Release 的那部分。
> 不覆盖：README 的「变更记录」段（给翻仓库的人看，可以写长）、`HANDOFF.md` 的发版附录（给下一个会话看，要写细节）。
> 与 `文案规范.md` 的关系：术语、禁止词、体积口径**一律从它**；本文只补三件事 ——
> 标题怎么起、正文怎么分点、每点写多长。
> 建立于 2026-11-18；**同日已把 v0.1.0 – v0.3.5 与组件包 v1 全部按本文重写**（标题 + 正文），
> 原文移进各自底稿的「维护者备注」，一个字没删（见 §6，含改前备份的位置）。
> 底稿：`docs/dev/release-notes-vX.Y.Z.md`。

---

## 1. 标题

格式：`vX.Y.Z · 主线`（版本号 + 空格 + `·` + 空格 + 一句话）

- **一条主线**，≤ 12 字：这一版最要紧的那件事。其余变更全进正文，标题里不并列
- **说变了什么**：不用「优化体验」「多项改进」「一次重要的更新」这类指不出内容的词
- **删功能、改口径要进主线** —— 人先看标题，得先知道「我熟悉的东西没了 / 数字会变」
- 不加 `Release` / `Update` / `最新版` / 日期这类冗余词，不用感叹号，不卖萌
- 补丁版（x.y.**z**）就写修好的那件事，别写「若干问题修复」

| 好 | 字数 | 差 | 差在哪 |
|---|---|---|---|
| v0.3.6 · 导出支持整批 | 6 | v0.3.6 · 一次重要的版本更新 | 说了等于没说 |
| v0.3.5 · 去掉番茄钟，自动整理 | 9 | v0.3.5 · 多项体验优化 | 指不出内容 |
| v0.3.7 · 试卷识别更准 | 6 | v0.3.7 · Bug 修复 | 没有主线、还是英文 |

## 2. 正文结构

编号点 + 固定短句，顺序固定：

```text
1. <第一条>
2. <第二条>
3. <第三条>

升级：设置 → 关于 → 检查更新

数据：数据目录不动，可装回上一版

安装包：Cairn-X.Y.Z-setup.exe（184.5 MB），sha256 见附件

注意：<这一版不写就会踩的坑>（可选，最多一行）
```

> 固定短句**之间要留空行**：GitHub 把段内换行折成空格，不留空行会挤成一整行。

### 2.1 编号点（正文主体）

- **3–7 条**：不足 3 条就合并成一句话写；超过 7 条说明这一版该拆成两次发
- **每条 ≤ 15 字**（汉字、字母、数字各算 1，编号与标点不算）
- **一句一件事**：出现「并且 / 同时 / 另外 / 以及」就拆成两条
- **动词开头**：去掉 / 新增 / 改成 / 修好 / 现在…；不写「XX 的优化」「对 XX 的改进」
- **顺序：删与改 → 新增 → 修复**。会让人以为「坏了」的那条必须排最前
- **只写用户看得见的变化**：类名、端点、字段名、脚本、验收条数**不进编号点**；
  要给维护者留档，写到 §2.3（不贴进 Release）

### 2.2 固定短句（不编号，3–4 行）

紧跟编号列表，各占一行，句式照抄、只换值：

| 行 | 写法 | 什么时候改句式 |
|---|---|---|
| 升级 | `升级：设置 → 关于 → 检查更新` | 走不了更新器（例如跨大版本要重装）时换成 `升级：重新下载安装包覆盖安装` |
| 数据 | `数据：数据目录不动，可装回上一版` | 真做了不可回退的迁移时写 `数据：升级后不能再装回上一版`，并说清哪一步不可逆 |
| 安装包 | `安装包：Cairn-X.Y.Z-setup.exe（184.5 MB），sha256 见附件` | 同时上传了 `.sha256` 才这么写；没上传就把完整 sha256 放这一行（长值不数字数） |
| 注意（可选） | `注意：<这一版不写就会踩的坑>` | **最多一行**。只放「不说就会有人踩」的：没签名会被 SmartScreen 拦、预览版检查更新看不到、PDF 与图片要先装识别组件、这次要手动装一次。常态规则（怎么卸载、数据在哪）不写 |

- 体积用**十进制 MB**（1 MB = 10⁶ 字节），与 `utils/format.fileSize`、README 同一口径，**不写 MiB**
- 体积与 sha256 必须与附件一致：发版前用 `sha256sum` 核一遍，别手抄
- **不是应用本体的 Release**（如 `components-v1` 组件包）把这三行换成 `用法 / 适用 / 体积`：
  它没有「升级」「数据目录」这回事，硬套模板只会写出假话

### 2.3 维护者备注（可选，不贴进 Release）

代码清单、口径改动、验收条数、踩坑 —— 都放这里。贴 Release 时从这一行往后整段删掉。

## 3. 用词

- 术语从 `文案规范.md` §2：**内容**（不是条目）、**整理 / 已整理**、**练习 / 复习**、**学习页**
- 禁止词清单 §6 同样适用：`条目` `就绪` `入库` `后端` `LLM` `pending` `ready` 不出现
- **面向使用者，不写「我们」**：主语是用户或功能本身（「出题现在读整理好的笔记」）
- **句子短、少从句**：括号只放补充值（版本号、体积、天数），不放大段解释
- **不承诺做不到的**：写进 Release 的能力，这一版必须真的能点到
- 理由（为什么删、为什么改口径）留给维护者备注；正文只回答「变了什么、要不要担心」

---

## 4. 自检（发版前逐条过）

1. 标题的主线，能不能让人一眼看出「这版变了什么」
2. 有没有一条点其实是两件事 → 拆
3. 每点数一遍字数，有没有过 15
4. 删除 / 口径变化是不是排在最前，且写清了「不是坏了」
5. 编号点里还有没有类名、端点、内部代号 → 删
6. 体积与 sha256 与附件对得上吗
7. 维护者备注删干净了吗（贴之前）

---

## 5. 底稿与 Release 的关系

`docs/dev/release-notes-vX.Y.Z.md` 是正文**底稿**，固定三节：§1 标题 / §2 正文 / §3 维护者备注。

- 贴进 Release 的是 **§1 的标题 + §2 的正文**（编号点与固定短句，照抄，不现场压句）
- **不贴**：开头的「作用域 / 读者 / 建立」提示块、§3 维护者备注
- 正文里的固定短句**之间留空行**（见 §2），否则 GitHub 会折成一行
- 写底稿时不必自己数字数，按 §4 第 3 条过一遍即可（历史那批是用脚本数的）
