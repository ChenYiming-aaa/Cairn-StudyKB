## 0. 结论

1. **产品上最痛的不是「缺功能」，是「做完一轮就回不去」。** 试卷结果页那颗「再做一遍」点了只会退回空舞台；
   由材料出的那组题交卷后没有任何重做入口，只剩错题本。两条都实测复现（§3.1、§3.2）。
2. **工程上最大的漏洞不是「没有 CI」，是「有 8 秒就能跑完的 229 条离线断言，一条都没进 CI」。**
   `verify_m4` 78/78 用 5.6 秒、`verify_m10` 151/151 用 2.5 秒，全程打桩不联网（§4.1）。
3. **数据上唯一「一次事故全赔」的地方是零备份。** 全部知识、笔记、作答记录在一个 SQLite 文件里，
   应用内没有任何备份动作，只有关于页一句「复制这个文件夹」（§3.3）。

排序原则：**先修用户每天撞到的东西，再修让下一轮改动变便宜的，最后才是让代码变好看。**
所以本方案的 P0 里没有「拆巨石文件」，P2 里才有。

## 3. P0 · 止血（建议本周，约 1.5 天）

### 3.1 试卷「再做一遍」要真的重开

**现状**：`Practice.vue` 里 `onRestart()` 只会 `backToIdle()`；而 `QuizRunner` 在按卷练时把按钮文案设成
「再做一遍」。实测：25 题答完、交卷 5/25 → 点「再做一遍」→ 舞台变成「还没开始 / 左侧已选好试卷，点『按卷练』开始」。
**卷子和作答都在库里**（`按卷练` 再点一次仍能取到 25 题），坏的是这颗按钮。

**改法**（3 行，只动前端）：

```js
async function onRestart() {
  backToIdle()
  // 试卷的「再做一遍」要真的重新开卷：题在库里，不必让用户回左侧再点一次。
  // 生成的题组仍然回配置 —— 题是现出的，得重选题型与题数。
  if (paperRun.value) await startPaper()
}
```

`startPaper()` 自己会判 `phase === 'idle'`（`backToIdle` 刚给），重新取题并 `runKey += 1` 重挂作答器。

**验收**：`verify_m10.py` 全绿 + `verify_m11.py` 全绿；手工走一遍「按卷练 → 全答 → 交卷 → 再做一遍 → 第 1/25 题」。
**风险**：极低。唯一要确认的是 `paperRun` 不被 `backToIdle` 清掉（已核，不清）。

### 3.2 已有题：让做过的题能重来

**现状**：`POST` 出题把题写进 `question` 表就结束了，界面上没有「这条内容下有哪些题」。
交卷后只剩两个出口：错题本（只含答错的）、复习队列（只含到期的）。这就是「只保留了错题」。

**改法**（新增一个只读端点 + 练习页一颗按钮，不建任何新表）：

- 后端：在 `knowledge` 路由下加 `{item_id}/questions`，返回该内容全部题（按 `origin`、题号数值序），
  字段与按卷练一致，前端可直接喂给 `QuizRunner`；同时登记进 `接口契约.md`。
- 前端：练习页对**非试卷**内容，在「出题」下面加一颗次要按钮 `做已有题（N）`，N 为 0 时不渲染；
  点下去取题、`paperRun = false`、进作答。试卷条目不出这颗按钮（`按卷练` 已经是整份卷子）。
- 文案过一遍 `文案规范.md` §6：不用「题库 / 条目 / 就绪 / 入库」。

**为什么不做「最近一组」**：那需要「题组」这个实体（一张记录表 + 写入时机 + 清理策略），
而题池用现有数据就能回答同一个问题，成本差一个量级。等真出现「我要的是上周那一组的第 3 题」再谈。

**验收**：
1. 出 5 题 → 交卷 → 回练习同一条内容 → 按钮显示 `做已有题（5）` → 点开是**同一批题号**；
2. 再出 5 道新题 → 按钮变 `做已有题（10）`；
3. 试卷条目**不出现**这颗按钮，`按卷练` 行为不变；
4. 后端空库：没有题时不渲染按钮，也不发请求。

**风险**：中低。主要是不让「出题」与「做已有题」两个入口互相抢戏——所以试卷条目只保留一个入口。

### 3.3 数据备份：让「一次事故全赔」变成「最多丢一天」

**现状**：全部知识、笔记、作答、题目在一个 `data.db` 里。关于页只写了一句话让人自己去复制文件夹。
用户不会做，也不该被要求记得做。

**改法**：
- 启动后台线程：距上次备份超过 24 小时就 `VACUUM INTO <数据目录>/backup/data-YYYYMMDD.db`，
  保留最近 7 份（多出来的按文件名删除）；当天已有同名文件就跳过（`VACUUM INTO` 目标存在会报错）。
- 设置页「关于 / 数据」区加一行：上次备份的时间与位置 + `立即备份` 按钮（同一函数，跳过 24 小时门槛）。
- 备份失败只写日志 + 界面一句「这次没备上」，**不阻塞启动**。

**验收**：删掉 `backup/` 目录 → 重启 → 24 小时内生成一份；连点两次 `立即备份` 不产生第二份；
生成的文件能用标准 `sqlite3` 打开并查到 `knowledge_item` 行数；卸载不删数据目录（现在就不删）。

**风险**：低。库到 500 MB 时 `VACUUM INTO` 约几秒——放后台线程，别在请求路径里做。

**验收**：`python tools/doc_check.py --strict` 退出码 0；清单里不再出现未完成但实际已完成的条目。

## 4. P1 · 可持续（建议一周内）

### 4.1 CI：先把现成的 229 条跑起来

**现状**：`.github/workflows/` 只有 `pages.yml`（演示站）。`verify_m4` / `verify_m10` 全程打桩、
不联网、不碰 `data/`，本地 8.1 秒跑完 229 条。它们从没在 CI 里跑过。

**改法**（一个 workflow，三个 job）：

| job | 内容 | 预计 |
|---|---|---|
| `front` | `npm ci` → `npm run lint` → `npm run build`（顺带挡住「demo 数据进了 dist」） | ~2 min |
| `docs` | 纯 Python：`tools/doc_check.py --strict` + `tools/bump_version.py --check` | ~10 s |
| `backend` | `uv sync --frozen` → `verify_m4` + `verify_m10` | 冷装 ~3 min，有缓存 ~1 min |

`backend` 这条要实测一次冷装耗时再定：`import app.main` 只要 1.05 秒、且**不拉 torch**
（重依赖是懒加载的），但 `uv sync` 会按 `pyproject.toml` 装齐。如果太慢，就先只上 `front` + `docs`。

**验收**：故意在 `Practice.vue` 改坏一个字符 → PR 上 `front` 变红；故意改坏 `review.next_interval` → `backend` 变红。

**风险**：低。唯一成本是 GitHub Actions 分钟数；私有仓库有额度，公开仓库免费。

### 4.2 最小单测 + 提示词 schema

**现状**：`pytest` 收集到 0 个用例，全仓没有 `test_*.py`。11 个跨里程碑脚本验的是「链路能跑通」，
验不出「`organize_if_pending` 的六个前置判断各自正确」。提示词输出的 JSON 没有 schema 校验，
只在每个调用方各写一段容错。

**改法**：
- 加 `[dependency-groups] test = ["pytest"]`，建 `backend/tests/`，**只写三类**：
  1. `organizer` 失败路径：非 JSON / 超时 / 额度三种返回各自落到哪个错误码（这是注释里自认「失败率最高」的一段）；
  2. `review.next_interval` 的边界（1/2/4/7/15、答错重置、None 不排期）；
  3. `exam.commit` 的事务：中途抛错必须整批回滚，不能留半份。
- 提示词：`organizer` / `quizzer` / `exam.parse` 的输出用 Pydantic 模型校验一次，
  失败走现有「问题照报、改法丢掉」路径，不新增第三种失败文案。

**验收**：`pytest -q` 全绿且用例数 ≥ 30；故意删掉 `commit` 里的 `with conn` 事务 → 有用例变红。

**风险**：低。注意别把「调用模型」写进单测——一律打桩（照抄 `verify_m10` 的做法）。

### 4.3 版本与台账的单一事实源

**现状**：`bump_version.py --check` 核四处（pyproject / version.py / 两个 package.json），
不含 `README.md` 徽标——所以徽标停在 `0.3.4` 而代码是 `0.3.7` 没人发现。
台账「当前状态」段落日期停在 11-13，内容却写到 0.3.7。

**改法**：
- `bump_version.py` 加第五处：README 第 23 行的徽标（正则替换 `version-X.Y.Z`），`--check` 一起比对；
- HANDOFF 顶部「当前状态」压到 ≤120 行，历史按月搬进归档目录（照 `HANDOFF.md` 自己的归档规则执行）；
  并在 `docs/dev/运行与打包.md` 里把「发版后更新哪几处」列成清单。

**验收**：把徽标改回 0.3.4 → `--check` 退出码 1；HANDOFF 打开后第一屏能看到「现在是什么版本、下一步做什么」。

**风险**：低。分拆时按「只追加、不改历史」的既有规则整段搬家。

### 4.4 列表加载更多（需先确认 H2 的原裁决）

**现状**：知识库固定取 50 条、练习页取 100 条，超出只在计数旁写一句「仅显示前 50 条」。
这是 2026-11-15 的明确裁决（不做分页，只补说明），不是疏忽。

**为什么现在提**：3 周进了 13 条，按这个速度约 3 个月撞到 50（估算）。撞到之后用户会开始
「搜关键词找自己的东西」——而这本来是列表该解决的。所以要问的是：这条裁决还成立吗。

**改法（若裁决推翻）**：知识库列表加「加载更多」按钮（cursor = 最后一条 id），不做页码；
筛选条件变化时回到第一页。练习页同理，或在搜索框之外加分组。

**验收**：造 120 条 → 翻到底能看到第 120 条；筛选后不会串页。

**风险**：中。列表是最高频页面，动之前先跑 `verify_m7`。

## 6. 明确不做

- **不引 ORM / 多 Agent 框架 / UI 组件库 / 独立向量库**：ADR-020 的四条红线，理由与解除条件都还成立。
- **不上 FSRS**：现在 `review_item` 只有 13 条排期，「2→4→7→15」已经够用；等排期数过两千再说。
- **不为「题组」建表**：题池（§3.2）能用现有数据解决同一个问题。
- **不做多用户 / 云同步 / 移动端**：红线 1。
- **不追测试覆盖率**：先把三类高频失败覆盖住，覆盖率是结果不是目标。
- **不做「AI 自动决定下一步学什么」**：那会踩到红线 3 的解除条件（「LLM 自主决定下一步」），要单独立项讨论。
