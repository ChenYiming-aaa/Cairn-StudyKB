# 前端视觉与动效内部一致性审计 · 2026-11-17

审计范围：`frontend/src/` 全部 64 个带样式的文件（61 `.vue` + 3 `.css`），共 41 条 `transition` / `animation` 声明。

**与同日 `动效审计-2026-11-17.md` 的分工**：那份回答「该不该动、性能贵不贵、有没有尊重减少动效」；
这份只回答「同一个意思，有没有两种做法」，以及「动效是否过量到抢注意力」。不评价设计品味。

方法：读全部样式定义 + 脚本统计（时长/缓动/圆角/阴影分布）+ 比对「被引用的 CSS 变量」与「已定义的变量」两个集合。
所有数字来自脚本，不是估的。

## 0. 一句话结论

**12 条全部落地，见 §4 汇总与 §5 落地记录。** 下面是审计时的原始判断，保留是因为「当时怎么判的」比「改完了」更有用。

- **Token 层**：间距、字号、圆角、阴影、颜色都收敛得不错。**动效原本一个 token 都没有**（`tokens.css` 里 `duration` / `ease` / `transition` 关键字出现 **0** 次），7 种时长、4 类缓动全靠各文件手写 —— 这是本轮绝大部分不一致的**同一个根因**。
  **已落地**：补 7 个 token，全部非循环动效改为引用，`--shadow-1` 缺陷已修。
- **克制性层**：**基本干净**。全项目零悬停位移、零缩放，零超过 400ms 的交互，零「等动画结束才能操作」的代码。这一项我给通过，详见 §2。

### T1 · 动效完全没有 token 化

- **类别**：Token 一致性
- **位置**：`frontend/src/styles/tokens.css:16-58`（`:root` 块）
- **不一致之处**：`:root` 里有间距、字号、圆角、行高、版面尺寸、阴影、字体七组 token，**没有一组是时间或缓动**。结果是同一个「进度填充」在五个文件里写了三种缓动，同一种「元素出现」写了四个时长（T2、T3）。
  更隐蔽的一层：9 处 `transition` 没写缓动函数，吃的是 CSS 默认 `ease` —— 作者不写缓动不是因为选择了 `ease`，而是因为**没有东西可写**。
- **依据**：项目自己的约定写在 `tokens.css:13`「任何组件都不许写死颜色，一律引用这里的变量」。这条约定的理由（散落值会漂移）对时间同样成立，只是当年只落地了颜色与尺寸。
- **最小收敛方案**：在 `:root` 补一组，**取值全部对齐现有众数，不引入新数值**：

  ```css
  --dur-fast: 150ms;      /* 悬停/聚焦/按下 —— 已有 11 处就是它 */
  --dur-overlay: 140ms;   /* 弹窗进出 */
  --dur-enter: 180ms;     /* 内容出现（吸收 160 / 220，见 T2）*/
  --dur-progress: 200ms;  /* 进度填充 */
  --dur-slow: 350ms;      /* 单点：专注计时 */
  --ease-out: ease-out;   /* 状态变化、出现 */
  --ease-in-out: ease-in-out;
  --ease-linear: linear;  /* 扫描线、计时 */
  ```

  缓动**不加 `cubic-bezier`**：项目 14 处已经在用 `ease`，换成自定义曲线是纯粹的视觉改动，不属于「收敛」。
- **优先级**：**高**（它是 T2/T3/T4 的共同根因；做完这一条，后面三条都只是几分钟的替换）
- **✅ 已落地（同日）**：
  - `tokens.css` 新增 7 个 token，落在 `:root` 的阴影之后、字体之前；注释里写清每个值的来处与「循环动画不在此列」的理由。
  - 14 个文件、20 处声明改为引用；`--dur-fast` 11 处、`--dur-overlay` 2 处、`--dur-enter` 4 处、`--dur-progress` 5 处、`--dur-slow` 1 处、`--ease-out` 5 处、`--ease-linear` 1 处。
  - **取值全部沿用现状，只有两处数值收敛**：`PdfPage` 160→180、`Practice` 220→180（即 T2 的收敛，一并做了）。
  - 缓动**只收了真有引用的两个**：`--ease-in-out` 仍被 4 处循环动画使用，但循环不在本轮范围，所以没有为它建 token（避免留一个悬空定义）。
  - 验证：`npm run lint` / `npm run build` 干净；`verify_m7` **96/96 PASS**；另建 `tools/check_motion_tokens.py` 读**构建产物**在 msedge 里断言（见 §7）。

### T2 · 「元素出现」用了 4 个不同时长

- **类别**：Token 一致性
- **位置**：
  - `styles/app.css:355-359` 弹窗：**140ms** `ease-out`
  - `components/raw/pdf/PdfPage.vue:137` PDF 页淡入：**160ms** `ease-out`
  - `App.vue:490` 通知条：**180ms** `ease`（关键帧 `slide-in`，`App.vue:497-508`）
  - `views/Practice.vue:758` 出题卡浮现：**220ms** `ease`（关键帧 `pop-in`，`Practice.vue:794-804`）
- **不一致之处**：这两组关键帧**效果完全相同** —— 都是 `opacity 0→1` + `translateY(6px)→0`，一个像素不差，却用了两个名字、两个文件、180ms 与 220ms 两个时长。
  用户看到的是：同样「一块内容浮上来」，通知条 180ms、卡片 220ms，弹窗 140ms、PDF 160ms —— 四种速度。
- **依据**：同一类交互（元素出现/状态变化）应收敛到同一 token，这是设计系统对动效的基本要求；四值并存意味着用户无法从速度里建立任何预期。
- **最小收敛方案**：`.toast` 与 `.gen-card` 合并为一个 `.rise-in` 关键帧（放 `app.css`，两者都引用），时长统一 `--dur-enter: 180ms`；`PdfPage` 160ms 归入 180ms；`dialog` 保留 140ms 但改用 `--dur-overlay`（**不改数值** —— 140ms 是同日审计认定为「桌面正确」的值，动它是无谓 churn）。
  净变更：`220→180`、`160→180` 两个数字，四条规则变 token 引用。
- **优先级**：中
- **✅ 已落地，但结论改了**：时长统一到 `--dur-enter`（180ms）做到了；「合并成一个关键帧」**没做，而且不该做** ——
  因为 K3 把 `.gen-card` 的 `translateY` 去掉了，两者不再是同一个效果：
  通知条是「上浮 6px + 淡入」，出题卡是「纯淡入」。合并会把其中一个的信息量削掉。
  现在的分工是清楚的：`slide-in`（App.vue，单个浮出物）+ `fade-in`（Practice.vue，批量出现），
  两者都用同一个时长 token。**同效异名的债没了，但不是靠合并，是靠让它们真的不同。**

### T3 · 同一类「进度填充」三种缓动

- **类别**：Token 一致性
- **位置**：

  | 文件 | 时长 / 缓动 | 属性 |
  | --- | --- | --- |
  | `components/ingest/LinkForm.vue:360` | 200ms `ease-out` | `transform: scaleX` |
  | `components/settings/AboutTab.vue:345` | 200ms `ease-out` | `transform: scaleX` |
  | `components/settings/DownloadsTab.vue:384` | 200ms `ease-out` | `transform: scaleX` |
  | `views/Tasks.vue:337` | 200ms `ease-out` | `transform: scaleX` |
  | `styles/app.css:414`（`.meter` 原生进度条） | 200ms **`ease`** | `inline-size` |
  | `components/Pomodoro.vue:311` | **350ms** **`linear`** | `transform: scaleX` |

- **不一致之处**：六个都是「一条横条填充到某个百分比」。四处 `ease-out`、一处 `ease`、一处 `linear`。
  `.meter` 是唯一的 `ease` —— 这不是设计选择，是作者手写时随手写的默认值。`ease` 起步慢（前 30% 时间只走约 12% 距离），**在进度条上的直接后果是填充比读数慢半拍**，正是同日审计在 `.meter` 300→200ms 那条里想消除的现象，只是没意识到缓动函数也在拖后腿。
  `Pomodoro` 的 `350ms linear` 是**对的**（1s 一次跳变，`linear` 表达匀速流逝），不该并入 200ms —— 它属于另一类（计时流逝，不是任务进度）。
- **依据**：进度填充是「追上一个已知值」，属 `ease-out` 语义（快启动、末端收敛）；`ease` 的慢启动与这个语义相反。同一类视觉重复三种缓动，用户在不同页面会看到同一根条「跟手程度」不同。
- **最小收敛方案**：五处任务进度统一 `--dur-progress` + `--ease-out`（`.meter` 改一个字）；`Pomodoro` 保留 `linear`，只把 350ms 换成 `--dur-slow`。
- **优先级**：中
- **✅ 已落地**：`.meter` 的 `ease` → `var(--ease-out)`，是这条里唯一一处**观感**变化（进度条起步变快）。
  浏览器实测：`.meter` 之外的四处 `0.2s ease-out`，`.meter` 现为 `0.2s ease-out`，Pomodoro 仍是 `0.35s linear`（另立语义，见 T4 末尾）。

### T4 · 同一个进度条，五份实现、两种高度、三种圆角

- **类别**：Token 一致性
- **位置**：

  | 文件 | 高度 | 圆角 |
  | --- | --- | --- |
  | `LinkForm.vue:344-346` | **6px** | 3px |
  | `Pomodoro.vue:293-296` | **6px** | 3px |
  | `AboutTab.vue:330-332` | 4px | **999px** |
  | `DownloadsTab.vue:369-371` | 4px | **2px** |
  | `Tasks.vue:321-324` | 4px | **2px** |
  | `app.css:396-398`（`.meter`） | 4px | 2px |

- **不一致之处**：五份 CSS 结构完全一致（`.bar { height; border-radius; background: var(--c-bg-2); overflow: hidden }` + 内部填充 `transform: scaleX`），靠复制粘贴扩散到五个文件，随后各自漂移：高度 6/4px 两种，圆角 3px / 2px / 999px 三种。
  **可感知性分级**（这里必须分清，否则会误判）：
  - `999px` vs `2px` 在 4px 高的条上**完全等同**（2px 恰为半高，两者都是胶囊端）→ **不可感知，不必动**；
  - **6px vs 4px 高度是可感知的**：上传进度条比任务进度条粗 50%，两个页面并排看会读成两套组件；
  - 圆角写法不统一本身不可感知，但它让「改一处视觉」必须改五个文件。
- **依据**：同日审计 `#22–#25` 已经点出「同一个 `width` 过渡在五个文件里各写一遍」，当时**只换了属性、没有合并实现**，并把合并留作后续。这次的分歧（高度/圆角）就是那个决定的可预见代价。
- **最小收敛方案**：抽 `.progress` / `.progress > i` 进 `app.css`（高度 4px、圆角 2px、`--dur-progress` + `--ease-out`），五处改引用；`LinkForm` 的 6px 一并降为 4px。**不动 `.meter`** —— 它必须保留原生 `<progress>` 以维持读屏百分比语义。
- **优先级**：中（高度差可感知；且这是「改一处要改五处」的持续成本）
- **✅ 已落地**：抽成 `app.css` 的 `.progress-bar` / `.progress-bar > *`（4px、2px、`--dur-progress` + `--ease-out`），
  四处改引用，各自只保留本页的差异（`Tasks` 的行间距、`LinkForm` 的失败换色）。
  `LinkForm` 的 6px/3px 一并降为 4px/2px —— 这是本项唯一的观感变化。
  **落地时踩到一个坑，值得记**：共享类**不能叫 `.bar`** —— `PdfView` / `PptxView` 的翻页工具栏也叫 `.bar`
  （`display:flex` 的按钮行）。四条 scoped 规则今天互不干扰，但一旦 app.css 里出现全局
  `.bar { height: 4px }`，工具栏没声明 height，就会被压成一条 4px 灰线。所以共享类名取了 `.progress-bar`。
  **Pomodoro 没有并进来**，因为它量的不是「任务进度」而是「时间流逝」（`--dur-slow` + `linear`），
  且它的 `.bar` 同样面临上面那个命名冲突 —— 合并只会换来一次改名，没有收益。

### T5 · `--shadow-1` 这个变量不存在，PDF 页的阴影永远走兜底值

- **类别**：Token 一致性
- **位置**：`frontend/src/components/raw/pdf/PdfPage.vue:123`
  ```css
  box-shadow: var(--shadow-1, 0 1px 2px rgb(0 0 0 / 6%));
  ```
- **不一致之处**：`tokens.css` 只定义了 `--shadow-sm` 与 `--shadow-md`，**没有 `--shadow-1`**（用「引用集合 − 定义集合」比对，全项目只有 `--shadow-1`、`--font-body`、`--p` 三个未定义，后两个是死代码与内联变量，见 §5）。
  因为写了兜底值，浏览器不报错、构建不失败、界面上看不出来 —— 但它带来一个真实后果：`tokens.css:126/197/268/339/410/481` 在 **六套深色主题里都把 `--shadow-sm` 覆盖成 `0 1px 2px rgba(0,0,0,0.5)`**（注释写明「深色下阴影要更重，否则卡片浮不起来」），而 PDF 页**永远停在 6% 黑**。
  于是深色模式下：卡片阴影 50%，PDF 纸页阴影 6%，同一个界面上相差 8 倍。
- **依据**：`tokens.css:13` 的硬约定；以及这属于「静默失效」—— 兜底值让它既不报错也不显眼，只能靠比对变量集合发现。
- **最小收敛方案**：改成 `var(--shadow-sm)`，删掉兜底值。**兜底值本身就是缺陷的掩体**：真值缺失时宁可让它一眼看出来，也不要悄悄降级。
- **优先级**：中（深色模式下可感知；浅色下 6% 与 `--shadow-sm` 的 6% 几乎同值，所以只在深色暴露 —— 这解释了它为什么能活到现在）
- **✅ 已落地（同日）**：改成 `box-shadow: var(--shadow-sm);`。浏览器实测：浅色 `rgba(35, 33, 28, 0.06)`、深色 `rgba(0, 0, 0, 0.5)` —— 修复前两处都是 0.06。顺带复查「引用集合 − 定义集合」，「被引用但未定义」从 3 项降到 **1 项**：`--font-body` 死代码已删（T9），只剩 `--p`（组件用 `:style` 内联写入，属正常，见 §6）。

### T6 · 「遮住页面」的浓度有 **三** 个值，且变量作用域过窄

> **⚠️ 本条在落地时更正过一次**：本节初版写的是「两处」，漏了 `IngestPanel.vue:146`。
> 漏的原因很具体——当时只 `grep` 了 `app.css` 与 `Pomodoro.vue` 两个文件，就下了「全项目两处」的结论。
> 教训记在这里：**「全项目只有 N 处」这种断言，必须对 `src/` 全目录 grep，不能对想得到的文件 grep。**

- **类别**：Token 一致性
- **位置**：
  - `styles/app.css:347` `--dialog-backdrop: rgb(20 18 14 / 0.42)` —— **定义在 `dialog` 选择器内部**
  - `styles/app.css:382` 弹窗遮罩 `background-color: var(--dialog-backdrop)`
  - `components/IngestPanel.vue:146` `.ingest { --dialog-backdrop: rgb(35 33 28 / 0.32); }` —— 注释写明「采集是高频动作，不该把整页压黑」
  - `components/Pomodoro.vue:240` `background: rgba(35, 33, 28, 0.12)` —— 硬编码，无注释
- **不一致之处**：同样是「全屏压暗页面」，三个浓度 **0.42 / 0.32 / 0.12**，色值两组（`20 18 14` 与 `35 33 28`）。
  根因是 `--dialog-backdrop` 被声明在 `dialog` 选择器里，**只对 `dialog` 子树可见** ——
  非 `<dialog>` 的遮罩拿不到它，只能自己再写一个；而 `IngestPanel` 恰好也是 `<dialog>`，
  于是用「重定义同名变量」的方式做了局部覆盖，导致这个变量名有两个定义点、语义却是「每个面板自便」。
- **依据**：同一种视觉语义（遮罩）应有明确的档位，而不是「每个用到的地方写一个数」。
  但**「统一到一档」是错的**：`IngestPanel` 那条 0.32 带理由，且理由（高频开合的面板不该把整页压黑）成立。
  真正要修的是「值散落 + 变量只在子树可见」，不是「把三档压成一档」。
- **✅ 已落地（结论与初版不同）**：
  - `tokens.css` 出**两档**：`--overlay-scrim: 0.42`（设置这类低频模态）、`--overlay-scrim-soft: 0.32`（高频面板）。
  - `IngestPanel` 的局部重定义改为 `--overlay-scrim: var(--overlay-scrim-soft)`，**浓度不变**（仍是 0.32），
    但它现在是一个有名字的档位，而不是一个只有本文件知道的魔法数。
  - `Pomodoro` 的 0.12 → **0.32**，用 soft 档。理由：它在一次专注里会被开合好几次，与采集面板同类；
    而 0.12 淡到几乎看不出有层浮起来，那才是真正的问题——浓度本身不是。
  - 删掉 `dialog` 里的局部 `--dialog-backdrop`，`::backdrop` 直接读 `--overlay-scrim`。
  - **实测过一件事再敢用**：`::backdrop` 是否继承自定义属性。理论上有过变化（早期版本 ::backdrop 不继承），

### §2 附（题 3）· 主题切换是否会因动效产生错位

结论：**切换本身是干净的，没有闪烁或跳变；但有一类元素会滞后 150ms。**

- 切换机制正确：`composables/useTheme.js:74-82` 的 `apply()` 只写 `document.documentElement.dataset` 三个属性，CSS 变量随之整体重算，**不触发任何组件重渲染**，也不重放任何动画。`public/theme-boot.js` 在 CSS 之前写好属性，首屏无白闪。
- 弹窗：`app.css:355` 的 `transition-property` 只有 `opacity, display, overlay`，主题切换不触碰这三个属性 → **弹窗不会重新播放入场**，无闪烁。
- 流式内容：全项目 `<Transition>` / `<TransitionGroup>` 使用次数为 **0**，Markdown 走 `v-html` 重绘，**没有过渡可错位**。
- **唯一滞后项**：凡是声明了颜色类 `transition` 的元素，变量一变就会**播一次 150ms 过渡**：
  - `.btn`（`app.css:176`，`background` / `border-color` / `opacity` 各 150ms）
  - `.input` / `.textarea`（`app.css:233`，`border-color` 150ms）
  - `.theme-card`（`AppearanceTab.vue:145`，`border-color` / `box-shadow` 150ms）
  页面底色、面板、文字全部瞬时翻转，只有按钮和输入框在 150ms 内缓过去。深色↔浅色跨度大（`#FFFEFA` ↔ `#232F2B`），这 150ms 会读成「按钮比页面慢一拍地变暗」。
  主题卡这一处更明显：卡片自身 `background` 没有 transition（瞬时），只有 `border` 在过渡 —— **同一张小卡里，填充已经变了、描边还在路上**。
- **建议**：这属于「不该有」的过渡 —— 主题切换是整页瞬时事件，颜色过渡只应服务于**悬停/聚焦**这类指针驱动变化。给 `html` 加一个切换期间的抑制类是常规做法。
- **✅ 已落地**：`useTheme.apply()` 在改 `dataset` 前后包一层 `.theming` 类，CSS 里 `html.theming *, html.theming *::before, html.theming *::after { transition: none !important }`（作用域写 `*` 而不是列举类名：将来新增的带颜色过渡组件不必回来补名单）。
  `apply()` 里本来就有一次 `getComputedStyle(root)`（读 `--c-bg-0` 写 `theme-color`），它本身就是样式结算点 —— 读计算值会把属性变更 flush 掉，于是「新配色 + transition:none」落在同一帧，**不会有一条过渡被启动**。所以没有额外读布局，也没有用 `requestAnimationFrame`。浏览器实测：挂上 `.theming` 时 `.btn` 的 `transition-duration` 为 `0s`，移除后恢复 `0.15s`。
  三个细节值得记：
  ① **用 `*` 而不是列举类名**。列 `.btn, .input` 那种写法今天对、明天新增一个带颜色过渡的组件就漏，而这条规则的意图本来就是「这一帧所有过渡都停」。
  ② **加/删必须包在同一个任务里，中间不能有绘制**。`apply()` 里本来就要读 `getComputedStyle(root)` 取 `--c-bg-0`，那一下就是样式结算点 ——
  属性变更与 `transition:none` 在同一次 recalc 里生效，过渡根本不会被创建；随后删类，后续交互过渡照常。
  浏览器实测：挂上 `.theming` 后 `.btn` 的 `transition-duration` 是 `0s`，删掉后回到 `0.15s`。
  ③ 色值变化的 recalc 发生在「过渡被禁用」期间，之后那次 recalc 的色值没有再变，所以**不会有一条过渡在删类瞬间被补启动**。

### K3 · 出题卡并发浮现：10 条同时起步，没有错峰

- **类别**：克制性
- **位置**：`views/Practice.vue:758`（`.gen-card { animation: pop-in 0.22s ease }`）
- **过度之处**：`.gen-card` 是列表项，`v-for` 出来的每张卡都挂同一条 `animation`，**没有 `animation-delay`**。出题完成后一屏可能同时出现 8–12 张，于是 10 个元素在同一帧各自上浮 6px + 淡入。
  单看一张卡完全克制（220ms、6px、合成器）；**并置之后是「整页往上涌一下」** —— 这正是题目第 4 条所说的「多个动效产生视觉竞争」。附带一个具体后果：用户在出题完成的瞬间想点第一题，那一瞬间整列文字正在移动。
- **依据**：Apple HIG —— 不要让人「等待动画完成才能做下一件事」；并发的同类空间运动会叠加成整页尺度位移，而整页位移是前庭负担最大的一类（这也是同日审计把它列入 reduce 覆盖的原因，但它只解决了 reduce 用户，没解决默认用户）。
- **最小收敛方案**：**保留 opacity、去掉 `translateY`**。即 `pop-in` 只做淡入（`opacity 0→1`），不再位移。这是「保留一个主运动（淡入）+ 零辅助运动」的最小收敛，比加 `stagger` 更省 —— 加延迟会让最后一张卡更晚出现，反而拉长等待。
  若产品坚持要「一条条出来」的节奏感，则改为**只给前 3 张加位移**（`nth-child(-n+3)`），其余纯淡入。
- **优先级**：中
- **✅ 已落地**：`pop-in`（`opacity + translateY(6px)`）改为 `fade-in`（只有 `opacity`）。
  **连带删掉了 `.gen-card` 的 `@media (prefers-reduced-motion)` 覆盖** —— 它当初存在是为了抑制「整列上涌」那个空间位移；
  位移没了，一条纯淡入不需要 reduce 覆盖（与 `.toast` / `PdfPage` 的处理一致）。
  这不是撤销同日审计的 #28，而是那条要抑制的东西已经不在代码里了。
  **没有采用 `nth-child(-n+3)` 的错峰方案**：加延迟会让最后一张卡更晚出现，等于把「等动画」拉长，与 HIG 那条正好相反。

- **类别**：跨组件一致性
- **位置**：全部 `translate` / `transform` 声明
- **实测**：全项目只有 **2 处**位移变换用于动效 —— `App.vue:508`（通知条 `translateY(6px)` 由下向上入场）与 `Practice.vue:796`（出题卡同向）。其余 `translateY(-50%)` 是垂直居中定位（`CategoryTree.vue:223`、`ItemList.vue:216`），不是动效；`translateX` 只出现在骨架屏扫光上。
  **不存在**「从上方滑入、向侧面滑出」这种方向矛盾 —— 因为**全项目没有任何退场动效**。通知条是「上升入场、瞬时消失」，出题卡只有入场。
- **判定**：单向不对称（有进无出）在题目第 8 条的判据下**不算违规**：空间关系只在「进出配对」时才需要自洽。同日审计也已论证给 toast 加退场会延迟 DOM 移除、对临时元素不划算，结论是**保持现状**。我同意。
- **优先级**：无（记录为已核实）

### 5.1 地基：token 与静默缺陷（T1 + T5）

| 动作 | 结果 |
| --- | --- |
| `tokens.css` 新增动效 token | 5 个时长 + 2 个缓动，含取值来处注释 |
| 20 处声明改为引用 | 非循环动效**零字面时长残留**；剩 2 处 `3s` / `3.2s` 是 reduce 下的循环放慢，故意保留 |
| `--shadow-1` → `--shadow-sm` | 深色下 PDF 页阴影从 6% 变 50% |

**一个差点埋下的坑**：`tools/check_contrast.py` 的 `ROOT_BLOCK` 是硬编码模板，`--write` 会**整份重写** `tokens.css`。
手工往 `tokens.css` 里加的 token，只要有人跑一次生成脚本就会被抹掉。已把 7 个时间 token、两档遮罩、`--scroll-offset`
全部写进 `ROOT_BLOCK`，让它们成为生成物的一部分，而不是手工补丁。

### 5.2 缓动与克制性（T3 + K3 + T2）

- `.meter` 的 `ease` → `var(--ease-out)`。`ease` 是慢启动，与「追上一个已知值」的语义相反，用户会觉得填充比读数慢半拍。
- `pop-in` **整块删除**，`.gen-card` 改用纯 `fade-in`。原方案是「去掉 `translateY` 保留淡入」，落地时发现
  更省的做法是直接复用已有的 `fade-in` 关键帧，`pop-in` 随即消失 —— 于是 **T2「两套关键帧效果相同」也一并消解**，
  不需要再造一个 `.rise-in`。
- 连带删掉了 `.gen-card` 的 `prefers-reduced-motion` 覆盖：**淡入不是空间运动**，不必为此停掉动画。

### 5.3 主题切换（题3）

`useTheme.apply()` 里已有 `getComputedStyle(root)` 这个样式结算点，正好可以用作强制 flush，
所以不需要额外读一次布局。切换时挂 `.theming` 一帧，`.theming` 下禁用过渡，颜色瞬时翻转与整个页面保持一致。

### 5.4 遮罩与浮层（T6 + C1）—— 这里有一处**更正**

**审计初稿错了两处，都记在这里：**

1. **不是 2 处遮罩，是 3 处。** 漏了 `components/IngestPanel.vue:146` 在 `.ingest` 上的 `--dialog-backdrop: 0.32` 覆盖。
   所以本条的标题与结论都从「两个值」改成「三个值」。
2. **那个覆盖本来是生效的，`::backdrop` 会继承自定义属性。** 这一点没有靠猜 —— 写了一个最小用例在 msedge 里实测：
   `dialog { --scrim: var(--scrim-soft) }` 下读 `::backdrop` 的计算背景，得到 0.32。所以「作用域过窄」只对
   **非 `<dialog>` 的遮罩**成立，对 `IngestPanel` 不成立。

落地时**没有把浓度统一成一个值**。`IngestPanel` 的注释给了原因：「采集是高频动作，不该把整页压黑」——
这是个有依据的决定，推翻它等于为了「一致」制造一个更差的结果。所以保留两档：

| token | 值 | 谁用 |
| --- | --- | --- |
| `--overlay-scrim` | 0.42 | `<dialog>`（设置、删除确认等） |
| `--overlay-scrim-soft` | 0.32 | 采集面板、Pomodoro（都是一次会话里反复开合的面板） |

Pomodoro 从 0.12 提到 0.32 —— 它挡满全屏、点遮罩关闭、下层不可交互，行为上就是模态，
不该用另一个更淡的值去暗示「我不是」。**0.12 是三者里唯一站不住的那个**（0.42 之于模态合理，0.32 之于高频面板合理）。

三处浮层（`.overlay` / `.hist-drawer` / `.sheet`）出场统一为 `@starting-style` + `opacity var(--dur-overlay)` 淡入。
后两者不压暗，但都声明了 `role="dialog"`，出场节奏至少要和真弹窗同一套。

## 7. 这条审计的方法教训

两轮下来，真正有价值的发现都不是「读代码读出来的」，而是三类机械比对的结果：

1. **「引用集合 − 定义集合」** 找出 `--shadow-1` 与 `--font-body`。靠读代码永远看不见一个「写了但不存在」的变量，
   因为兜底值让它既不报错也不显眼。
2. **「落地前先查生成链」** 找出 `check_contrast.py --write` 会抹掉手工 token。手工补丁如果不在生成模板里，
   下一次生成就是一次静默回归。
3. **「一句注释也是一个决定」** 找出 IngestPanel 的 0.32 不该被统一。审计初稿把它当成「散落值」，
   读到注释才知道理由（采集是高频动作）。**统一之前先找那个值为什么存在**，否则「收敛」就是拿一致性换掉一个更好的判断。

第 3 条是这份报告最该记住的：**一致性是手段，不是目的**。三个浓度值里真正该改的只有 0.12 那一个，
把它们统一成一个数值，反而会让两个各有道理的决定一起变差。
