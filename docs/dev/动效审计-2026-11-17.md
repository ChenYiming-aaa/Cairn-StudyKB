# 前端动效审计 · 2026-11-17

审计对象：`frontend/src/` 全部 89 个 `.vue` / `.js` / `.css` 文件。
结论口径：**动效是否有目的、节奏是否在感知阈值内、是否走合成器线程、是否尊重减少动效偏好**。
不评价"好不好看"。

---

## 0. 总体结论

| 项 | 数 |
| --- | --- |
| 动效触点总数 | **29** |
| 高优先级 | **11** |
| 中 / 低优先级 | 4 / 14 |
| 建议移除的无目的动效 | **1** |
| 无 `prefers-reduced-motion` 覆盖的动效 | **7 类 / 14 个位置**（其中 **5 类**是无限循环） |
| 触发布局的动画 | **7 条**（5 条进度条 `width` + 1 条栅格列宽 + 1 条 native progress 伪元素） |
| 触发绘制的动画 | **4 条**（骨架屏 / 思维导图 / 刷新线 / 不确定态进度条，均重绘 `background-position`） |

三点判断，先说清楚：

1. **项目没有引入任何动效库**（`package.json` 只有 vue / vue-router / marked / dompurify / pdfjs-dist），
   全部动效是手写 CSS + 少量 `scrollIntoView({behavior:'smooth'})`。这意味着没有"库默认值超标"的隐形债务，
   所有问题都在明面上、可以逐条改。
2. **弹窗动效是全项目做得最对的一处**，也是唯一用了 `@starting-style` + `transition-behavior: allow-discrete`
   + `overlay` 的地方。它可以直接当其余触点的模板，不需要另找方案。
3. **最大的系统性缺口是可访问性**：全项目只有 2 处 `@media (prefers-reduced-motion)`，
   而这两处处理得**恰好符合规范**（调参数而非停掉），说明作者知道该怎么写 —— 只是没铺开。
   7 类未覆盖里 5 类是无限循环，这是这次审计里最值得先动手的部分。

另外，`<Transition>` / `<TransitionGroup>` **在全项目 0 次使用**，所有视图与页签切换都是 `v-show` / `v-if`
瞬时切。四问里"`<Transition>` 只包单根元素 / 同类型切换加 key / `mode="out-in"`"这三条因此**不适用且无需补**——
页签跟视图切换属于高频交互，Apple HIG 的原话就是"避免为频繁发生的 UI 交互添加动效"，不给动效是对的，
这不是缺口。

## 2. 低频过渡

### #8 工作区栅格列宽（侧栏折叠 / 列表宽度）

- **位置**：`frontend/src/styles/app.css:101-118`（107 行 `transition: grid-template-columns 0.18s ease`；
  111-113 行 `body.is-resizing` 下 `transition: none`）
- **动效类型**：低频过渡
- **判定**：**性能不通过**（`grid-template-columns` 是布局属性，每帧重排三列）
- **依据**：判据 §3 只允许 `transform` / `opacity`。这里是全应用最贵的一次动画 ——
  一帧内重排左栏 + 列表 + 详情三个子树。
- **最小改动**：**建议保留现状，不做改动**。理由三条：
  ① 触发频率低（只有点折叠按钮 / 松手结束拖拽时各一次）；
  ② 180ms 落在"简单过渡 100–200ms"窗口内，且已经在拖拽中显式关掉（111-113 行），
     说明作者知道"跟手时不能有延迟"；
  ③ 换成 `transform` 只能给列表面板做位移，邻居不会跟着让位，视觉上会从"布局收拢"变成"面板滑走压住详情"，
     是另一种设计而非优化。**这条记为已知取舍，写进注释即可，不算待修项。**
- **优先级**：中（若不接受取舍，需要重构布局模型，成本远大于收益）

### #9 模态对话框进出

- **位置**：`frontend/src/styles/app.css:336-359`
  （`transition-property: opacity, display, overlay` + `0.14s ease-out` + `allow-discrete` + `@starting-style`）
- **动效类型**：低频过渡
- **判定**：**四项全通过**
- **依据**：
  - 目的性：入场/出场是"状态变化"，遮挡层用 `opacity` 表达"层浮起来了"，用途单一清晰。
  - 节奏：140ms，在 100–200ms 窗口内，且 `<dialog>` 是低频操作，140ms 比 180ms 更贴合"桌面更快"的基线。
  - 性能：`opacity` 合成器；`display` / `overlay` 是离散属性，靠 `allow-discrete` 而不是关键帧，
    不产生逐帧布局。
  - 可访问性：`opacity` 淡入**不属于空间运动**，按 Modern Web Guidance「保留 color / background 这类非运动过渡」的口径，
    这里不加 reduce 覆盖是对的，不是遗漏。
- **备注**：349 行那条注释（"写进 transition 简写会让不认识它的浏览器整条丢弃"）是对的，
  `transition-behavior` 确实必须单独一行。这是全项目唯一按 Modern Web Guidance 写的动效。
- **最小改动**：无。**建议把这块当模板**用于其余浮层。
- **优先级**：低

### #10 对话框遮挡层

- **位置**：`frontend/src/styles/app.css:361-378`（`background-color` / `display` / `overlay`，140ms）
- **判定**：**通过**
- **依据**：`background-color` 属绘制；`::backdrop` 本身不受布局影响。362-364 行把 backdrop 改成滚动容器
  再上 `overscroll-behavior`，是为了"背景页不跟着滚"，不是动效，但和动效同处一块，逻辑正确。
- **最小改动**：无
- **优先级**：低

### #11 平滑滚动（8 处调用）

- **位置**：
  - `frontend/src/components/CategoryTree.vue:117`（侧栏分段跳转）
  - `frontend/src/components/raw/ImageView.vue:71`（命中行居中）
  - `frontend/src/components/raw/pdf/PdfTextPanel.vue:77`（命中行居中）
  - `frontend/src/components/raw/PdfView.vue:140`、`:148`（翻页定位）
  - `frontend/src/components/raw/PptxView.vue:107`（命中行居中）
  - `frontend/src/components/raw/TextRawPane.vue:79`（问答跳转高亮）
  - `frontend/src/composables/useFocus.js:48`（问答跳转高亮）
  - 另有一条间接路径：`frontend/src/components/raw/pdf/PdfScroller.vue:137` 以 `smooth = true` 调
    本文件的 `scrollToPage()`（103-107 行的三元表达式），实际也走平滑滚动。
- **动效类型**：低频过渡（JS 驱动）
- **判定**：**可访问性不通过**
- **依据**：判据 §4 明确点名"JS 动画库未检查 `matchMedia('(prefers-reduced-motion: reduce)')`"。
  平滑滚动是**前庭敏感最主要的触发源**（整页内容位移，幅度可达上千像素），比任何 opacity 淡入都更该被尊重。
  这 8 处直接 `behavior: 'smooth'` + 1 处间接，全部无条件，无处检查偏好。
  注意 `frontend/src/components/raw/pdf/PdfScroller.vue:171-179` 显式写了 `scroll-behavior: auto` ——
  那条是**对的**（避免 CSS 与 JS 双重平滑），别把它当成遗漏一起改。
- **最小改动**：新增 `frontend/src/utils/motion.js`，导出
  `export const reduceMotion = () => matchMedia('(prefers-reduced-motion: reduce)').matches` 与
  `export const scrollBehavior = () => (reduceMotion() ? 'auto' : 'smooth')`，
  8 处把 `behavior: 'smooth'` 换成 `behavior: scrollBehavior()`。
  这是唯一不改变"有动效"这一决策、只让它可被关掉的改法。
- **优先级**：**高**

## 3. 装饰性动效

### #12 骨架屏 shimmer

- **位置**：`frontend/src/styles/app.css:522-537`（`animation: shimmer 1.4s ease infinite`）
- **动效类型**：装饰性
- **判定**：**可访问性不通过 + 性能不通过**
- **依据**：
  - 可访问性：无限循环，**全项目无任何 reduce 覆盖**。判据 §4 第一条就是"无限循环动画无覆盖"。
  - 性能：动画改的是 `background-position`（531-536 行），属绘制属性，不走合成器。
    面积不小 —— 列表页 5 行 × 2 块（`ItemList.vue:137-141`）、详情页 4 行（`ItemDetail.vue:304`）、
    导航栏 3 块（`CategoryTree.vue:159-161`）、问答 4 块（`Ask.vue:533-535`），同时跑约 16 块。
  - 目的性：**通过**。骨架屏表达"内容正在来"，是状态反馈的一种，不是装饰。
- **最小改动**：两件事分开做。
  ① 覆盖：按 Modern Web Guidance 的"调参数"分支（与项目现有 `.spin` 写法一致）加
     `@media (prefers-reduced-motion: reduce) { animation: none }` —— 骨架屏停住不影响"还有东西要来"的语义，
     因为静态灰块本身就在说这件事，所以这里该**停**而不是放慢；
  ② 性能：改 `background-position` 为伪元素 + `transform: translateX()`，或直接接受
     （16 块 4px 高的条带，绘制成本可控）。**建议只做 ①，②记为可接受**。
- **优先级**：**高**（①）

### #13 思维导图加载骨架

- **位置**：`frontend/src/components/MindmapPane.vue:88-95`（`animation: shimmer 1.2s ease-in-out infinite`）、
  `115-123`（`@keyframes shimmer`）
- **判定**：**可访问性不通过**
- **依据**：同上，无限循环无覆盖。面积更大（`min-width: 160px` × `min-height: 120px` 的整块渐变扫过）。
  另外这里与 #12 **同名 `@keyframes shimmer` 但关键帧不同**（一个走 `background-position: 100%→0`，
  一个是 `0 → -200%`），同名不同实，日后改一处必然踩到另一处。
- **最小改动**：
  ① 加 `@media (prefers-reduced-motion: reduce) { .mindmap-box.loading { animation: none } }`；
  ② 把本组件的 `@keyframes` 改名 `mindmap-shimmer`，消除与 `app.css` 的同名冲突。
- **优先级**：**高**（①）

### #14 出题中状态点（空 span）

- **位置**：`frontend/src/views/Practice.vue:488`（`<span class="pulse" />`），
  样式来自 `frontend/src/styles/app.css:297-309`
- **动效类型**：装饰性（实为无目的）
- **判定**：**目的性不通过 → 建议移除**
- **依据**：这是本次审计唯一一条真正"为了动而动"的。`<span class="pulse" />` 是空元素，
  `.pulse` 只给 `animation: pulse 1.2s infinite`（改 `opacity`），**没有任何规则给它宽高或底色**
  （`Practice.vue:728-734` 的 `.gen-bar` 只给了 flex 与字号，没有对子 span 定尺寸）。
  一个零尺寸的行内盒动画自己的 `opacity`，屏幕上**什么都不会变** —— 它既不传达状态，也不引导注意力，
  只在合成器上白跑一条无限动画。
  判断它是不是漏了 `.dot` 类很简单：`StatusBadge.vue:20` 里的同类写法是
  `<i class="dot" :class="{ pulse: ... }" />`，靠 `.dot`（`app.css:290-295`，6px + `currentColor`）才有形。
  这里少了 `.dot`。
  旁边的文字「正在出题，已收到 n / m 题」已经完整表达了状态，不需要第二个信号。
- **最小改动**：**删除 488 行的 `<span class="pulse" />`**。
  （若产品要求保留一个视觉呼吸点，则改成 `<span class="dot pulse" />` —— 但那样就是"多一个重复信号"，
  且仍缺 reduce 覆盖，所以首选删除。）
- **优先级**：中

## 4. 状态反馈动效

### #15 「整理中」徽标呼吸点

- **位置**：`frontend/src/styles/app.css:297-309`；使用处 `frontend/src/components/StatusBadge.vue:20`
- **判定**：**可访问性不通过**
- **依据**：`animation: pulse 1.2s ease-in-out infinite`，无限循环，**无 reduce 覆盖**。
  目的性通过 —— 后台正在跑的任务，界面需要一个"还在动"的信号，`opacity 1 → 0.35` 的呼吸是标准做法。
- **最小改动**：按"停掉不影响语义"分支处理（文字「整理中」已在徽标里）：
  `@media (prefers-reduced-motion: reduce) { .pulse { animation: none } }`。
- **优先级**：**高**

### #16 计时中的小圆点

- **位置**：`frontend/src/App.vue:427-448`（432 行 `animation: breathe 1.6s ease-in-out infinite`；
  435-438 行 `.paused` 已 `animation: none`）
- **判定**：**可访问性不通过**
- **依据**：同上，无限循环无覆盖。435-438 的处理值得肯定：暂停时用 `animation: none` 而不是
  `animation-play-state: paused`，正好避开了判据 §4 点名的"暂停的动画可能意外恢复"那个坑。
  但"运行中"这一态仍缺 reduce 覆盖。
- **最小改动**：`@media (prefers-reduced-motion: reduce) { .mini-dot:not(.paused) { animation: none } }`。
  不能写成 ` .mini-dot { animation: none }` 覆盖整条类，否则会把 435-438 的 `.paused` 语义一起抹平
  （虽然结果相同，但会让"为什么暂停就不动"这条信息丢失）。
- **优先级**：**高**

### #17 详情页后台刷新扫光线

- **位置**：`frontend/src/components/ItemDetail.vue:481-499`（`animation: detail-refreshing 1.1s linear infinite`）
- **判定**：**可访问性不通过 + 性能不通过**
- **依据**：
  - 可访问性：无限循环，无覆盖。
  - 性能：`background-position` 从 `-40%` 扫到 `140%`（493-498 行），绘制属性，不走合成器。
  - 节奏：`linear` 在这里是**对的** —— 匀速扫描的"扫描线"语义就是匀速，换成缓动反而会让它看起来在加速。
    所以这一条不要按"禁用 linear"去改。
- **最小改动**：加 `@media (prefers-reduced-motion: reduce) { .detail-refreshing { animation: none; opacity: 0.6 } }`
  —— 停住会把这条 2px 的渐变线留成一块半透明静态条，`opacity: 0.6` 让它在静态下仍读作"有东西在这儿"，
  避免变成一条脏边。
- **优先级**：**高**

### #18 原生进度条的确定值填充

- **位置**：`frontend/src/styles/app.css:400-404`（`transition: inline-size 0.3s ease`）
- **判定**：**性能不通过（受原生限制，可接受）**
- **依据**：`inline-size` 是尺寸属性，走布局。但 `::-webkit-progress-value` 是浏览器内部伪元素，
  无法塞入子元素做 `transform: scaleX`，除非放弃 `<progress>` 换成两个 `div` ——
  而项目在 `app.css:380-381` 明确写了"一律用原生 `<progress>`"是为了读屏能念百分比。
  **用一点布局换取无障碍语义，这个交换是对的。**
- **最小改动**：不改属性。把 300ms 压到 **200ms**（进度值本身就是离散跳变，300ms 会让填充条明显落后于读数，
  尤其 `OcrProgress` 逐页更新时）。若要更省，`transition: none` 也可接受 —— 4px 高的条，
  跳变不会读成卡顿。
- **优先级**：中

### #19 不确定态进度条

- **位置**：`frontend/src/styles/app.css:409-424`（`animation: meter-indeterminate 1.4s ease-in-out infinite`）、
  `426-430`（`@media reduce { animation-duration: 3.2s }`）
- **判定**：节奏 / 可访问性**通过**，性能**可接受**
- **依据**：
  - 这一条**已经有 reduce 覆盖，且是规范推荐的做法**。Modern Web Guidance 的 `motion` 指引写着：
    当减少动效的策略是"改参数"时，用 `@media (prefers-reduced-motion: reduce)` 只改 `animation-duration`，
    并在示例里把 `progress:not([value])` 从 1s 放慢到 20s。这里 1.4s → 3.2s 完全同构。
  - 至于为什么"放慢"不"停"：406-408 行的注释已经说清了 —— 不确定态**没有百分比可显示**，
    停住就只剩一条空槽，用户读成"卡住了"。这时候动效本身就是唯一的状态信号，
    属于必须保留的那一类，不能按"无限循环一律停"处理。**这个判断是对的，别改。**
  - 性能：`background-position` 是绘制属性。4px 高、单条，成本可忽略。
- **最小改动**：无（如要再稳一档，可把 3.2s 提到 4s，收益可忽略）
- **优先级**：低（记录为已核实）

### #20 按钮内旋转环

- **位置**：`frontend/src/styles/app.css:436-462`（444 行 `animation: spin 0.9s linear infinite`）、
  `471-475`（`@keyframes spin { to { rotate: 1turn } }`）、`477-482`（`@media reduce { 3s }`）
- **判定**：**四项全通过**
- **依据**：

### #21 通知条入场

- **位置**：`frontend/src/App.vue:472-483`（482 行 `animation: slide-in 0.18s ease`）、`497-506`（关键帧）
- **判定**：**通过（可访问性记一条建议）**
- **依据**：
  - 节奏：180ms，在 200ms 内；一次性的入场，不是循环。
  - 性能：`opacity` + `translateY(6px)`，两样都在合成器上。6px 的位移极小，不构成前庭负担。
  - 目的性：通知从右下角浮出，表达"这是刚发生的一件事"，用途明确。
  - 可访问性：无覆盖。但按 Modern Web Guidance 的口径，只有空间运动/缩放/旋转/持续动画才需要抑制，
    一次性 6px + opacity 属于可保留范围。**判定不通过的话会说不过去。**
- **最小改动**：可选：`@media (prefers-reduced-motion: reduce) { .toast { animation: none } }`（成本一行，收益边际）。
  真正值得做的是**退场对称性**：当前只有 `slide-in`，通知消失是瞬时的。
  但给退场加动画会延迟 DOM 移除、也让"它走了"这件事变慢，对 transient 元素不划算 ——
  **建议不加退场，保持现状。**
- **优先级**：低

### #22 上传进度条

- **位置**：`frontend/src/components/ingest/LinkForm.vue:344-356`（355 行 `transition: width 0.3s ease`）
- **判定**：**性能不通过 + 节奏不通过（轻）**
- **依据**：`width` 是布局属性，判据 §3 明令不允许。触发频率是本组里最高的：
  上传进度按块回调，一秒内可能变好几次，而每次 300ms 的 `width` 过渡都要求一次布局 +
  父容器 `.bar`（`overflow: hidden`）的裁剪重绘。
- **最小改动**：把填充条改成 `transform: scaleX()` 方案 ——
  `.bar i { transform-origin: left; transform: scaleX(var(--p)); transition: transform 0.2s var(--ease-standard) }`，
  模板把 `:style="{ width: pct + '%' }"` 换成 `:style="{ '--p': pct / 100 }"`。
  若不想动模板：退一步把 300ms 压到 **150ms** 并保留 `width`（减少单次过渡占用时长，不解决问题但减半开销）。
- **优先级**：**高**

### #26 专注计时进度条

- **位置**：`frontend/src/components/Pomodoro.vue:293-304`（304 行 `transition: width 0.9s linear`）
- **判定**：**节奏不通过（最严重的一条）+ 性能不通过**
- **依据**：
  - 节奏：**900ms** 远超任何窗口 —— 展开/折叠上限 300ms，复杂编排上限 500ms。
    而页面上的倒计时数字**每秒才跳一次**（`useTimer.js` 的 `setInterval` 是 1s），
    900ms 的填充条意味着它永远追不上数字：数字跳到 42%，条要花近一秒才爬过去，
    然后立刻被下一次更新打断。视觉结果是"条比数字慢半拍"，读起来像在缓冲。
  - 缓动：`linear` 本身对计时进度是对的，问题只在时长。
  - 性能：`width`，布局属性。进度条每 4px 高的元素，但父级 `.bar` 的裁剪区每秒重排一次。
- **最小改动**：`transition: width 0.9s linear` → **`transition: width 0.35s linear`**。
  350ms 略大于 1s 的更新间隔的 1/3，既能抹平跳变，又不至于和数字脱节。
  更好的做法仍是 `scaleX`，但**这一条先改时长**，因为节奏问题是这里最刺眼的部分。
- **优先级**：**高**

## 5. 现代 CSS 原生方案评估

用 `npx -y modern-web-guidance@latest` 检索了 `dialog motion` / `animate-element-entry-exit` /
`animate-to-from-top-layer` / `motion`，逐项对照当前实现：

| 原生能力 | 当前状态 | 建议 |
| --- | --- | --- |
| `@starting-style` + `transition-behavior: allow-discrete` + `overlay` | **已用于** `dialog` / `::backdrop`（`app.css:336-378`） | 保留。这是本次审计里唯一完全合规的浮层实现，可作为其余浮层的模板 |
| 同上，用于通知条 `[popover]` | **未用**。`.toast` 走 `@keyframes slide-in`（`App.vue:482`），`popover="manual"` 容器已就位（`App.vue:261`） | **不替换**。关键帧一次性入场已经够用（180ms、合成器、无退出需求）；换原生方案收益是"语法统一"，但会引入 `allow-discrete` 对 `display` 的时序依赖，而通知条是随时增删的列表，风险大于收益 |
| `document.startViewTransition()` | 未用 | **不建议引入**。唯一候选是页签/视图切换，但那是高频交互 —— 给它加过渡本身违背 HIG「不要为频繁交互加动效」。而且 hash 路由 + `v-show` 的机制下，view transition 会拿到整页快照，桌面端收益低、翻车成本高（快照期焦点丢失、PDF canvas 重绘闪烁） |
| `animation-timeline: scroll()` 滚动驱动动画 | 未用 | **不适用**。项目没有需要"随滚动进度变化"的装饰效果；报告里的滚动相关需求都是"跳到某处"，那是 `scrollIntoView` 而非滚动动画 |
| `progress` 元素替代手搓进度条 | 部分用于 `.meter`（OcrProgress 等），5 处仍是 `div > i` | **建议逐步迁移**（见 #22–#25 的合并建议）。原生 `<progress>` 同时解决"读屏念百分比"与"`width` 过渡"两件事，且项目已有 `.meter` 样式可复用 |

**结论：不需要为新 API 而改。** 唯一值得动的原生能力（`<progress>`）项目已经在用，只是没铺开。
