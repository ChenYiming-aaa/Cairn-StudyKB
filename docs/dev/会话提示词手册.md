# 会话提示词手册

> **作用域**：**人读文档**。这是写给你（项目所有者）看的操作手册，agent 不需要读它——agent 按 `00-总纲.md` §6 的会话工作法自行工作。
> **冲突时**：本文件只是操作建议，与 `00-总纲.md` 冲突时以总纲为准。

---

## 1. 唯一要记住的原则

> **提示词只负责「路由」，不负责「装载信息」。**

所有任务细节、技术约束、接口形状、验收标准，**已经写在文档里了**。提示词的作用只有三件事：

1. 告诉 agent 读哪两个文件（入口 + 当前里程碑）
2. 划定这次的范围（做到哪个任务为止）
3. 规定收尾动作（跑什么、写什么、提交什么）

**为什么不能把细节写进提示词**：一旦你复制一段"用 trafilatura 抓网页"进提示词，你就有了第二份真相源。下次改文档时忘了改提示词，两边就打架——这正是我们花大力气建契约层想避免的事。

## 2. 四个标准模板

### 模板 A · 新里程碑开工（最常用）

```
M5 开工。

先读 docs/dev/00-总纲.md 和 docs/dev/milestones/M5-计时与交付.md，读完后按 M5 §2 逐条核对环境。

本次只做 T5.1 到 T5.4（计时与仪表盘），T5.5 之后先不动。

做完跑一次 scripts/status.py 把输出贴给我，然后按 M5 §8 收尾（写 HANDOFF、commit、tag、push 到 GitHub）。

遇到文档之间冲突、或需要我拍板的设计取舍，先停下来问我，不要自己决定。
```

**四个要素，一句都不能少**：
- 读什么（两个文件路径）
- 做到哪（明确的 T 编号区间）
- 怎么算完（跑哪个脚本）
- 什么情况停（冲突/取舍）

### 模板 B · 继续上一个会话（同一里程碑）

```
继续 M5，从 T5.5 开始。

先读 docs/dev/HANDOFF.md 的「当前状态」表 + 最后两条，再跑 python tools/doc_check.py 和 scripts/status.py，
确认当前实际状态后直接动手，不用再读一遍整个 M5 文档（除 T5.5 之后的部分）。
```

> 第二个会话**不需要重述任何背景**。台账 + 状态脚本就是为这个存在的。

### 模板 C · 修 bug

```
这里有个问题：<一句话描述现象 + 怎么复现>。

先定位根因再改，不要先改代码再猜原因。
改完在 HANDOFF 里记一条"根因是什么"，然后 commit。

如果根因涉及契约（表结构/接口形状），停下来先跟我说。
```

> 关键在"先定位根因"。不加这句，agent 很容易加个 `try/except` 把错误吞掉。

### 模板 D · 里程碑验收

```
M3 做完了，做验收。

按 M3 §5 的 DoD 清单逐条核对，每条给 PASS/FAIL 和证据（命令输出或文件路径）。
FAIL 的条目列出原因，不要修，先给我看。

另外跑一遍 scripts/verify_m3.py 贴输出。
```

> 关键在"FAIL 的先别修"。让它一边验收一边修，你会失去一份可信的验收报告。

## 3. 反例（这几句话会让 agent 失控）

| ❌ 别这么说 | 为什么会出问题 |
|---|---|
| "帮我做 M4" | 8 个任务一口气做完，中途必然丢上下文，最后交付质量最差的那天 |
| "按照之前的计划继续" | 新会话没有"之前"，它只能瞎猜或重读一堆无关文档 |
| 把里程碑文档内容复制进提示词 | 制造第二份真相源，下次改文档必漂移 |
| "尽量做好一点 / 完善一下" | 没有可验证标准，agent 只能自己发明验收条件 |
| "顺便把 M4 的出题也做了" | 一次一个里程碑是硬规则，混做会导致数据模型反复改 |
| "有什么想法你直接改" | 它会在你没注意时改技术选型。要放权时至少加一句"改选型前先说" |

## 4. 什么时候该开新会话

| 情况 | 开新会话 |
|---|---|
| 里程碑切换（M4 完成 → M5） | ✅ 必须 |
| 同一里程碑，但已做完 3 个以上功能模块 | ✅ 建议 |
| 你发现它在"回忆"之前写过的代码，而且回忆错了 | ✅ 立即 |
| 同一个 bug 连修两次没修好 | ✅ 立即（上下文里的假设已经错了，重开更干净） |
| 只是改个文案、调个样式 | ❌ 不用，直接说 |

## 5. 懒人版（一条命令搞定）

如果你不想每次拼提示词，用这一句就够：

```
按 docs/dev/00-总纲.md §6 的会话工作法开工，当前里程碑：M5，本次做到 T5.4。
```

**这一句为什么够**：总纲 §6 已经写死了"开场读哪两个文件、跑哪两个脚本、收尾做哪三件事"。你只需要告诉它"哪个里程碑"和"做到哪"。

## 7. 你可以随时问它的三句话

不需要它写代码时，这三句能拿到高质量回答：

- **"现在项目的真实状态是什么？跑一遍 status.py 和 doc_check.py 给我看。"**
  比问"做到哪了"可靠，因为它拿事实回答。

- **"这个设计你为什么不选另一种做法？代价是什么？"**
  逼它说权衡，而不是给你一个听起来合理的结论。

- **"如果三个月后我自己看这段代码，哪里会看不懂？"**
  让它主动暴露复杂度，比事后重构便宜。

## 8. 执行中遇到小问题，在哪问

**可以问，但要分清两类，因为答案的落点不同。**

| 问题类型 | 例子 | 在哪问 | 关键动作 |
|---|---|---|---|
| **决策类** | "这个接口要加字段吗？" "要不要换个方案？" | **规划会话**（和写代码的会话分开也行） | 定完**必须写回文档**（ADR 或 HANDOFF），否则下个会话不知道这回事 |
| **执行类** | "这个报错怎么修？" "这段为什么跑不通？" | **执行会话**（正在写代码的那个） | 那边有完整上下文：代码、报错、刚改的文件 |

**核心风险**：跨会话的决策如果不写回文档，就**等于没发生**。下个会话读到的是旧文档，会照着旧文档把决定推翻一遍。

所以最简单的约定是：

> 在规划会话里问完，让 agent 把它写进 `docs/dev/HANDOFF.md` 的「待裁决冲突」或新开一条 ADR，然后再回执行会话继续。

**问的时候别贴整个文件**，给三样东西就够：

1. 你想做什么（一句话）
2. 报错原文（完整粘贴，别截断中间）
3. 你刚才改了什么（如果没有就写"没改"）

**什么时候不用问，直接让执行会话自己决定**：改文案、调间距、变量名、日志格式——这类改错了也不心疼的事。**什么时候必须先问**：涉及表结构、接口形状、技术选型、目录结构、依赖新增。
