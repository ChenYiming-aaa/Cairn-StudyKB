## 一、分层规划（2026-11-10）

### 1.1 为什么必须分层

M8 的 9 个任务不是并列关系，是**一条流水线**：协议没定，就没法把重依赖从包里剔除（剔了就直接 ImportError）；
组件包没造出来，下载中心就没有可下载的东西；下载中心没有，欢迎页的「选装」就只是个空壳。
按「地基 → 削体 → 造件 → 装件 → 自更新 → 发布」切六层，**每一层都有独立出口断言**，
任何一层做完停下，产品都处在一个能跑、能回滚的状态。

| 层 | 任务 | 这一层做什么 | 出口断言（不过就不往下走） | 依赖 |
|---|---|---|---|---|
| **L0 地基** | T8.0 | 组件协议 + `ComponentClient` + 三条降级路径 + `COMPONENT_MISSING` + 空壳 worker | 无组件状态下 `verify_m1..m7` 全绿；问答 / 采集 / 导航不 500；协议自检 exit 0 | — |
| **L1 削体** | T8.1 | spec `excludes` 三个重栈，打 0.2.0-alpha 包，量体积 | 安装包 ≤ 170 MB；解包 ≤ 750 MB；无组件跑 `verify_m1..m7` 仍全绿 | L0 |
| **L2 造件** | T8.2 | `tools/build_components.py` + 三个真组件（embed / asr / browser） | 三个包各自 `--selftest` 退出码 0；zip + sha256 回写 `components.json` | L0 |
| **L3 装件** | T8.3 → T8.4 | 下载中心后端（断点续传 / sha256 / 卸载）+「下载」tab + 欢迎页选装 | 装 / 卸 / 取消三路有明确反馈；断网续传真测过；坏包被拒且不留残目录 | L1 L2 |
| **L4 自更新** | T8.5 → T8.6 | Electron 更新器 + 版本元数据（`GET version` / 三处 0.2.0） | 0.1.9 包能发现 0.2.0；断网给人话；取消下载文件删净；装完无孤儿 `cairn-backend.exe` | L3 |
| **L5 发布** | T8.7 → T8.8 | 发布物料、两枚 Release、干净机器走查、`verify_m8.py` 收口 | 干净机器（无 Python/Node）装 → 装 embed → 问 → 卸 → 再问不崩 | L4 |

**为什么 L1 在 L2 之前**（与任务书编号相反）：任务书按「协议→瘦身→造件」排，但**瘦身不依赖组件包存在**，
它只依赖「缺组件时能优雅降级」这件事成立。先削体可以先量到真实体积、早发现 excludes 误伤，
而组件包的生产（PyInstaller ×3 + zip）是纯机械工，放到知道「到底要压多少」之后做更省事。
唯一要守的是：**L1 打出来的 alpha 包在没有组件时必须是"功能少一点"，不是"坏了"** —— 这正是 L0 的出口。

### 1.2 本部分（L0 / T8.0）的边界

**做**：协议文档、`services/components.py`、`app/components.json`、三个空壳 worker + `--selftest`、
`embed` 的**端到端管道**（真跑子进程编向量）、`asr` / `browser` 的**降级判定**、错误码与前端文案、`verify_m8.py` §1。

**不做**（留给 L2，写在这里是为了不让它变成"忘了"）：`asr` 与 `browser` 的**真实管道调用**。

**理由**：`embed` 一个人就能把协议证完 —— 一段文本进、一组向量出，无回调、无长任务、无窗口交互。
`asr` 要带进度回调与长任务看门狗，`browser` 要带可见窗口的登录流程与 `capture_json` 的响应钩子；
这两条管道化**要等真组件存在时才有东西可测**，现在做等于把假实现搬进子进程，L2 还要重写一遍。

但**降级判定现在就必须是真的**：`resolve()` 必须能正确回答"这个组件到底有没有"，
否则 L1 一削体，用户看到的就是崩，而不是降级。

### 1.3 三个跨层决定（后面几层都依赖它们，改起来贵）

**D1 · 可用性三态 `resolve(id)`：`"component"` > `"local"` > `None`**

1. 组件目录存在且 `hello` 通 → `"component"`（走子进程）
2. 否则本进程能 import 到对应库 → `"local"`（源码运行的日常态）
3. 否则 → `None`（降级）

**为什么保留 `local`**：源码运行时 torch 就在本机，验收脚本 `verify_m1..m7` 也全跑在源码里。
若只认组件，开发态会掉进"向量永远不可用"，`verify_m3` 的向量断言与日常调试一起废掉。
而**冻结包里 `excludes` 让 `find_spec` 返回 None**，于是自动落到组件 —— 不需要写"打包版专用分支"，
这是这套判定最值钱的地方：**同一份代码，两种形态，没有 if is_frozen**。

**D2 · 一个错误码 `COMPONENT_MISSING`，`detail` 写组件 id**

- 数据契约 §10 原写 `TRANSCRIBE_NO_ASR`，与 M8 §2.2 的 `COMPONENT_MISSING` 不一致 → 按 M8 定案统一，**已回写数据契约**。
- 三种缺组件的**表现不同**，别一把抓：`embed` 静默降级（不报错，只在检索页提示一句），
  `asr` / `browser` 报错（用户正在等这一步的结果，不报就是"卡住"）。

**D3 · 组件进程跟着主进程死**：`stop_all()` 挂在 FastAPI lifespan 的 shutdown 上。
不挂的后果是每次退出留一堆孤儿 exe，而且 Windows 下**占着的目录删不掉**（v0.1.0 的 `app.asar` 被锁已有前车之鉴）。

### 1.4 每层的验收入口

| 层 | 命令 |
|---|---|
| L0 | `uv run python scripts/verify_m8.py` + `verify_m1..m7` |
| L1 | 同上 + 量 `desktop/release*/Cairn-*-setup.exe` 与 `_internal` 体积 |
| L2 | `uv run python tools/build_components.py --selftest` |
| L3 | `verify_m8.py` 的安装 / 卸载 / 续传三组 |
| L4 | 0.1.9 包实机点「检查更新」 |
| L5 | 干净机器走查单（写进 `T8.8`） |

## 二、L0（T8.0）实现中发现的问题

### S-1 `fallback` 在"没装向量组件"时报成了「向量距离太远」（**真缺陷，本轮已修**）

**现象**：缺组件时（或任何 `ready=False` 的时候）只要全文零命中，`/api/search` 返回
`fallback="vector_below_threshold"`。前端 `Ask.vue` 的 `fallbackHint` 只认
`vector_disabled` / `like_short_query` → **一句提示都不显示**。用户不知道自己已经在用纯文字检索。

**根因**：`retriever.hybrid()` 里 `limit_distance` 只看"全文有没有命中"，不看"向量跑没跑"：

```python
limit_distance = None if fts_rows else get_settings().vector_min_distance
vec_ids = vector_ids(...) if ready else []          # ready=False → 必空
if not vec_ids and limit_distance is not None:       # ← 于是恒成立
    fallback = "vector_below_threshold"
```

M3 时期 `ready` 几乎总是真（装了 torch 就有模型），这条分支没被走到；M8 把向量变成可选之后，
它就成了"默认路径"，所以现在才暴露。

**处理**：加 `ready` 前提；同时把"没装组件"与"关了开关/没下模型"分开
（`vector_component_missing` / `vector_disabled`），前端各给一句人话。
漏了这一步，T8.4 的「问答页顶部提示条」就没有可靠的触发条件。

### S-2 「去设置 → 下载」这句文案现在略超前（**有意为之，T8.4 收口**）

组件的两条报错文案现在指向「设置 → 下载」，而该 tab 里还是 M6 的占位
（"现在装的是全量包，三个组件都已经在里面"）。这在 v0.1.0 全量包里**是对的**，
在瘦身后才有意义 —— T8.4 会用真卡片替掉占位，届时两者自然一致。**本轮不改**，
否则要写一句两头都不对的话。

### S-3 三条降级路径的"缝合点"清单（留给 L2，别当已完工）

| 位置 | 现在 | L2（T8.2）要补 |
|---|---|---|
| `embedder` | **已接真管道**（`kind=doc/query` 走子进程，前缀在组件里加） | 组件内部换成真 bge 模型 |
| `transcriber._load_model` | 只判"有没有"，缺了报 `COMPONENT_MISSING` | `transcribe` op：主程序 ffmpeg 抽 16k wav → 传路径 → 组件回 segments，进度每 30s 必须有 |
| `browser` | 只换了提示文案，`available()` 仍只看本进程 playwright | `render` / `capture_json` / 登录助手三个 op。**登录窗口必须活在组件进程里**，不能跨管道开 |

也就是说：**冻结包 + 只装 embed = 现在就能用**；装 asr / browser 要等 L2。

### S-4 组件 stderr 全部按 WARNING 记进 `app.log`

组件只在真出问题时往 stderr 写（约定），所以日常不吵；但真出问题时一次能刷几十行。
排障时按 `[embed]` / `[asr]` 前缀过滤即可，不建议降成 DEBUG —— 那样等于没有。

### S-5 数据契约 §10 的 `TRANSCRIBE_NO_ASR` 与任务书冲突（**已按 M8 定案统一**）

契约 §10 原写"转录 → 报 `TRANSCRIBE_NO_ASR`"，任务书 §2.2 写"新增错误码 `COMPONENT_MISSING`"。
按 §5.1 的裁决链契约优先级更高，但它那句是 M6 阶段在没有设计错误码时写的登记句，
且 `TRANSCRIBE_NO_ASR` 在代码里从未存在过。**决定**：统一为 `COMPONENT_MISSING`（`detail=组件 id`），
已回写数据契约 §10 与接口契约的错误码清单，`doc_check` 通过。理由：一个码能让前端只写一条人话，
三个码会让三处界面各写一遍。

### S-6 `verify_m8.py` 是分组长大的

目前只有 `§1 protocol`（37 条）。L1 加 `§2 slim`、L3 加 `§3 install`、L4 加 `§4 update`，
`--only <组>` 可单跑。**不要**在 L1 之后把 §1 的断言删掉换成新的 —— 它是唯一能证明
"没装组件时应用照常能用"的东西。

### S-7 `proc.kill()` 之后 `poll()` 仍是 `None`（**真缺陷，连跑三次才暴露**）

**现象**：`uv run python scripts/verify_m8.py` 第一次 37/37，把 `CAIRN_COMPONENT_MODE`
换成 `process` 再跑就挂一条「组件进程真的退出了 — 仍在运行」。同一份代码、同一台机器、
只差一个环境变量，是典型的**时序偶发**。

**根因**：`kill()` 只是发信号，Windows 上进程句柄要 `wait()` 才真回收；紧接着调
`poll()` 经常还拿得到 `None`。验收脚本用它判断"死了没有"，于是随机失败。

**处理**：`Session.stop()` 里 `kill()` 之后补 `proc.wait(timeout=5)`。除了修掉这条偶发，
它还顺带治了"卸载时目录被占用"—— 进程没真退，`rmtree` 就会留半个目录。

### S-8 `components.py` 一开始 414 行，拆成两个

总纲 §7 定的是单文件 ≤300 行。第一版把"协议收发"和"清单/判定/状态"写在一起，
L3 还要往里加下载逻辑，必然爆。拆法：`component_proc.py`（进程、管道、超时、重启）
+ `components.py`（清单、三态判定、状态、卸载）。**判据是"改哪个文件"**：
调协议语义改前者，改"装没装/怎么跑"改后者。

### S-9 冻结包里的 `console=False` 与组件无关

主程序 `cairn-backend.spec` 是 `console=False`（用户看不到黑框）；**组件 exe 反过来必须是
`console=True`**，否则 stdout 不可用、管道直接废。这条 T8.2 打包时容易顺手继承错，
先记在这里（任务书 §5 T8.2 也写了，但两处 spec 长得像，容易复制粘贴出错）。

## 三、L1（T8.1）主包瘦身

### 1.1 实测体积（2026-11-10）

| 项 | v0.1.0 | 瘦身后 | 目标 |
|---|---|---|---|
| 安装包 | 426,428,660 B（426 MB） | **172,035,473 B（172 MB）** | ≤170 MB → **差 2.0 MB，未达标（待裁决）** |
| 后端解包 | 965 MB | **90 MB** | — |
| 安装后整目录 | ~1.4 GB | **474 MB** | ≤750 MB ✅ |

**没达标的那 2 MB 不是我们的代码**：172 MB 里约 **124 MB 是 Electron 本身**。
任务书 §1 按「Electron ~230 MB 解包 → ~70 MB 压缩」估的，实际 Electron 45.2.3 =
`Cairn.exe` 249 MB + `locales` 49 MB + `dxcompiler.dll` 25 MB + 其余 ≈ **355 MB 解包**。
三行后端的差异（120 → 90 MB）只值 10 MB 压缩体积，剩下的差就是壳变大了。

**还没动的杠杆（都不做，等裁决）**：

| 杠杆 | 省 | 代价 |
|---|---|---|
| 删 `dxcompiler.dll`（25.8 MB）+ `vk_swiftshader*`（6 MB） | ~11 MB 压缩 | WebGPU / 软件 Vulkan 不可用；界面用不到，但要一次真机启动确认 |
| 换 audio-only 的 ffmpeg 构建 | ~10 MB | `avfilter` 等 DLL 是 `ffmpeg.exe` 的硬链接依赖，删不得；只能整包换，要重验抽音轨与抖音路径 |
| 删 `LICENSES.chromium.html`（6 MB） | ~1.6 MB | **违反 Chromium 的分发许可，不做** |

### 1.2 两个白捡的裁剪（都是"别人捎进来的"）

1. **babel 的 locale-data 31 MB** — `trafilatura` → `courlan.filters` → `from babel import Locale`，
   而 PyInstaller 的 babel hook 会收全世界的 `.dat`。我们只留 `root/en/en_US/zh/zh_Hans/zh_Hant`，
   31 MB → 2 MB。**安全性依据是代码**，不是乐观：courlan 全文只有一处 `Locale.parse()`，
   外面包着 `except (TypeError, UnknownLocaleError)`，缺表只是"该过滤器不生效"。
2. **Electron 的 `locales/`** — 50 个语言包 49 MB，`electronLanguages: ["zh-CN","en-US"]` 后 2 MB。
   这条没实测过就不知道：`locales` 比后端整个 `_internal` 的一半还大。

### 1.3 `compression: "maximum"` 对 NSIS **无效**（省了我一次白折腾）

按它重打了一遍，安装包只差 **2 字节**。NSIS 的载荷本来就是 solid LZMA，
electron-builder 的 `compression` 只影响 zip/7z/tar 那几个 target。想要更小只能删内容。

### 1.4 `CAIRN_COMPONENT_MODE=none`：验收"没装组件的机器"的唯一办法

源码态永远能 import 到 torch，`resolve()` 就永远不会返回 `None`；
而冻结包靠 `excludes` 制造"没有"，开发机上模拟不出来。加了这个值之后：

```bash
CAIRN_COMPONENT_MODE=none uv run python scripts/verify_m1.py   # …m7 同理
```

**回归结果（全绿）**：m1 52 · m2 118 · m3 61 · m4 69 · m5 57 · m6 78 · m7 41。
`verify_m8` 本身在 none 下没有子进程可跑，会以 `exit 2`（环境不满足）退出 —
它验的是"协议往返"，不是"降级"，别拿它当无组件回归用。

### 1.5 torch.distributed 那条历史约束换了住处

v0.1.0 为省 12 MB 排除过 `torch.distributed`，结果 sentence_transformers 半初始化炸掉。
现在 torch 整个不在主包里，这条约束搬进了 `tools/build_components.py` 的 embed 段
（`collect_submodules('torch.distributed')`）。主 spec 里留了反向指引，改一边会被另一半的注释提醒。

## 四、L2（T8.2）三个组件

### 2.1 三个包的真实体积（比任务书估的都大）

| 组件 | 解包 | 下载（zip） | 任务书估 | 差在哪 |
|---|---|---|---|---|
| `embed` | 690 MB | **262 MB** | 520 / 190 MB | `torch/lib/torch_cpu.dll` 一家 309 MB；另有 scipy 72、transformers 48 |
| `asr` | 257 MB | **100 MB** | 165 / 60 MB | `av.libs` 65 + ctranslate2 61 + onnxruntime 38 + numpy 28 |
| `browser` | 134 MB | **49 MB** | 104 / 38 MB | playwright 驱动 104 + Python 运行时 |
| 合计 | 1.08 GB | **411 MB** | ~685 / ~290 MB | 装全了确实回到"1.4 GB 时代"，但每一步都是用户自己点的 |

体积估算偏小的原因找到了：任务书按"解包后的库目录"估，实际每个组件还要带一份
Python 运行时（~20 MB）+ numpy（28 MB，`ctranslate2` 与 `scipy` 都要它）。
`app/components.json` 里的 `size` / `sha256` 现在都是**打包脚本回写的实测值**，不是估的。

### 2.2 为什么要新开一个 `backend/shared/` 包

`shared/browser_pw.py`（playwright 的机械动作）与 `shared/cookies.py`（Netscape 格式）
被**主程序和组件同时用**，理由只有一条：**两份副本必然漂移**。
开发机走本进程（`app/services/browser.py`），装机版走组件；两边一旦对不上，
问题只在装机版复现 —— 而装机版是最难查的地方。

但主程序在冻结包里 `excludes` 掉了 playwright，组件又**不能** import `app`
（会把 fastapi / sqlite / trafilatura 拖进组件包）。所以这份代码必须满足两个条件：
**只依赖标准库或 playwright**、**不 import `app`**。设置一律当参数传。

`browser.py` 因此瘦成"调度层"：取设置 → 决定走本进程还是管道 → 报状态。

### 2.3 协议补上"空闲超时"（`idle=True`）

任务书说转录"无上限但每 30 秒必须有 progress"，原来的实现只有一个总截止时间 ——
转录 20 分钟的视频必然超时。`component_proc.Session.request(idle=True)` 改成
**每收到一条消息（含 progress）就把截止时间往后推**：转录用 120 s 窗口、
登录用 30 s 窗口。这不是"更宽松"，是"卡死能判出来、慢不算卡死"。

### 2.4 真模型下"可复现"只能到容差级（`verify_m8` 一条断言改口径）

空实现时"同样文本 → 同样向量"比的是**相等**；换成 bge 之后第一次跑就红了。
根因不是随机性：这次送 1 条、上次送 2 条，**批大小不同 → BLAS 的归约顺序不同**，
末位差 1e-7 量级。要求改成 `< 1e-4`，理由写在断言旁边。

顺带两条断言也按真管道改了：转录素材从"随便一个 .py 文件"换成**现场生成的静音 wav**
（空实现只查路径存在，真组件必须能解 wav）；组件默认模型目录用
`CAIRN_MODELS_DIR` 指到项目的 `data/models`，免得验收脚本去拉 90 MB。

### 2.5 繁简归一留在主程序，不进组件包

`zhconv` 是主包依赖。组件回 `segments` 原文，主程序 `_transcribe_remote` 里再转简 ——
"拿到 segments 之后改写文本"本来就不需要音频，放哪边都一样快，但组件能少一个依赖。

### 2.6 自检素材刻意"假"，验的是打包不是准确率

- `embed`：真模型 + 一句中文，只断言"维度自洽、已归一化"；
- `asr`：**现场生成 1 秒静音 wav**，允许 0 段（VAD 会把静音干掉）；
- `browser`：`data:text/html,...` 本地地址，不联网。

拿真实站点/真实语音当自检素材会把"打包坏了"和"网断了/没登录"混在一起。
反过来，**不允许**在自检里换成假向量/假结果 —— 那样 `torch_cpu.dll` 没打进去也照样"通过"。

### 2.7 装完真的能用（手工走了一遍解压路径）

不是只看自检：把 zip 解到临时数据目录的 `components/<id>/`，
用 `DATA_DIR=<临时> CAIRN_COMPONENT_MODE=process` 起主程序 ——
`resolve()` 认到 `component`，`browser.render()` 与 `embedder.encode_docs()` 都真跑通了
（512 维、|v|=1.0、查询向量因前缀而不同）。zip 根目录必须是 `cairn-<id>.exe` + `_internal/` +
`manifest.json`，`components._argv()` 就是按这个位置找入口的。
