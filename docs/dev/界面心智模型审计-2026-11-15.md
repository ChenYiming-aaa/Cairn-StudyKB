# 界面心智模型审计 · v0.3.1

> **审的是什么**：界面是否按「用户做这件事时的思路」组织，而不是按系统的数据模型组织。
> **不审**：配色、间距、动效、视觉还原度；也不提新功能。
> **与 `交互断裂清单-v0.4.md` 的分工**：那份是「点了没反应 / 接口缺失 / 状态丢了」的施工单，已全部勾完并有复核；
> 这份是「能点，但组织方式让人形成错误预期、或让他多做一步」的审计。两份重叠的地方在条目里注明。
> **方法**：静态读码（`frontend/src/` 全部页面、路由、浮层组件）+ 与 `api/client.js`、`composables/*` 对照。
> **没做的**：本轮未实机点击；凡是标「判据」的结论都能在代码里指到行。初稿标「推断」的 4 处已全部回代码查实（§5），
> 其中试用页那条推断**被推翻**，判定随之改了（见 §4 表下注）。
> **口径**：只有能指出具体元素、能说明用户会形成什么错误预期（多做/漏做哪一步）、能给最小改动的，才记为问题。

## 0. 一句话结论

界面骨架是按「用户的活」分的，不是按表分的——五个主导航（知识库 / 检索 / 学习 / 练习 / 复习）就是五件不同的事，
内容详情页的页签也是按「看内容时会切换的视角」切的（摘要 / 笔记 / 原文 / 导图 / 记录），这两处是全站最正确的地方。

断裂集中在三个位置：

1. **筛选区**（知识库左栏）：工作区、状态、分类、标签四种「缩小范围」的手段同权重平铺，其中两个「全部」语义不同、两个搜索框作用域不同。
2. **交接处**（出口与下一步）：任务中心、错题本、粘贴入库、零命中采集——用户完成了动作，界面不告诉他"接着去哪"，或给了一个去不到那的按钮。
3. **口径处**（同一个数字两处不同说法）：「今日」条上的待整理是全库数、仪表盘上分今日/全库；「连续学习」副标题写死一句与事实无关的话。

31 个界面里：1 个判「需要重组」（知识库左栏），24 个「局部断裂」，6 个逻辑自洽
（整理笔记、学习记录、出题中、番茄钟、试用页、演示横幅）。

初稿留的 4 项「待确认」已全部查证落地（§5），其中 3 项不必再猜、1 项（待判行的「你的答案」）
确认为接口缺口；**因此没有遗留的待确认项**，改动全部可以在现有接口上做完或只补一列。

## 2. 逐界面分析

### 1. 知识库（`frontend/src/views/Knowledge.vue`）

- **用户目标**：在一堆内容里找到一条，读它；顺手知道"还有多少没整理"。
- **目标可见性**：符合。三栏结构本身就在说"左边挑、中间选、右边读"，顶栏「＋ 采集内容」是唯一实心主按钮，与"往库里加东西"这个前置目标对应。
- **信息分组**：问题。三栏里塞了两处「全部」：左栏工作区段第一行是「全部」（`WorkspaceBar` 的 `{ key: '', name: '全部' }`），紧下方状态段第一行是「全部内容」（`StatusFilter` 的 `{ key: '', label: '全部内容' }`）。前者只清工作区这一维，后者清全部四维。两个词相邻、字数相近、计数取的都是全库总数——用户点「全部」发现列表还是上次筛选过的样子，会认为"这个全部坏了"。
- **决策点**：问题（轻）。列表工具栏的「开始整理 N 条」把当前筛选（分类/标签/工作区）带进请求（`organizePending` 传了三个参数），但按钮文案只说"待整理 N 条"——用户以为在整理全库，实际只整理了当前这一撮，剩下的明天还在。后果可预期性不足。
- **出口与下一步**：符合。采集完成走 `onOpen` → 回知识库并选中新入库那条，是全站最完整的一条链路。
- **认知负荷**：偏高。进入本页时顶栏常驻 12 个可交互元素（两个折叠钮、5 个导航、连接状态、「还差一步」、任务、专注、采集、齿轮），再加「今日」条 6 个元素，而本次任务只需要"挑一条读"。其中「今日」条是信息行、与本任务无关，但它占掉了首屏一整行的垂直空间。
- **最小改动**：① 把 `WorkspaceBar` 的「全部」改成「全部工作区」（或删掉，让"清全部"只有一个入口）；② 「开始整理」按钮在有筛选时文案带上范围，如「整理这批 12 条」。
- **判定**：局部断裂。

### 2. 仪表盘（`frontend/src/views/Dashboard.vue`）

- **用户目标**：确认今天学了多久、还剩多少没处理，然后决定现在做什么。
- **目标可见性**：符合。六张卡，数字大、标签小，两张带 `cursor:pointer` 直接跳去能干活的页面。
- **信息分组**：基本符合（今日 / 本周 / 分布三段）。问题：「分类分布」六行是纯 `<li>`，不可点，而上面四张卡里两张可点——同一屏内"能不能点"不一致。用户看到「数据结构 12」想去看这 12 条，点了没反应，会以为筛选坏了。（这是 v0.4 清单 M1 里那句"分类分布若顺手，行可点"的遗留项。）
- **决策点**：问题。「连续学习」卡的副标题是写死的一句 `<span class="card-sub">今天还没学，不算中断</span>`，不看数据。今天已经专注过 30 分钟的人看到这句，会怀疑"是不是没记上"。
- **出口与下一步**：符合。两张卡分别带 `?status=pending` 与 `/review`，落点接得住数字。
- **认知负荷**：正常（一屏看完，无跨页记忆）。
- **最小改动**：① 分类行改成按钮 → `/?category=<名>`（`Knowledge.vue` 已支持 `query.category`）；② 「连续学习」副标题按 `today.focus_seconds`/`sessions` 切换成"今天已学 25 分钟"或原句。
- **判定**：局部断裂。

### 3. 「今日」条（`frontend/src/components/TodayBar.vue`）

- **用户目标**：扫一眼今天要处理的数字，点进去。
- **目标可见性**：符合。四格数字 + 「详情 →」，可点的两格有 hover 提示。
- **信息分组**：问题（口径）。整条以「今日」开头，但第一格「待整理」取的是 `today.pending_total`（全库待整理），仪表盘同名卡取的是 `pending_items`（今日新增待整理）并在副标题才写"全库还有 N 条"。同一个词在两处是两个数，用户在知识库顶部看到 12、进仪表盘看到 3，会判断为统计不一致。
- **决策点**：符合（两格各自带筛选条件跳转）。
- **出口与下一步**：符合（M1 已修）。
- **认知负荷**：正常。
- **最小改动**：第一格文案改「待整理（全库）」或「待整理 · 全库 12」，与仪表盘的「今日待整理」明确区分。
- **判定**：局部断裂。

### 4. 知识库左栏（`components/CategoryTree.vue` + `filters/*`）

- **用户目标**：把列表收窄到"我现在想看的那一撮"。
- **目标可见性**：问题。左栏顶部有一个搜索框，placeholder 是「筛选分类或标签」；列表栏顶部也有一个搜索框，placeholder「搜索标题」。两个框长得一样、位置相邻（一个在左、一个在右），作用域完全不同：左栏那个只过滤左栏里的分类名和标签名，一个内容都不搜（`shownCategories` / `shownTags`）；列表那个才搜内容。用户想找"那篇讲 B+ 树的文章"，十个有八个会先在左栏那个框里打字，然后看到「没有匹配的分类或标签。换个词，或清空上面的筛选」，误以为库里没有这条。
- **信息分组**：问题（本页最实质的一处）。四段同权重纵向平铺：工作区（用户自建）、状态（系统字段）、分类（模型给的）、标签（模型给的）。它们的层级关系只写在注释里（"工作区在状态快筛之上、分类之上"），界面上只有一条分隔线和一点字重差异。用户脑子里只有"我想看哪一坨"，界面却要求他先分清"这是我自己划的抽屉还是机器给的归类"。
- **决策点**：符合（再点一次已选项 = 取消，这一条做得对）。
- **出口与下一步**：问题（轻）。列表因筛选变空时，空态说「换个关键词，或点左栏『全部内容』」——「全部内容」这四个字确实存在，但它埋在状态段第一行，而用户刚点过的是分类或工作区，视线停在上半部分，会先去找「全部」并点它（那个只清工作区）。
- **认知负荷**：偏高。同一屏四个维度 + 两个搜索框 + 两处「全部」，用户要记住"哪个清哪一维"。
- **最小改动**：① 左栏搜索框改成「在分类/标签里找…」并移进「分类」标题行内（或直接删掉，列表搜索已覆盖）；② 工作区那个「全部」改「全部工作区」，全站只保留一个"清全部"入口；③ 四段加两个分组标题：「我的工作区」/「机器整理的」（下辖分类、标签），状态段留在最上（它是"还没处理"的提醒，不是分类）。
- **判定**：需要重组（这是全站唯一一个）。

### 5. 内容列表栏（`components/ItemList.vue` + `list/ItemRow.vue`、`BulkMoveBar.vue`）

- **用户目标**：在几十条里挑一条打开。
- **目标可见性**：符合。搜索框 + 计数 + 每行标题/状态/分类/时间，层级清楚；勾选框常驻低透明度，批量能力可发现。
- **信息分组**：符合（按"一条内容"聚合，而不是按字段列表）。
- **决策点**：问题。勾选若干条后出现的批量条，目标默认是「未归类」（`BulkMoveBar` 的 `target = ref('')`，提交时 `'' → null`）。用户勾了 5 条、想"移到某个工作区"，如果没注意下拉还停在默认值就点了「移到」，这 5 条会被**移出**原工作区。后果可撤销（再移回去），但方向与用户意图相反，且按钮文字「移到」不含目标名。
- **出口与下一步**：符合（H4 已修：失败项留在勾选里、按钮显示 `移到中 3/20`）。
- **认知负荷**：正常。
- **最小改动**：按钮文案跟着下拉走：`移到「未归类」`/`移到「数据结构」`；或在未选目标时禁用（把默认值从"未归类"改成"请选择"）。
- **判定**：局部断裂。

### 6. 内容详情面板（`components/ItemDetail.vue`）

- **用户目标**：读这条，判断要不要整理、要不要改笔记。
- **目标可见性**：符合。标题最大，5 个页签平铺在标题下方，第一个页签就是"读"。
- **信息分组**：符合，且是范本。页签是「摘要与要点 / 整理笔记 / 原文 / 思维导图 / 学习记录」——全是"我看这条时会切换的视角"，没有一个页签叫"元数据""实体""记录"。试卷会自动隐藏「整理笔记」（不出笔记），也是按用户预期来的。
  - 一处小问题：页签名「摘要与要点」，面板里的标题叫「关键点」。同一个东西两个词。
  - 一处结构问题：`工作区` 是个 `<select>`，但被放进了 meta 行，夹在状态徽标、分类 chip、标签 chip、"笔记已手改" chip 之间。一排放只读的标签中间夹一个可编辑下拉，用户会当成又一个标签，读不出"这里能改归属"。而"把这一条移到别的工作区"除此之外只有回列表勾选这条路。
- **决策点**：符合（整理前 `note_edited` 会确认覆盖；整理中按钮禁用并转圈）。
- **出口与下一步**：问题。这条内容出过的题，在详情里看不到——「学习记录」只有专注轮次，没有作答/错题。用户想知道"我在这条上练过什么、错了什么"，得去复习页，而复习页只能按到期/错题看、不能按内容过滤，于是他要把"我刚才读的是哪条"记在脑子里再去找。这是全站最明显的一处跨界面记忆负担。

## 3. 跨界面的三处系统性问题

单看每个界面都还成立，串起来才露出来的三类负担。

### 3.1 「这个数字是什么口径」要在脑子里记

- 「今日」条的「待整理」= 全库（`pending_total`）；仪表盘的「今日待整理」= 今日新增（`pending_items`），全库那个写在副标题里。
- 「复习」页头的「队列中」（`tracked`）与「今日到期」（`total`）并列，但前者不是"排期总数"，用户没有别的入口能看到它的定义。
- 学习页/练习页顶部的「共 N 条」在超过 50/100 条时会变成"仅显示前 N 条"（已修），但左栏计数仍是全库——两处数字并排时大小不一致是正常的，界面没说这一点。

**最小改动**：凡是口径不是"全库"或不是"今日"的数字，标签里就写出来（全库 / 今日 / 前 N）。

### 3.2 "我刚弄完的那条，从哪再看它一眼"

采集面板关掉之后，全站的定位通道只有一条：`useUi.openItem(id)` → 回知识库并选中。
它被用在：采集完成「去看看」、复习行「看原文」、任务页——最后这个没接。

于是在这几处断了：
- 粘贴入库后（面板直接关，不选中）；
- 任务中心（有 `output_json.item_id`，没入口）；
- 试卷导入后（接了，是全站做得最好的一处）。

**最小改动**：凡是接口里已经带 `item_id` 的地方，都给一个「去看看」，走同一条 `openItem` 通道。

### 3.3 "这条内容的题，去哪看"

详情页 5 个页签里没有"题目/作答"，复习页不能按内容过滤，练习页不能带上某条内容。
用户想知道"我在这条上练过什么"，必须自己记住标题，去复习页翻错题本。

**最小改动**：详情头部加「拿这条练一遍」→ `/practice?item=<id>`（练习页读一次 query 预选）。这只是把已有页面接上参数，不新增页面。

## 5. 四项「待确认」的查证结果

初稿把 4 处标成「待确认（不猜测）」。本轮逐条回代码查实，**没有一项还悬着**：

### 5.1 待判行缺「你的答案 / 参考答案」→ 一半是假问题，一半是真缺口

- **参考答案其实早就在返回里**。`routers/review.py:30-36` 的 `_question_fields()` 白名单含 `answer` 和 `explanation`，`/review/pending` 每条都带；`views/Review.vue:306-331` 的 `row-pending` 只渲染题干、出处、时间和两个按钮——**字段收下了却没用**。→ 纯前端，零接口成本。
- **「你的答案」是真缺**。`db/repo/review.py:150-160` 的 `_PENDING_SQL` 只 `JOIN question` 与 `knowledge_item`，取不到 `quiz_attempt.user_answer`；`_question_fields` 的白名单里也没有这个 key。补法（4 行、不新增端点）：

  ```sql
  (SELECT a.user_answer FROM quiz_attempt a
    WHERE a.question_id = q.id ORDER BY a.id DESC LIMIT 1) AS user_answer
  ```

  再把 `"user_answer"` 加进 `_question_fields` 的 key 元组。
- **为什么「你答的」非显示不可**：这一页的判决动作是「算我对 / 算我错」，判的是**简答**。只看参考答案、看不到自己写了什么，用户只能靠回忆裁决，判错的代价是明天的复习队列。
- 顺带核实了 H5 那条注释：`report()` 落裁定记录时用 `attempts_of(limit=1)` 沿用上一次作答内容（`review.py:96-103`），所以补了这列之后，**人工裁定完的历史记录也是完整的**，不会出现"被判过的那次没有答案"。

### 5.2 试卷复核的字段来源 → 后端早就给了 `source`，前端把它丢了

- `services/exam/audit.py:96-98`：`_issue(code, source="rule")` 返回 `{"code", "level", "message", "source"}`。
- `audit.py:289`：模型侧显式 `_issue(code, source="model")`。
- `audit.py:74-76`：`RULE_CODES` 9 条 / `MODEL_CODES` 4 条，**两集合不重叠**；`SUPERSEDES`（80-83 行）已经把「题干断了」和「选项混进题干」两处同义项收敛过，所以不会同一件事出现两个 chip。
- 结论：**不需要映射表、不需要动后端**，`ExamReview.vue` 渲染 issue 时按 `issue.source` 出 chip（`规则` / `模型`）即可。原审计说"需要与接口契约确认后再决定映射表"——这一步可以删掉。
- 仍然成立的是：`stats.model === 'failed'` 落在批次级 `auditLine`，**这一条即使有了 chip 也不该由它表达**；批次级只说"这次模型没连上"，字段级靠 chip，两者分工清楚。

### 5.3 试用页「问一句」的禁用原因 → 原推断是错的，不构成问题

- `demo/useTry.js:25-30` 的 `splitParas` 按空行切段并过滤空段；`:86` 是 `const paras = computed(() => splitParas(material.value))`——**粘贴材料后立刻就有**，与「整理成笔记」跑没跑过无关。
- 因此按钮的 `:disabled="!ready || !question.trim() || !paras.length || busy"`（`views/Try.vue:194`）里，`!paras.length` 与 `!material.trim()` **完全等价**，是个冗余条件。
- 禁用的真实原因只有三个：没连上 Key、没粘材料、正在跑——三者同屏可见（第 1 步的卡片、输入框 placeholder、`0 字 · 0 段` 的 pill）。**不是隐藏顺序，也不是无说明**。
- 处置：判定改「逻辑自洽」，动作降为「可选：删掉那个冗余条件」。这条是本轮**唯一被推翻的推断**，也在 §4 表下注明了原因。

### 5.4 `HtmlPages` 历史抽屉的层级 → 矮窗口没问题，窄窗口才有

- `.drawer` 是 `position: absolute; top: 0; right: 0; bottom: 0`（`HtmlPages.vue:578-590`），挂在 `.html-page` 上，而后者是 `position: relative; flex: 1; min-height: 0`（`318-326`）——这块区域本身就是「顶栏以下到窗口底」，所以**纵向与 Ask 的 `fixed` 等价**，不存在层级或高度差。
- 内部 `.drawer-list` 是 `flex: 1; min-height: 0; overflow-y: auto`，矮窗口下自己滚，不撑破页面。
- 真正的差别在**宽度**：这里写死 `width: 340px`，Ask 那边是 `width: min(420px, 92vw)`。窗口窄到 340 + 左侧选择器放不下时，抽屉会向左盖住选择器（右对齐、向左生长）。
- 处置：一行加固 `width: min(340px, 92vw)`，与 Ask 对齐；不改定位方式——改成 `fixed` 反而会盖住顶栏。
