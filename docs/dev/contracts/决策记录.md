# 决策记录（ADR）

> **作用域**：只读本文件 + `00-总纲.md`。**不要读** `milestones/*`（那里只有"怎么做"，没有"为什么这样选"）。
> **冲突时**：本文件记录的理由优先于任何里程碑文档对同一决策的描述。想改技术选型，先在这里追加 ADR，不要直接改实现。
> **用途**：上下文被压缩时，任务清单会留下，"为什么这么选"会消失。这个文件就是用来抗压缩的。
> **规则**：新增决策用 ADR 追加；**推翻任何一条，必须先在下面补一条"ADR-0xx 推翻 ADR-0yy"并写清代价**。
> **推翻成本**分三档：低（改一个文件）/ 中（改一层）/ 高（改数据模型或架构，要迁移）。

---

## ADR-001 · 不用 webclaw，改用 trafilatura

**决策**：网页正文提取用 `trafilatura + httpx`，不用 webclaw（Rust MCP）。

**理由**：webclaw 官方只提供 macOS/Linux 预编译二进制，Windows 需自建 Rust 工具链（MSVC + cmake + clang）；主协议 AGPL-3.0，将来分享给他人受约束；它是给 Claude Code/Cursor 用的 MCP 插件，不是嵌入式库。

**推翻成本**：低。`services/fetcher.py` 里 `BaseFetcher` 只有一个子类，换实现不动上层。

---

## ADR-002 · 不用 video-transcriber-mcp，改用 yt-dlp + faster-whisper

**决策**：视频转录 = `yt-dlp`（下载）+ `ffmpeg`（抽音轨）+ `faster-whisper`（识别）。

**理由**：前者是 3K 行的新 Rust 项目，Windows 需手动下 zip、配 PATH；后者三个组件都是 pip/winget 可装、活跃维护多年、能直接用上 3060 的 CUDA。

**推翻成本**：低。同样走 `BaseTranscriber` 接口。

---

## ADR-003 · 不用 softrag / CortexDB / ChromaDB

**决策**：向量检索自己用 `sqlite-vec` 写，不用现成 RAG 库。

**理由**：softrag 21 star、API 频繁 breaking；CortexDB 是 Go 写的难以在 Python 进程内嵌；ChromaDB 是独立服务，违背"一个文件搞定"。RAG 逻辑本身只有一百多行，自己写更可控。

**推翻成本**：低。

---

## ADR-004 · Python 固定 3.12，不用 3.13

**决策**：`uv python install 3.12`，项目锁死在 3.12。

**理由**：本机是 3.13.14，但 `ctranslate2`（faster-whisper 的依赖）、`sentence-transformers` 等二进制包对 3.13 的 wheel 覆盖不完整，装不上就整条视频/向量链路停摆。

**推翻成本**：低（重建环境）。但**踩坑的代价是中**，不要因为"想用新版"去改。

---

## ADR-005 · 不用 ORM，裸 sqlite3 + 薄 repository

**决策**：`db/repo/*.py` 里手写 SQL，不做对象映射。

**理由**：项目要"自己能读懂能改"，ORM 的隐式行为（懒加载、session 生命周期、N+1）会显著提高调试难度；表只有 13 张，手写 SQL 反而更短。

**推翻成本**：高。整个数据层。

> 后续精确化见 **ADR-020**：不是"不用 ORM"，而是"不用对象关系自动映射"；搜索/向量层本来就是 raw SQL，这是本条最硬的理由。

---

## ADR-006 · 端点用 `def` 不用 `async def`

**决策**：所有路由函数写成同步 `def`，内部允许同步阻塞调用 DB 与模型。

**理由**：FastAPI 对同步端点自动丢进线程池，不会阻塞事件循环；而 `async def` 里直接调同步 `sqlite3` 或 `model.encode()` 会**真的**卡死整个服务。这是一个高频且隐蔽的坑。唯一的例外是 SSE 端点（必须 `async`，但内部用 `run_in_threadpool` 包住阻塞部分）。

**推翻成本**：低但**影响面广**，改的时候容易漏。

## ADR-007 · FTS5 必须 `tokenize='trigram'`

**决策**：`chunk_fts` 建表时写死 `tokenize='trigram'`。

**理由**：默认 `unicode61` 按空白/标点切词，中文整句会变成一个 token，"番茄钟"搜不到"番茄钟应该绑定知识条目"。

**已知代价**：trigram 对**少于 3 个字符**的查询无效（"AI"、"错题"两字词搜不到）。对策：查询词长度 < 3 时改走 `LIKE '%kw%'`，返回 `match_type: "like"`。

**推翻成本**：高。建表时写错，后面要重建索引 + 重灌数据。

## ADR-008 · Embedding 用本地 bge-small-zh-v1.5

**决策**：`sentence-transformers` 加载 `BAAI/bge-small-zh-v1.5`（512 维）。

**理由**：DeepSeek 没有 embedding 接口（这是原方案走不通的地方）；本地方案免费、离线、不用再开账号；100MB 模型在 3060 上是毫秒级。

**已知细节**：检索时 query 前**必须**加 `为这个句子生成表示以用于检索相关文章：`，入库的文档向量**不加**。漏了这一步召回会明显变差。

**推翻成本**：中。换模型要重算全库向量（512 维换维度就换表）。

## ADR-009 · 混合检索用 RRF，不做加权求和

**决策**：全文与向量的结果用 `score = Σ 1/(60 + rank_i)` 融合，取前 8。

**理由**：FTS5 的 bm25 分数与余弦相似度量纲完全不同，直接加权需要调参且不稳；RRF 只看排名，天然免调参。

**推翻成本**：低（一个函数）。

---

## ADR-010 · sqlite-vec 加载失败时降级 numpy

**决策**：启动自检，扩展不可用则用 numpy 暴力余弦相似。

**理由**：Windows 上加载 SQLite 扩展存在不确定性；而 10 万 chunk 以内暴力算一次只要几十毫秒，完全够用。**功能降级优于功能中断。**

**推翻成本**：低。

---

## ADR-011 · 复习用固定间隔，不用 SM-2 / FSRS

**决策**：答错 1 天、答对则 1→2→4→7→15 天。

**理由**：SM-2 需要用户对每次作答打 0-5 的"回忆质量"分，实际使用中没人认真打分，数据是脏的；固定间隔在本项目规模下收益已达 90%。

**推翻成本**：低（一个函数），但**不打算改**。

---

## ADR-012 · "子 Agent" = 固定管线，不引多 Agent 框架

**决策**：`services/agents/` 下四个普通 Python 模块（organizer / quizzer / grader / asker），由 `tasks.py` 串起来。

**理由**：节点数固定、走向固定、无自主决策需求。LangGraph/CrewAI 为多团队、复杂状态、生产编排设计，在这里只增加抽象层与调试难度。

**推翻成本**：高（架构级）。**这条要提前和使用者对齐预期**，避免后期觉得"这不是 Agent"。

**术语**：本项目说的"子 Agent"，指的是"按内容类型/任务类型路由的专用 LLM 调用管线"。

## ADR-013 · Electron 端口随机探测 + 启动握手，M1 就定

**决策**：主进程用 `net.createServer().listen(0)` 拿空闲端口，spawn Python 时传 `--port`；确认后端**真的可用**之后再建窗口（握手方式见 ADR-016）。

**理由**：端口硬编码会在用户装了别的东西后静默冲突；不等握手就建窗口会白屏。这两个坑等到最后一天才发现，返工成本极高。

**推翻成本**：低，但**必须早做**。

---

## ADR-014 · 打包用 pyinstaller --onedir，不用 --onefile

**决策**：后端 `--onedir`，前端 `electron-builder --win nsis`。

**理由**：`--onefile` 每次启动要解压到临时目录（慢 3-5 秒），且更容易被 Windows Defender 误报为可疑自解压程序。`--onedir` 启动快、误报少，代价只是一个文件夹。

**推翻成本**：低。

---

## ADR-015 · 前端不用 Pinia

**决策**：状态用 Vue 组合式函数（`composables/use*.js`）自管理。

**理由**：本项目全局状态只有"当前条目""当前任务列表""计时器"三处，Pinia 带来的收益低于新增一层抽象的认知成本。

**推翻成本**：低。如果后期发现跨页面共享状态超过 5 处，再引。

## ADR-016 · 启动握手用 HTTP 轮询，不用 stdout 读 READY（修订 ADR-013）

**决策**：主进程 spawn 后端后，每 300ms 轮询 `http://127.0.0.1:{port}/api/health`，最多 30 秒，返回 ok 后再建窗口。

**理由**：ADR-013 最初设计"Python 打印 `READY <port>` 到 stdout，主进程捕获"。但 PyInstaller 以 windowed 模式打包后，Windows 上 `sys.stdout` 是 `None`，读不到任何输出；若为握手改成 console 模式，用户每次启动都会看到黑框。HTTP 轮询在开发与生产下行为一致，且顺带验证了服务**真的可用**（不只是进程起来了）。

**推翻成本**：低。

## ADR-017 · 思维导图由后端生成 SVG，不用前端 JS 库

**决策**：`GET /api/knowledge/{id}/mindmap` 返回一段纯 SVG（Python 手写布局，零依赖），前端只负责展示。**不引入 markmap / mermaid / d3**。

**理由**：
1. M3 要导出**单文件、离线可开**的 HTML。若用前端渲染库，导出时得把约 1MB JS 内联进去，非常臃肿
2. 后端出 SVG 后，**应用内预览与导出 HTML 用的是同一份图**，不存在"预览好看、导出错位"的漂移
3. 纯 Python 生成约 180 行，无新依赖，符合"十年老库/零依赖"原则

**已知代价**：没有缩放、拖拽、折叠交互，只是静态层级图。够用，因为用途是"概览"而非"编辑器"。

**推翻成本**：中。要做交互式导图就得换方案，但届时导出 HTML 仍应保留静态 SVG 版本。

## ADR-018 · structured_note 用 Markdown 源码编辑，不做富文本

**决策**：`textarea` + 实时预览分屏（左源码右渲染），500ms 防抖。**不引入 Tiptap / Quill / ProseMirror**。

**理由**：富文本编辑器的内部模型（ProseMirror 的 doc/schema/transform）学习成本极高，且与"Markdown 是唯一存储格式"会打架（来回转换必丢格式）。源码编辑对你这个用户反而是优势——你能精确控制结构，思维导图也是从标题层级直接生成的。

**配套决策**：
- 保存后 `note_edited=1`，重新整理前必须确认"将覆盖手改内容"
- 用户笔记进 `chunk`（`source='note'`），**手写的内容必须能被搜到**，否则体验断裂

**推翻成本**：低。

## ADR-019 · 思维导图不落库

**决策**：每次请求现场从 `structured_note` 生成，不存表、不缓存。

**理由**：笔记可随时编辑，存快照必然与正文不一致，而"导图和笔记对不上"是最伤信任的那类 bug。生成成本 2–5ms（几十个节点），完全不值得为它引入缓存失效逻辑。

**推翻成本**：低。

## ADR-020 · 四条技术限制的真实理由与解除条件（精确化 ADR-005）

**背景**：用户质疑总纲红线第 3–6 条是否过于武断。复核后确认：**ADR-005 的表述不够准确**（把"不用 ORM 自动映射"写成了"不用 ORM"），其余三条站得住但缺少"何时该解除"的判据。本条连同改正一起记录。

### 一、多 Agent 框架

**不是难度问题**。LangGraph 几个小时能上手。

**真实理由**：本项目的四个"子 Agent"（整理/出题/批改/问答）每一步的输入输出都是确定的，没有需要 LLM 决定"下一步做什么"的地方。框架的核心价值（动态路由、状态机、多轮协作）用不上，而它带来的抽象层会在调试时变成负担——排查"为什么整理失败"要先穿过 `StateGraph/Node/Edge/Checkpointer` 四个概念。另外框架 API 迭代快，16 天项目锁在年轻依赖上风险不划算。我们已用 `agent_task` 表 + 线程池自己实现了持久化与重试。

**代价**：没有现成的执行轨迹可视化。

**解除条件**：出现「LLM 自主决定下一步」的场景，例如学习教练 Agent 自己判断今天该复习什么、该补哪块知识、先读哪篇。

### 二、ORM 自动映射

**修正**：不是"不用 ORM"，而是"不用对象关系自动映射"。用 Pydantic 做模型 + `repo/` 层封装语义化方法（`get_item()` / `list_items()`），业务代码同样不写裸 SQL 调用。

**最硬的理由**：FTS5 需要 `WHERE chunk_fts MATCH ? ORDER BY bm25(chunk_fts)`，`vec0` 需要 `WHERE embedding MATCH ? AND k = 20`。这两条是 ORM 的表达死角，只能退回 `text()` 原样 SQL —— 绕了但一行没省。而它们恰好是本项目最核心的两个查询。11 张表的普通 CRUD 用 ORM 确实省，但会导致"两套写法共存"，心智切换成本高于收益。

**代价**：手写 SQL 易拼错、必须严格参数化、字段改动要改多处、无类型提示。

**解除条件**：出现大量多表 JOIN 与复杂关联的业务表（当前没有）。若单个模块手写太痛苦，**允许局部引入 SQLAlchemy Core（非 ORM 部分）**，但搜索层保持 raw SQL。

### 三、整包 UI 组件库

**真实理由**：组件库真正解决的是数据表格（排序/筛选/分页/虚拟滚动）、日期范围选择、可拖拽树、富文本、文件上传。这七页一个都没有——左侧"分类树"是按数据 `v-for` 渲染的两级列表，不需要树控件。需要的全是 HTML 原生元素。此外组件库默认样式有强主张，改成自有风格常要写更深的覆盖选择器。

**代价**：按钮/弹窗/Toast/Tab 的样式与交互自写，约多花 2–3 天。

**解除条件**：**单个控件**自写成本超过半天 → 只引那一个专用小库（如日历热力图），不引整包。

### 四、独立向量数据库

**真实理由**：个人知识库三年约 3000 篇 × 8 块 ≈ 2.4 万 chunk，sqlite-vec 的精确检索在几十万量级仍为毫秒级，用量不到容量十分之一。更关键的是**两份数据不同步**：删条目后向量库残留、备份要备两处、换机要迁两套。Milvus 单机需 Docker + etcd + minio，常驻 4GB 起步。

**代价**：无法水平扩展、无法多进程并发写。

**解除条件**：chunk 数超过 50 万，或需要多人/多设备并发写入。

**推翻成本**：以上四条各自的解除时机已写明，达到条件时属于"正常演进"而非"推翻决策"，只需新开 ADR 记录切换原因。

## ADR-021 · LLM 用 deepseek-flash，base_url 不带 /v1，开 low 思考档

**决策**

```python
LLM_BASE_URL = "https://api.deepseek.com"      # 不带 /v1
LLM_MODEL    = "deepseek-flash"
LLM_EFFORT   = "low"                           # low | high | max
response_format = {"type": "json_object"}      # 需要结构化输出时必带
```

**理由（2026-11-05 实测，非凭记忆）**

1. 官方文档现行规范：`base_url (OpenAI)` = `https://api.deepseek.com`，**没有 `/v1`**。这是本次最容易踩的坑——旧模板写的是老地址。
2. 现行模型只有两个：`deepseek-flash`（由 DeepSeek-V4.1-Flash 提供服务）与 `deepseek-v4-pro`。旧名 `deepseek-chat` 仍可调用但被静默转给 flash，不应依赖。
3. 上下文 **1M token**、单次输出上限 **393k**。这意味着原方案"8000 字截断"过于保守——截断阈值改为 **50,000 字符**，理由是成本而非能力。
4. 模型**默认带思考**：实测一个只输出 `{"theme":"番茄钟"}` 的请求，`reasoning_tokens=89`、正文仅 7 token。思考过程放在 `reasoning_content`，`content` 始终是干净答案，所以 JSON 解析不受影响，但成本受影响。
5. `reasoning_effort` 支持 `low|high|max`，默认 `high`。结构化任务（整理、批改）用 `low` 即可；出题、问答可给 `high`。

**代价**

- 每次调用都要为思考 token 付费，即使任务很简单
- 换服务商时必须同步改 `base_url` 的 `/v1` 约定（DeepSeek 是少数不带 `/v1` 的）

**解除条件**：出现需要长链推理的场景（复杂多跳问答、数学推导），把 `LLM_EFFORT` 提到 `high` 或改用 `deepseek-v4-pro`；不需要换架构。

**推翻成本**：低（改配置 + 一个拼 URL 的函数）。

## ADR-022 · `llm_call_log` 增 `reasoning_tokens` 列

**决策**：`llm_call_log` 新增 `reasoning_tokens INTEGER`（可空），取自响应 `usage.completion_tokens_details.reasoning_tokens`。

**背景**：ADR-021 确认 DeepSeek 默认带思考，但新版 M1 T1.5 / §6.11 要求记录思考 token 时，数据契约 §2 的 DDL 还没有这一列——L1 契约与 L3 里程碑冲突。按 §5.1 裁决链以契约为准，由用户裁决「加字段 + 新 ADR」，本条即该 ADR。

**理由**：实测一个只输出 `{"theme":"番茄钟"}` 的请求，`reasoning_tokens=89` 而正文仅 7 token。只看 `completion_tokens` 会把成本归因错；缺这一列就无法回答"钱花在哪了"。

**代价**：多一列存储；换到不返回该字段的服务商时记 NULL，不报错。

**推翻成本**：低。字段只增不改，首次建库直接进 `schema.sql`，无迁移脚本、不递增 `user_version`。



## ADR-023 · 站点登录走自维护的浏览器 profile，不读系统浏览器的 cookie

**决策**：需要登录的站点（B 站字幕、知乎受限页）由后端弹一个**自己控制的**浏览器窗口让用户登录，登录态存在 `data/browser/` 这个独立 profile 里，成功后导出 Netscape `cookies.txt`，供 yt-dlp 与网页抓取共用。不读用户日常浏览器的 cookie，也不走 OAuth 回调。

**背景**：M2 收尾时两个真实缺口撞到一起——B 站字幕要登录，知乎采集报 403。先试了三条"更轻"的路，全部堵死（2026-11-06 实测）：

1. **读系统浏览器 cookie 库**：Chrome 127+ 的 App-Bound Encryption 解不开，Edge 的 cookie 库在浏览器运行时被锁。`transcriber.py` 里已经把这个结论记过一次。
2. **OAuth 式跳转回调**：知乎没有面向第三方的开放平台，B 站开放平台要企业资质。没有 code 可换。
3. **给 httpx 塞 cookie / 伪装请求头**：知乎专栏页对 httpx 返回 403 + **584 字节**；把 UA、Accept、Referer、`sec-ch-ua`、`Sec-Fetch-*` 全部伪装成真实 Chrome，响应**一个字节都没多**。而同一个 URL 用真实浏览器打开，是 403 + **431KB**、抽得出 3184 字正文。

第 3 条是关键的认知修正：**知乎拦的是 TLS/指纹层，不是登录态**。cookie 只证明"你是谁"，证明不了"你是浏览器"。所以对这个站点，光有 cookie 没用，必须有真浏览器；而既然要维持一个真浏览器，登录和渲染就变成同一件事——这也是选这条路的第二个理由。

**理由**：

- 后端跑在用户本机，弹窗是天然成立的；换成服务器部署这条就不成立（届时需要另做方案，见解除条件）
- 一套 profile 同时喂两条链路：导出 cookies.txt 给 yt-dlp 拿 B 站字幕，直接渲染给知乎拿正文。做两套的成本远高于做一套
- 复用本机已装的 Edge（`BROWSER_CHANNEL=msedge`），**不额外下载 Chromium**；只有用户机器上没有 Edge/Chrome 时才需要 `playwright install chromium`
- 登录结果落成标准 `cookies.txt`，用户仍然可以手工替换，不形成锁定

**代价**：

- 新依赖 `playwright`（wheel 约 37MB）。它是可选依赖：没装时 `PLAYWRIGHT_AVAILABLE=false`，站点照常启动，只是浏览器能力与登录入口不可用
- 降级渲染每次 3–5 秒（实测知乎问答 4.6 秒、专栏 7.5 秒含首次 httpx 失败）。只有 httpx 失败时才走，正常站点不受影响
- Playwright 的 sync API 不线程安全、且同一 `user_data_dir` 只能被一个实例打开，所以所有浏览器操作串行化（一把全局锁）。任务池只有 2 个 worker，排队可接受；登录会长时间占锁（最长 5 分钟），属低频操作
- 登录态明文存在 `data/cookies.txt`，必须进 `.gitignore`，且日志只记站点与条数、不记内容（沿用红线 7）

**解除条件**：若将来要做多人/服务器部署，"本机弹窗"不再成立，需改为"用户在自己机器上跑一个登录小工具、把 cookies.txt 传给服务端"，或改用各家开放平台。届时 `services/browser.py` 的 `SITES` 与 cookie 格式可原样复用，换掉的只是"怎么拿到 cookie"。

**推翻成本**：中低。`browser.py` 是独立模块，`fetcher` 只依赖它的两个函数（`render` / `cookies_for`），`transcriber` 只依赖 `cookie_file()`。

## ADR-024 · 抖音不逆向签名，改用浏览器截获页面自己的请求

**决策**：抖音视频走一条独立通道——浏览器打开视频页，截获页面**自己发出**的 `aweme/detail` 响应拿媒体直链，再下 mp4、ffmpeg 抽音轨、whisper 识别。不实现 `a_bogus` 签名，也不试图让 yt-dlp 通过抖音。

**背景**：用户粘的是 App 里复制的聚合页链接 `https://www.douyin.com/jingxuan?modal_id=7704937199334116608`，任务报 `TRANSCRIBE_UNSUPPORTED`。拆开看是两个独立的坑（2026-11-06 实测）：

1. **链接形态**：`modal_id` 才是视频 id，聚合页本身 yt-dlp 不认（`Unsupported URL`）。改写成 `/video/<id>` 即解决——这层必须做，跟下面无关。
2. **签名**：改写后 yt-dlp 报 `Fresh cookies (not necessarily logged in) are needed`。它在请求 `aweme/v1/web/aweme/detail/` 时缺 `a_bogus`。实测四种姿势全部失败：
   - httpx 裸请求 → 200 + **空体**（0 字节）
   - 浏览器取 22 条匿名 cookie（含 `__ac_nonce`/`__ac_signature`/`ttwid`）→ 塞给 yt-dlp 的 cookiefile，仍然 `Fresh cookies`
   - 浏览器里 `fetch` 同一接口、不带签名 → 200 + 空体；**连试三次都是空体**
   - 同一页面**自己**发的同一个请求 → 200 + **140KB** 完整 JSON

第 4 条是全部结论：空体不是 cookie 不够，是缺 `a_bogus` 签名，而签名只存在于页面自己的 JS 里。所以"拿到签名"这件事不必自己做——让页面去发，我们听结果就行（`browser.capture_json`）。

**理由**：

- 不逆向签名：`a_bogus` 是混淆过的 JS，随版本变，跟一次修一次，性价比极低
- 复用已有底座：`browser.py` 的 persistent context / 串行锁 / 兜底通道都是现成的，只加了一个 40 行的 `capture_json`
- 抖音本来也没有字幕轨道，走不通"字幕优先"那条捷径，只能下载后识别
- 媒体直链（`douyinvod.com`）**下载不需要 cookie**，实测 45MB 一次成功；带上 UA/Referer 更稳

**代价**：

- 每个抖音视频多一次浏览器启动（约 2 秒）+ 一次整页渲染；比 yt-dlp 慢，但抖音本来就不通
- 浏览器锁会把抖音任务串行化（任务池 2 worker），两条抖音同时跑时后一条排队
- 依赖页面结构：`aweme_detail` 的字段名（`video.play_addr_h264`、`duration` 毫秒）一变就失效；
  解析逻辑集中在 `parse_douyin_detail` 这个纯函数里，坏了改一处，`verify_m2` 第 12 组用构造数据兜着

**解除条件**：若抖音官方开放平台提供视频详情接口，或 yt-dlp 上游实现了签名，直接换回 yt-dlp，删掉 `_transcribe_douyin` 即可。

**推翻成本**：低。`video_sites.canonicalize`（链接归一化）无论如何都要留着，与签名无关。

## ADR-025 · 繁简归一放在识别之后，不放解码里

**决策**：whisper 识别出来的文本，在**拼装 `[mm:ss]` 之前**按汉字段做一次繁→简归一（`services/zh_text.py`，依赖 `zhconv`）。标点、英文、数字、时间戳一律不动。字幕路径（`source=subtitle`）不参与，字幕是站点原文，照收。

**背景**：M2 收尾时我写过一句"whisper 中文默认输出繁体"，用户反问"为什么我自己导入都是简体"。查库后确认**那句话是错的**（2026-11-06 实测）：

| 来源 | 条目 | 繁字占比 |
|---|---|---|
| 网页 / 粘贴文本 | #4 #6 #11 #17 #30 #33 #35 | 全部 **0%**（正文照抄原文） |
| 视频 ASR | #19 #34 #39 #40 | **0% ~ 0.08%** |
| 视频 ASR | #36 #37 | 9.3% / 13.7% |

按时间切段看，#37 的繁体是 4%→18%→12%→19% 的**散落**，不是"越走越繁"的漂移；#39 整条干净。所以真实现象是：**繁简是逐段的概率选择，遇到背景音重、语速快、口音重的音频会偏到繁体**，不是模型的默认行为。

**为什么不用 `initial_prompt`**：同一份音频（#37，158 秒）只改解码参数做了三组对照：

| 参数 | 段数 | 平均段长 | 繁体占比 | 汉字数 |
|---|---|---|---|---|
| 现状（无提示词） | 88 | 1.5s | 14.3% | 911 |
| `initial_prompt="以下是普通话的句子。"` | 28 | 4.5s | 0% | 907 |
| 提示词 + `condition_on_previous_text=False` | 82 | 1.7s | 1.2% | 919 |

第一组提示词方案能把繁体清零，但**段数从 88 掉到 28**——`[mm:ss]` 是知识库的检索线索，粒度不能丢。加 `condition_on_previous_text=False` 能救回粒度，却仍要改全局解码行为（对长音频、对非中文的连带影响无法只靠一条样本论证）。转后处理则对解码零影响，文本与段落各自独立。

**为什么只转汉字段**：zhconv 整段调用会把中文引号 `「」` 规范成 `“”`（实测 #4、#35 各 4 / 12 处）。那是**样式**不是繁简，用户粘的原文不该被改。按 `[\u4e00-\u9fff]+` 切段后只把汉字送进 zhconv，标点原样返回。

**为什么不设"改动超过 x% 才转"的阈值**：在库里 11 条既有条目上实测，已是简体的一律 **0 改动**（含 `乾隆`、`著名`、`头发`、`台湾`、`只要` 这类易误判词，zhconv 词表处理正确），英文也 0 改动。既然对简体是恒等变换，阈值只会漏掉 #40 那种"3930 个汉字里只残留 3 个繁体"的长文。

**代价**：
- 多一个纯 Python 依赖 `zhconv`（约 1MB，无编译、无网络）
- 只改字形，**不修同音错字**：`搅屎棍狂潮` 被识别成 `脚使过光潮` 是声学错误，换字形救不回来
- 转换在逐段文本上做，跨段的词组（极少）不受词表规则影响
- 已在库的旧条目不会被追溯修改（`content_hash` 参与去重，事后改文本要连带改哈希，不做）

**解除条件**：若将来换用自带简繁约束的识别服务（如各家的中文专用 ASR），或 whisper 上游支持 `script=Hans`，删掉 `zh_text` 的调用即可，模块本身无副作用。

**推翻成本**：低。只有一个调用点（`transcriber._transcribe` 拼行处），`verify_m2` 第 13 组 12 项兜着。

## ADR-026 · LLM 按任务路由模型，`reasoning_effort` 按 provider 能力决定是否发送

**决策**：把「全局一套 `LLM_BASE_URL` / `LLM_MODEL` / `LLM_EFFORT`」改成「两套 provider + 四类任务各自可覆盖」。
解析顺序 `tasks[agent]` → `tasks['*']` → `providers[active]` 的默认值，落在 `services/prefs.py` 与
`services/llm.py:resolve()`。`reasoning_effort` **只在 `supports_effort=true` 时进请求体**，
为 `false` 时整条字段都不出现（不是发空串）。

**背景**：v0.1.0 的 `llm._payload()` 无条件塞 `reasoning_effort`。DeepSeek 收，但大多数第三方
OpenAI 兼容网关（硅基流动部分模型、Ollama、vLLM 默认配置）不认识这个字段，直接 400 ——
也就是「接非 DeepSeek 服务大概率一配就挂」，而用户在引导页填完 Key 看到的只是「LLM 调用失败」。
另一件事：整理想用便宜模型、问答想用强模型是真实需求，全局一套做不到。

**代价**：
- 配置从「三个 `.env` 键」变成「`.env` 存 Key + `settings.json` 存路由」，多一个文件要备份
- 每次调用多一次配置解析（读缓存 + mtime 判断，量级可忽略）
- 排障时「为什么走这个模型」需要看 `llm_call_log.model` 而不是 `.env`（已按实际使用的模型写日志）
- 配置写坏会同时影响四类任务；靠「缺省即合并 + 损坏备份」兜底

**解除条件**：若将来所有目标服务都支持 `reasoning_effort` 且用户只需要一个模型，
把 `tasks.*` 全部清空并让 `resolve()` 恒返回 `providers[active]` 即可，`settings.json` 不必删。

**推翻成本**：中。涉及 `llm.py` 的三处（payload / headers / 写日志）、`prefs.py`、设置窗口的模型 tab；
`verify_m6.py` 与 `verify_m1`~`verify_m5` 的模型断言会同时报警。

## ADR-027 · 重组件（向量 / 语音 / 浏览器）按需下载，不进主安装包

**决策**：安装包只带「不装就跑不起来」的东西（Python 运行时、业务依赖、ffmpeg）；
`torch` + `sentence-transformers`（≈367 MB）、`faster-whisper` 语音栈、`playwright` 浏览器内核
拆成三个可选组件，装到 `<数据目录>/components/<id>/`，由设置窗口的「下载」tab 安装 / 卸载。

**背景**：v0.1.0 安装包 426 MB、解包 965 MB，用户第一反应是「是不是下错了」。
而这三个组件的真实使用率极不对称：向量组件几乎人人要用（影响检索质量），
语音只在「视频没有字幕」时用，浏览器只在知乎这类反爬站点用。让所有人替少数场景付 400 MB 不合理。

**代价**：
- **每条功能都必须有降级路径**：缺向量 → 纯全文检索并明说降级；缺语音 → 转录报错但不影响入库；
  缺浏览器 → 采集报 `FETCH_BROWSER_UNAVAILABLE`。降级路径写不对就是「装完像坏了」
- 下载要处理网络中断、sha256 校验、版本漂移（`manifest.min_app_version`），比随包发布复杂得多
- 首次使用某个功能会多一次几百 MB 的等待，必须给明确进度与可取消
- 卸载组件不能碰 `data.db`，删错目录就是用户数据事故

**解除条件**：若将来三个组件体积降到合计 100 MB 以内、或全部改为云端调用，直接塞回主包即可，
`ComponentClient` 的接口保持「拿得到一个可用实现」的语义，换成进程内实现不影响调用方。

**推翻成本**：高。这是 M8 的主体，涉及打包 spec、组件协议、下载中心、更新器四处；
`verify_m1`~`verify_m7` 都要在「无组件」状态下重跑一遍才有意义。
