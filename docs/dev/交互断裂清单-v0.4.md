## 1. 施工顺序

按依赖与风险排，一个人一次只开一批；每批独立可交付、可回滚。

| 批 | 内容 | 为什么这个位置 | 完成条件 |
|---|---|---|---|
| 批 1 | **H1** | 一行补接口 + 一句兜底，先止血（OCR 失败现在只有删了重传一条路） | 缺组件→装好→重读 能成 |
| 批 2 | **H2** | 独立改动，只碰列表加载 | 库 >50 条时能翻到底 |
| 批 3 | **H3** | 改动最大、收益最高，单独一批；碰详情生命周期，最怕夹带别的改动 | 刷新不再丢草稿、不再回第 1 页 |
| 批 4 | **H4** | 与批 2/3 都碰 `Knowledge.vue`，放在 H3 之后避免反复解冲突 | 20 条里失败 1 条能看出来、能重试 |
| 批 5 | **H5** | 需要拍板是否动后端（见 §8-③）；纯前端部分先做 | 结果页能把「待判」判成对/错 |
| 批 6 | **M1 + M2** | 都是「入口没接住数字 / 提示出现太晚」，文案与 query 打通 | 点「待整理 12」直接落在筛好的列表 |
| 批 7 | **M3 + M4** | M3 是文案 + 删一行调用；M4 是补两个出口 | 「稍后再说」不再偷偷下载；复习行能看原文 |
| 批 8 | **L1–L4** | 收口组，互不依赖，可拆可合 | 四条低优先全部勾掉 |

**不建议合并的**：H3 与 H4 虽然都在 `Knowledge.vue`，但一个是详情生命周期、一个是列表批量语义，混在一个提交里回滚会互相拖累。

## 2. 高优先级施工单

### H1 ★ 「重读」调用了一个不存在的接口

**场景**：扫描件读到一半断了（长文档常态）；用户刚装完识别组件从设置回来点「重读」；部分页没认出来想补跑。

**位置**
- `frontend/src/api/client.js:287-289` 一带（`getItem` / `patchItem` 之间）——**没有** `reocr`
- `frontend/src/components/ingest/FileIngestCard.vue:230-247`（`retry()`）
- 后端实为 `POST /api/knowledge/{item_id}/ocr`（`backend/app/routers/knowledge.py:401`，202 + `task_id`，`body` 可省）

**症状**：`api.reocr` 是 `undefined`，调用即 `TypeError`，被同一段 `catch` 接住 →
`friendlyMessage(TypeError)` 走末行 `return err.message` → 卡片上出现 **`api.reocr is not a function`**。
用户看到的是 JS 错误原文，且卡片停在「没读成」，与任务中心的真实状态不一致。

**为什么断了**：接口在客户端侧漏了。三条恢复路径（缺组件→装好→重读 / 读断→重读 / 部分页→重读）
共用这一个调用，所以三条一起断，用户唯一能想到的下一步是「删了重传」——而原件落盘后重传要重跑一遍识别。

**改法**
- [ ] `client.js` 在 `patchItem` 附近补：`reocr: (id) => post(\`/api/knowledge/${id}/ocr\`)`
      （不传 body 是合法的：`request()` 对 `body === undefined` 既不设 Content-Type 也不 stringify；
      后端签名是 `body: OcrBody | None = None`）
- [ ] `retry()` 的 `catch` 分支加一层：`err instanceof ApiError` 才用 `friendlyMessage`，
      否则统一成「重读没排上。去任务中心看这条的进度，或者稍后再点一次重读」
- [ ] 可选：把 `retry()` 里的 `OCR_RUNNING` 特判保留（现在是对的，别顺手删）

**验收**
- [ ] 装上识别组件后点「重读」→ 卡片回到「正在识别 N/M 页」，任务中心出现新任务
- [ ] 在识别进行中再点一次 → 不报错，继续看进度（`OCR_RUNNING` 分支）
- [ ] 断网后点「重读」 → 出现人话提示，不出现 `is not a function`

**回归**：`hasItem` 为 false 时 `retry()` 仍走 `start()`（首次上传失败的重试），这条别改坏。

### H2 ★ 知识库列表只取前 50 条，没有翻页，却显示全量条数

**场景**：库里超过 50 条（导入一学期课件就会到），用户在「全部内容」里找第 51 条之后的内容。

**位置**
- `frontend/src/views/Knowledge.vue:18`（`PAGE_SIZE = 50`）、`87`（`page_size` 恒 50，从不传 `page`）
- `frontend/src/components/ItemList.vue:101`（`{{ total }} 条`）
- 后端 `GET /api/knowledge` 支持 `page`，`page_size ≤ 100`

**症状**：左栏写「全部内容 218」，列表滚到底就停了。既没有「加载更多」，也没有一句「只显示前 50 条」。
用户要么以为没导进来，要么以为丢了 168 条——**这两件事他都无法在界面上证伪**。
分类/标签/工作区筛选能绕开，但「全部」这一层永远短一截。

**为什么断了**：分页参数只在后端存在，前端从 T? 起就固定单页，UI 却按「全量」措辞。

**改法**（2026-11-15 决定：只做条数说明，不做「加载更多」）
- [ ] `ItemList.vue:101`：`total > items.length` 时在计数后补一句
      `仅显示前 {{ items.length }} 条，用关键词或分类缩小范围`，`total ≤ items.length` 时不出现
- [ ] 句子里必须有「前 N / 共 M」两个数，不能只写「仅显示部分」；N 取 `items.length`（不是写死 50）
- [ ] 不新增 `page` 状态、不改 `loadList()` 的请求参数——列表行为与现在完全一致

**验收**
- [ ] 造 120 条 → 列表 50 条，计数旁出现「仅显示前 50 条，用关键词或分类缩小范围」
- [ ] 库里 30 条 → 这句话不出现（不会在正常的库上制造焦虑）
- [ ] 文案过 §6 禁止词（不许出现「条目」）

**已知代价（明确接受）**：第 51 条之后的内容，界面里**没有任何路径**能翻到，只能靠搜索/筛选/工作区绕。
所以这条只是把「静默短一截」改成「说清楚短一截」，不提供出口。要真出口时再回到本节加 `page`，
`GET /api/knowledge` 已支持，前端补 25 行即可。

### H3 任何一次后台刷新都会把详情区拆成骨架屏

**场景**
1. 用户在「整理笔记」里改了半页，同时另一条内容还在整理（`scheduleIfBusy` 每 2.5 s 触发一次 `refreshAll`），
   或者刚从批量移入回来。
2. 用户在原文页签读到第 40 页，此时采集了一条新内容（`refreshTick`）或点了「重新整理」。

**位置**
- `frontend/src/views/Knowledge.vue:152-156`（每次刷新都 `await loadDetail`）、`109-124`（`detailLoading = true`）
- `frontend/src/components/ItemDetail.vue:191-193`（`v-if="loading"` 用骨架屏**整块替换** `<template v-else>`）
- `frontend/src/components/NoteEditor.vue:95-100`（卸载即 `setEditorDirty(false)`）
- `frontend/src/components/RawPane.vue:54-57`（PDF/DOCX/PPTX/图片 全部 `:key="…-${itemId}"`，重挂即重置）

**症状**：用户什么都没做，系统自己刷新，然后：
- 笔记草稿没了，连「已修改 •」标记也一起消失（所以之后切内容时那句「当前笔记还没保存」也不会再弹，
  用户彻底无从知道刚才的编辑去哪了）；
- PDF 回到第 1 页，阅读位置归零；
- 整个详情区闪一次骨架屏，已展开的折叠区/滚动位置全丢。

**为什么断了**：`loadDetail` 只有「有/无」两种表现，没有「已有内容、正在后台更新」这一态；
`editorDirty` 守卫只写在 `selectItem` 里，管不到「同一条内容被刷新」。

**改法**（三层，按顺序做，做完前两层就能止血）
- [ ] **① 刷新不清屏**：`loadDetail(itemId, { soft })`。当 `detail.value?.id === itemId` 时
      不置 `detailLoading`，改为置一个 `detailRefreshing`，模板上用顶部细进度条或角标表达；
      只有「从无到有」或「切换 id」才走骨架屏。
- [ ] **② 草稿不被卸载吃掉**：`NoteEditor` 卸载前把未保存文本按 `itemId` 写入 `sessionStorage`
      （key 形如 `cairn.note.draft.<id>`），`onMounted` 时若有草稿则回填并把 `dirty` 置真、显示「已恢复未保存的改动」；
      保存成功或用户主动丢弃时清掉该 key。
- [ ] **③ 页位按内容记住**：`PdfView` / `DocxView` 等把 `scrollTop`（或页号）提到 `ItemDetail` 层，
      以 `itemId` 为键存放，重挂后 `restore`；`itemId` 变了才丢弃旧值。
- [ ] `ItemDetail.vue` 的 `watch(() => props.item?.id)`（`tab.value = 'summary'`）保持不动 ——
      **切换内容归位到摘要是有意设计**，本项只修「同一条被刷新」。

**验收**
- [ ] 改 3 行笔记不动 → 等 10 s（另一条在整理，触发轮询）→ 文字还在，「已修改」还在
- [ ] 强制刷新页面（F5）后回到该条 → 草稿回来并明确标「已恢复未保存的改动」
- [ ] PDF 读到第 40 页 → 点「重新整理」→ 仍停在第 40 页，不闪骨架屏
- [ ] 切换 A→B→A：页签回到「摘要」，且 B 的草稿不串到 A（key 按 itemId）

**风险**：`sessionStorage` 是本次唯一新增的本地存储（2026-11-15 已定：就用它，能扛 F5）。
清理时机必须三处都写，否则会在库里留一堆看不见的残稿：
保存成功 / 用户主动丢弃 / 内容被删（`GET /api/knowledge/{id}` 返回 404 时顺手删 key）。

### H4 批量移入：没有进度、没有失败明细、点完立刻清空勾选

**场景**：勾选 20 条 → 选工作区 → 点「移到」。其中一条正在整理（`ITEM_BUSY`），或目标工作区刚被删。

**位置**
- `frontend/src/views/Knowledge.vue:238-250`（`onMoveItems`：`Promise.all` 逐条 PATCH，无 loading、无汇总）
- `frontend/src/components/ItemList.vue:52-56`（`onBulkMove`：`emit` 同帧 `picked.value = []`）
- `frontend/src/components/list/BulkMoveBar.vue:20-23,33`（`submit` 与按钮，均无 disabled）

**症状**：请求还在飞，勾选已经消失，「移到」也没变灰——用户既看不到「正在移 20 条」，
也无法判断成没成；一条失败时只得到一条通用 toast，**成功 19 / 失败 1 的事实被吞掉**，
而且勾选回不来了，没法针对失败项重试。

**为什么断了**：`emit` 是同步的，父组件的异步结果没有任何回传通道；`Promise.all` 遇错即弃，
丢了「哪几条成了」的信息。

**改法**（2026-11-15 已定：只做「按钮禁用 + 移到中 3/20」，不做逐条行内反馈）
- [ ] 父组件 `onMoveItems`：`Promise.allSettled` 逐条 PATCH，按结果分成 `ok[]` / `failed[{id, err}]`
- [ ] 汇总 toast：全成 → 「已移入 N 条」；有失败 → 「成功 19 条，1 条没移成：〈标题〉」
      （标题从 `items` 里按 id 取，取不到就说「1 条没移成，已留在勾选里」）
- [ ] 失败项 id 回传给 `ItemList` 并**保留在 `picked` 里**；成功项从 `picked` 移除
- [ ] `BulkMoveBar` 加 `:busy` prop：`submit` 期间「移到」`disabled` 且文案变 `移到中…`；
      父组件维护 `moving = { done, total }`，按钮旁显示 `移到中 3/20`
- [ ] `ItemList.onBulkMove` 不再同帧清空：父组件下发 `picked`（`v-model:picked`），
      由父组件在结果回来后把失败项写回、成功项剔除

**验收**
- [ ] 20 条里故意挑一条正在整理的 → 完成后提示「成功 19 条，1 条没移成」，那 1 条仍勾着
- [ ] 移入过程中按钮不可重复点，能看到 `移到中 3/20`
- [ ] 全部成功后勾选清空、列表刷新、工作区计数同步变化

**连带（同类问题，可同批做或单独立项）**
- [ ] `ingest/FolderImport.vue:62-86`：`importRun` 同步跑完才回，无进度、无取消。
      至少补「正在导第 3/12 个」+「停止」（在两个请求之间停，不发下一个）

**权衡**：不为批量加后端端点（20–50 条规模不值），但也**不要**改成 `for await` 串行 20 次而不给进度——
串行且无反馈比并发更让人以为卡死。

### H5 ★ 「待人工判断」是个死状态：看得见，全站无处可改

**场景**：交卷时模型超时（`LLM_TIMEOUT` 的文案亲口承诺「简答会记成「待人工判断」，不会判错」），
或批改返回 null。

**位置**
- `frontend/src/components/QuizRunner.vue:259-262`（结果页只有一行计数）、`276`（「待判」标记）
- `frontend/src/api/client.js:381-382`（`reportReview`，注释写着「只用于人工裁定待判题」，**零调用** ★）
- `backend/app/routers/review.py:63-78`（`POST /api/review/{question_id}/result`，body 字段是 **`correct: bool`**）
- `backend/app/db/repo/review.py:52-78`（`apply(None)` 直接 return，**不建队列行**）

**症状**：这条题不进复习队列、不进错题本（错题本只收最近一次 `is_correct = false`），
也没有任何界面能把它判成对/错。用户看到「有 2 题待人工判断」，然后既找不到这 2 题在哪，
也没法判——唯一出路是把整组重做一遍。**承诺里的「人工」并不存在**，这是最伤信任的一类反馈。

**为什么断了**：裁定端点做了一半（后端有、客户端有、界面没有），而且因为 `apply(None)` 不建队列行，
这批题在「复习队列」里天然不可见——**只补按钮不够，还得有找回它们的入口**。

**改法（分两层，②已批准动后端）**
- [ ] **① 结果页就地裁定**（纯前端，必做）
  - `result.items` 中 `is_correct === null` 的行：把「待判」旁加「算我对」「算我错」两个小按钮
  - 点击 → `api.reportReview(item.question_id, { correct: true|false })`（**字段名是 `correct`，
    不是 `is_correct`**；`client.js` 那行注释也要一并改，否则下一个人照着注释又写错）
  - 成功后该行就地变 ✓/✗，`pendingManual` 计数减一，并 toast「已记为答对／答错，下次复习按这个排期」
  - 失败（`QUESTION_NOT_FOUND` 等）→ 按钮恢复可点 + 人话提示
  - 后端返回 `scheduled: false, reason: "not_tracked"`（答对且从没错过）不是错误：
    标 ✓ 并说明「这题不用复习」
- [ ] **② 离开后还能找回来**（2026-11-15 已定：加查询，不做 localStorage 临时方案）
  - 新端点 `GET /api/review/pending`（`backend/app/routers/review.py`）：取**最近一次作答**
    `is_correct IS NULL` 的题，返回与 `/review/due` 同形的字段 + `source_title`；
    同时给一个 `total`
  - ⚠ 实测补充（2026-11-15）：`POST /review/{id}/result` **原本不写作答记录**，
    只写 `review_item`。于是判完之后「最近一次作答」还是那条 NULL，待判列表会把题捞回来
    （`verify_m4` 的「裁定之后从待判列表消失」就是这么红的）。裁定必须顺手
    `save_attempt(..., is_correct=1/0, feedback='人工裁定')`，沿用上一次的作答内容。
