
然后按顺序读：本文件 §0 → 当前任务的卡片 → 需求文档对应层 → 要改的那个文件（**必须读，不许凭空改**）。

### 0.3 单个任务的标准循环

```
① 读卡 + 读要改的文件（全部读完再动手）
② 只改这张卡允许改的文件
③ 跑卡里的「自检」，全过
④ 跑相关 verify（卡里写明跑哪几个）
⑤ 更新 §9 台账 + HANDOFF（若有未结项）
⑥ commit（显式路径，不用 -A）→ push（见 §1.3）
```

一次 commit 只对应一张卡。**不要把两张卡塞进一个 commit**——回滚时会一起回滚。

### 0.4 必须停下来问的情况（不许自行决定）

| 情况 | 为什么 |
|---|---|
| 任何 verify 出现 FAIL | 项目约定：FAIL 只报不修，先给方案 |
| 体积超过卡里写的上限 | 体积是承诺，破承诺要人来点头 |
| 需要动本卡「不许动」列表里的文件 | 说明设计漏了，先补设计 |
| 实测数字与文档写的差 >20% | 文档里的数字都要能被复现，差太多说明前提变了 |
| 想新增依赖 | 许可、体积、打包三件事都要重新评估 |
| 发现同一功能有两种合理做法 | 选一个写进 ADR，不要两个都留 |

### 0.5 绝对不许做的事

- 不许改 `00-总纲.md` §2 的红线（离线优先、数据在本地、不做多用户、单文件 ≤300 行等）。
- 不许引入 AGPL 依赖（PyMuPDF 就是典型，用 pypdfium2）。
- 不许在界面上出现 `verify_m7.py` 的 `FORBIDDEN` 词。**特别注意「结构化」是禁止词**，界面写「整理成题目」。
- 不许 `git add -A`（工作区可能有另一路在建代码），一律显式路径。
- 不许为了过验收放宽断言（例如把「双栏不错行」改成「行数对得上」）。
- 不许把识别结果与页图分开存——它们必须同页配对，这是「认错也看得出来」的唯一保障。

### T9.3 上传与落盘

**目的**：文件进来先留住原件，再去读字。原件是「认错了能回看」的唯一凭据。

**依赖**：T9.2 · **触碰文件**

| 动作 | 路径 |
|---|---|
| 新增 | `backend/app/services/files.py`（落盘、sha256、删除、占用统计） |
| 新增 | `backend/app/routers/files.py` |
| 改 | `backend/app/main.py`（挂 router） |
| 改 | `backend/app/routers/knowledge.py`（`PatchBody` 加 `workspace_id`；详情形状加 `file`/`kind`/`workspace_id`） |

**步骤**

1. 流式接收：边写临时文件边算 sha256，**不要 `await file.read()` 一把梭**（200 MB 会吃掉内存）。
2. 先看大小：>200 MB 直接拒绝（`FILE_TOO_LARGE`，413），不落盘。
3. 扩展名白名单：`docx pdf pptx xlsx txt md png jpg jpeg webp`。`.doc/.wps` 单独给 `FILE_UNSUPPORTED` 并提示「另存为 .docx」。
4. **去重顺序**（这里有个真坑，见下）：先查 `item_file.sha256`，命中就直接返回已有内容；未命中才建内容。
5. 落盘路径：`<data_dir>/files/<item_id>/<sha256 前 8 位>.<ext>`，`stored_path` 存**相对数据目录**的路径。
6. 建内容时 `source_type='file'`（这个死枚举终于有写入口了），`kind` 按扩展名推：图片→`image`，其余→`material`（试卷要用户在复核页确认后才是 `exam`）。
7. 建完就把状态置成「等着读字」：PDF / 图片 `ocr_status='pending'`，其余 `none`。**入队不在这张卡**——
   任务处理器要到 T9.6（识别）/ T9.7（抽取）才注册，这里 `dispatch.submit` 只会拿到 `KeyError`；
   这两张卡落地时在本函数末尾接上入队即可。接口绝不等于识别完成，立刻返回。

**坑：`content_hash` 会撞**

`create_item` 用 `sha256(raw_content)` 去重。文件类内容在抽取前 `raw_content` 是空的，**所有空内容 hash 相同**，第二个文件会被当成重复，直接返回第一个。

两条路，选后者：

- ❌ 改 `create_item` 的 hash 算法 —— 会动到网页采集的去重语义。
- ✅ 建内容时先写占位正文（`f"[文件] {original_name}"`），抽取完成后用 `replace_raw_content()` 覆盖（它会同步更新 hash）。文件级去重靠 `item_file.sha256`，不靠 `content_hash`。

**坑：同名不同内容也会撞占位正文**（2026-11-12 实测）

两份都叫 `试卷.pdf`、内容不同、且都还没抽取 → 占位正文一模一样，`content_hash` 相同，第二份会被
`create_item` 判成重复并**挂到第一条内容上**（盘上两份原件、详情却只认一份）。解法是撞了就加 sha 前缀
重试（`[文件] 试卷.pdf（a1b2c3d4）`），只在这一条罕见路径上改变正文，正常路径仍是干净的原名。

**坑：中文文件名**

存储一律用 id + sha 命名，原名只进数据库。所有路径操作走 `Path`，不拼字符串。Windows 下 `cv2.imread` 读中文路径会返回 None，读图一律 `cv2.imdecode(np.frombuffer(Path(p).read_bytes(), np.uint8), ...)`。

**渲染（`pdf_pages.py`）**

```python
import pypdfium2 as pdfium
pdf = pdfium.PdfDocument(str(path))
w_pt, h_pt = pdf[0].get_size()
scale = min(1600 / max(w_pt, h_pt), 300 / 72)   # 长边 ≤1600 px，且不放大超过 300dpi

```

**逐页流式**：渲染一页 → 识别一页 → 落库一页 → 释放。绝不把 300 页都转成图放内存。

**双栏判列（`ocr_layout.py`，这张卡的验收核心）**

引擎只给行框，**不给阅读顺序**；实测双栏输出是「左1 → 右1 → 左2 → 右2」交错。算法：

```python
def order_lines(lines, page_width) -> list[str]:
    if not lines: return []
    mid = page_width / 2
    left  = [l for l in lines if (l.box[0][0] + l.box[1][0]) / 2 < mid]
    right = [l for l in lines if (l.box[0][0] + l.box[1][0]) / 2 >= mid]
    # 判双栏：两侧各 ≥3 行，且左列最大 x1 <= 右列最小 x0（真的不重叠）
    if len(left) >= 3 and len(right) >= 3:
        if max(l.box[1][0] for l in left) <= min(l.box[0][0] for l in right) + 8:
            return [_join(sorted(left, key=lambda l: l.box[0][1])),
                    _join(sorted(right, key=lambda l: l.box[0][1]))]
    return _join(_cluster_rows(lines))       # 单栏：y 聚类成行，行内按 x
```

`_cluster_rows`：按 y 中心排序，相邻行 y 差 < 0.6 × 中位行高 视为同一行，行内按 x0 排序。

**验收必须遍历四组 `samples/*/twocol.pdf`**，逐组断言输出里「左1」后面跟着「左2」，而不是「右1」；只跑一组不算过。

**并发：先测再决定，不许直接上多进程**

`component_proc` 是**每组件一个进程一把锁**，后端并发调只会排队。所以：

1. 先用任务管理器看单页识别时 `cairn-ocr.exe` 的 CPU 占用。
2. **若 >250%**（onnxruntime 已吃满多核）→ 并发无收益，**不做进程池**，30 页约 84 秒，把需求文档 §12 的性能线改成「≤90 秒」并告知用户。
3. **若 <150%**（基本单核）→ 再做进程池（`component_proc` 加 `pool_size`，ocr 配 2–3 个进程轮询），可到 40–50 秒。
4. 两种都要**先改文档再改代码**，不许代码偷偷跑超。

**断点续跑**：开工前查 `item_page` 已有页号，跳过；重识别只针对失败页或用户点名的页。

**进度**：`item_file.ocr_status` + 已识别页数 / 总页数。前端每 1.5 秒轮询一次，别用 SSE（这里不需要逐 token）。

**坑**

- `pypdfium2` 的 `render(scale=)` 是相对 72dpi 的倍数，别把 150 直接当 scale 传（会得到 150 倍图）。
- 单页识别过慢时先看是不是渲染成了 300dpi 的图（文件大小会明显变大）。
- 页图统一 JPEG q85；用 PNG 会让 30 页占 100 MB+。
- 「识别出空页」不是失败：`source` 留 `ocr`、`text` 为空、`avg_conf=0`，前端标「这页没认出文字」。整份有 ≥1 页为空时 `ocr_status='partial'`。

**自检**

**完成判据**

- [ ] 双栏样本不错行（逐行人工比对 5 页，不接受"看起来对"）

## 6. 横切约定（每张卡都适用）

### 6.1 后台任务的写法

统一走 `services/tasks.py` 的 `submit(type, fn, input, pass_task_id=...)`：

```python
tasks.submit("ocr_pages", run_ocr, {"item_id": item_id, "file_id": file_id}, pass_task_id=True)
```

- `fn(input, task_id)` 里用 `repo.update_task(progress=pct)` 报进度。
- 入队**必须在事务提交之后**（否则任务读不到未提交的行）。
- 长任务要能被打断：每页检查一次「内容是否已被删除」，删了就停。
- 启动时 `recover_stale_tasks()` 会把残留 running 标 failed，所以失败是安全的、可重试的。

新增任务类型：`ocr_pages` / `extract_file` / `import_dir`。

### 6.2 错误码表

| code | HTTP | 触发 | 界面文案（禁止词已避开） |
|---|---|---|---|
| `FILE_TOO_LARGE` | 413 | >200 MB | 这个文件 235 MB，超过 200 MB 上限，先压缩或拆分再试 |
| `FILE_UNSUPPORTED` | 415 | 扩展名不在白名单 | 暂不支持 .doc，请另存为 .docx 再上传 |
| `FILE_EMPTY` | 422 | 零字节文件 | 这个文件是空的，换个文件再试（2026-11-12 实测：不拦就会变成「上传成功但读不出字」） |
| `WORKSPACE_NOT_FOUND` | 404 | 指定了不存在的工作区（上传或 PATCH） | 工作区不存在，可能已经被删了 |
| `OCR_MISSING` | 409 | 识别组件未装 | 读 PDF 与图片需要先装识别组件（附「去设置」） |
| `OCR_FAILED` | 502 | 组件崩溃/超时 | 识别组件出错了，可以重试这一页 |

| `POST /api/files` 报 500 且栈里是 `multipart` 相关 | FastAPI 解析 multipart 要 `python-multipart`，不在默认依赖里 | 2026-11-12 已加入 `pyproject.toml`（纯 Python，约 40 KB） |

### 8.3 识别类（本项目特有，必看）

| 现象 | 原因 | 处理 |
|---|---|---|
| **双栏输出左右交错** | 引擎只给行框，按 y 排就是交错（实测必现） | `ocr_layout.order_lines` 判列（T9.6） |
| `cv2.imread` 返回 None | Windows 中文路径 | `Path.read_bytes()` + `cv2.imdecode` |
| 组件报 `DLL load failed` | opencv/onnxruntime 的 DLL 没进包 | `datas` 补；先打最小包验证（§2.2） |
| 识别结果全是方块/乱码 | 用了 PDF 文本层而不是识别 | 检查是否走了 `extract` 分支；PDF 只走 `ocr` |
| 30 页跑了 5 分钟 | 渲染成了 300dpi | 长边钳到 1600 px |
| 内存涨到 1 GB+ | 一次把 300 页都渲染了 | 单页流式：渲染→识别→落库→释放 |
| 认错但读起来通顺 | 模型"顺手润色" | 文字与页图并排；diff 编辑距离守卫 |
