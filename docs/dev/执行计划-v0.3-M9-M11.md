### 0.1 人只需看的三行

### 0.2 开场三件事（每次会话，不跳）

```bash
cd "C:/Users/cwqjk/Desktop/知识库agent开发"
python tools/doc_check.py                    # 文档一致性，必须 0 FAIL
"C:/Program Files/Git/cmd/git.exe" status --short   # 工作区必须干净；有别人的改动就别动

```

然后按顺序读：本文件 §0 → 当前任务的卡片 → 需求文档对应层 → 要改的那个文件（**必须读，不许凭空改**）。

### 0.3 单个任务的标准循环

```
① 读卡 + 读要改的文件（全部读完再动手）
② 只改这张卡允许改的文件
③ 跑卡里的「自检」，全过
④ 跑相关 verify（卡里写明跑哪几个）
⑤ 更新 §9 台账 + HANDOFF（若有未结项）
⑥ commit（显式路径，不用 -A）→ push（见 §1.3）
```

一次 commit 只对应一张卡。**不要把两张卡塞进一个 commit**——回滚时会一起回滚。

### 0.4 必须停下来问的情况（不许自行决定）

| 情况 | 为什么 |
|---|---|
| 任何 verify 出现 FAIL | 项目约定：FAIL 只报不修，先给方案 |
| 体积超过卡里写的上限 | 体积是承诺，破承诺要人来点头 |
| 需要动本卡「不许动」列表里的文件 | 说明设计漏了，先补设计 |
| 实测数字与文档写的差 >20% | 文档里的数字都要能被复现，差太多说明前提变了 |
| 想新增依赖 | 许可、体积、打包三件事都要重新评估 |
| 发现同一功能有两种合理做法 | 选一个写进 ADR，不要两个都留 |

### 0.5 绝对不许做的事

- 不许改 `00-总纲.md` §2 的红线（离线优先、数据在本地、不做多用户、单文件 ≤300 行等）。
- 不许引入 AGPL 依赖（PyMuPDF 就是典型，用 pypdfium2）。
- 不许在界面上出现 `verify_m7.py` 的 `FORBIDDEN` 词。**特别注意「结构化」是禁止词**，界面写「整理成题目」。
- 不许 `git add -A`（工作区可能有另一路在建代码），一律显式路径。
- 不许为了过验收放宽断言（例如把「双栏不错行」改成「行数对得上」）。
- 不许把识别结果与页图分开存——它们必须同页配对，这是「认错也看得出来」的唯一保障。

### T9.3 上传与落盘

**目的**：文件进来先留住原件，再去读字。原件是「认错了能回看」的唯一凭据。

**依赖**：T9.2 · **触碰文件**

| 动作 | 路径 |
|---|---|
| 新增 | `backend/app/services/files.py`（落盘、sha256、删除、占用统计） |
| 新增 | `backend/app/routers/files.py` |
| 改 | `backend/app/main.py`（挂 router） |
| 改 | `backend/app/routers/knowledge.py`（`PatchBody` 加 `workspace_id`；详情形状加 `file`/`kind`/`workspace_id`） |

**步骤**

1. 流式接收：边写临时文件边算 sha256，**不要 `await file.read()` 一把梭**（200 MB 会吃掉内存）。
2. 先看大小：>200 MB 直接拒绝（`FILE_TOO_LARGE`，413），不落盘。
3. 扩展名白名单：`docx pdf pptx xlsx txt md png jpg jpeg webp`。`.doc/.wps` 单独给 `FILE_UNSUPPORTED` 并提示「另存为 .docx」。
4. **去重顺序**（这里有个真坑，见下）：先查 `item_file.sha256`，命中就直接返回已有内容；未命中才建内容。
5. 落盘路径：`<data_dir>/files/<item_id>/<sha256 前 8 位>.<ext>`，`stored_path` 存**相对数据目录**的路径。
6. 建内容时 `source_type='file'`（这个死枚举终于有写入口了），`kind` 按扩展名推：图片→`image`，其余→`material`（试卷要用户在复核页确认后才是 `exam`）。
7. 建完就把状态置成「等着读字」：`ocr_status='pending'`。**入队不在这张卡**——
   任务处理器要到 T9.6（识别）/ T9.7（抽取）才注册，这里 `dispatch.submit` 只会拿到 `KeyError`；
   这两张卡落地时在本函数末尾接上入队即可。接口绝不等于识别完成，立刻返回。
   （T9.7 落地后修正：原来写的是「PDF / 图片 pending，其余 none」，那时抽取还没实现；
   现在 docx / pptx / xlsx / txt 也走后台抽取，一律 `pending`，只有未知扩展名才留 `none`。）

**坑：`content_hash` 会撞**

`create_item` 用 `sha256(raw_content)` 去重。文件类内容在抽取前 `raw_content` 是空的，**所有空内容 hash 相同**，第二个文件会被当成重复，直接返回第一个。

两条路，选后者：

- ❌ 改 `create_item` 的 hash 算法 —— 会动到网页采集的去重语义。
- ✅ 建内容时先写占位正文（`f"[文件] {original_name}"`），抽取完成后用 `replace_raw_content()` 覆盖（它会同步更新 hash）。文件级去重靠 `item_file.sha256`，不靠 `content_hash`。

**坑：同名不同内容也会撞占位正文**（2026-11-12 实测）

两份都叫 `试卷.pdf`、内容不同、且都还没抽取 → 占位正文一模一样，`content_hash` 相同，第二份会被
`create_item` 判成重复并**挂到第一条内容上**（盘上两份原件、详情却只认一份）。解法是撞了就加 sha 前缀
重试（`[文件] 试卷.pdf（a1b2c3d4）`），只在这一条罕见路径上改变正文，正常路径仍是干净的原名。

**坑：中文文件名**

存储一律用 id + sha 命名，原名只进数据库。所有路径操作走 `Path`，不拼字符串。Windows 下 `cv2.imread` 读中文路径会返回 None，读图一律 `cv2.imdecode(np.frombuffer(Path(p).read_bytes(), np.uint8), ...)`。

**为什么传路径不传 base64**：页图已经在盘上，1.5 MB × 30 页的 base64 编解码纯属浪费；组件与后端同机同用户，直接读文件。中文路径由组件用 `Path.read_bytes()` + `cv2.imdecode` 处理（`cv2.imread` 在 Windows 上读不了中文路径）。

**步骤**

1. 引擎按实测的那套写，**不要改调用形式**：

```python
from rapidocr import RapidOCR
eng = RapidOCR()                 # 模型随包自带，实测默认就是 PP-OCRv6 det/rec small
res = eng(str(image_path))       # 或传 ndarray
res.txts, res.scores, res.boxes  # 三个平行数组
```

2. 显式禁网：把模型路径指到包内（`Path(rapidocr.__file__).parent / "models"`，冻结后是 `_internal/rapidocr/models`）。**rapidocr 没有关闭下载的开关**，而且它每次加载模型都会调 `DownloadFile.run`：文件在且 sha256 匹配才跳过，否则直接 `requests.get`。所以做法是**包一层**——保留它自己的 `_should_skip_download`（齐全时照常返回），只在"真要下载"那一刻抛 `OCR_FAILED`：
   ```python
   orig = dl.DownloadFile.run
   def _guarded(cls, params):
       cls.verbose = bool(getattr(params, "verbose", False))   # 原 run 的第一行，跳过判断要用
       save = Path(str(params.save_path))
       if cls._should_skip_download(save, params.sha256, logger): return
       raise OpError("OCR_FAILED", "包内没有这个文件，组件包不完整，不做联网下载")
   dl.DownloadFile.run = classmethod(_guarded)
   ```
3. `--selftest`：内置一张 320×80 的 PNG（base64 常量，白底黑字写「本地识别」），断言出字包含「识别」两个字。**必须是真起子进程**（`_protocol.selftest` 已这样做），不能直接调函数。
4. 打包：`COMPONENTS["ocr"]` 的 `keep` 含 `rapidocr`、`onnxruntime`、`cv2`（`numpy`/`PIL` 不在 `HEAVY` 里，本来就不会被排）；`datas` 要收 `rapidocr`（模型在里面），外加 `collect_submodules('cv2')`。`HEAVY` **只加不删**：新增 `rapidocr`、`cv2` 是为了让 embed/asr/browser 三个包排掉识别栈，`onnxruntime` 一个字都没动。
5. 体积目标：**≤130 MB 下载 / ≤320 MB 解包**。T9.4 实测 **118 MB / 266 MB**（cv2 112 + onnxruntime 38 + rapidocr 31 + numpy.libs 21 + PIL 13）。超了先查是不是把 torch 或 playwright 收进来了。

**坑**

- `stdout` 只许放协议行。组件里任何 `print` 都会打断 id 配对——日志一律 `sys.stderr`。
- Windows 下 opencv 的 DLL 最容易漏（`opencv_videoio_ffmpeg*.dll`）。打出来先跑 `--selftest`，报 `ImportError: DLL load failed` 就是漏了。
- 组件进程**全局串行**（一把锁），所以后端并发调它没用，并发策略见 T9.6。
- 别把 `onnxruntime` 从 `HEAVY` 里删掉——asr 组件靠它排除重复收集，删了两个包都会变大。
- **别把 `DownloadFile.run` 整个替换掉**（T9.4 踩过）：rapidocr 每次加载模型都会调它，齐全时它只是空转。整替换会让正常的加载也报「包内缺模型」——自检里表现为「目录里明明有那个文件，却说不存在」。要包一层、保留 `_should_skip_download`。
- `_guarded` 里必须补 `cls.verbose = params.verbose`：原 `run` 第一行就是设它，`_should_skip_download` 会读，漏了就是 `AttributeError: type object 'DownloadFile' has no attribute 'verbose'`。
- `RapidOCR()` **构造不读模型**（懒加载），第一次推理才读。测"缺模型会怎样"必须真跑一次 ocr，只调构造函数会误判成"正常"。

**渲染（`pdf_pages.py`）**

**逐页流式**：渲染一页 → 识别一页 → 落库一页 → 释放。绝不把 300 页都转成图放内存。

**双栏判列（`ocr_layout.py`，这张卡的验收核心）**

引擎只给行框，**不给阅读顺序**；实测双栏输出是「左1 → 右1 → 左2 → 右2」交错。算法：

```python
def order_lines(lines, page_width) -> list[str]:
    if not lines: return []
    mid = page_width / 2
    left  = [l for l in lines if 中心 x < mid]
    right = [l for l in lines if 中心 x >= mid]
    if _is_two_column(left, right, page_width):   # 判据见下
        return _cluster_rows(left) + _cluster_rows(right)
    return _cluster_rows(lines)                   # 单栏：y 聚类成行，行内按 x
```

`_cluster_rows`：按 y 中心排序，相邻行 y 差 < 0.6 × 中位行高 视为同一行，行内按 x0 排序。

`_is_two_column` 的判据（**实现与文档已对齐到这一版**，2026-11-13 核正 —— 卡里原写「每侧 ≥3 行 +
max/min」，实测下来两条都错）：

1. **每侧 ≥2 行**，不是 3。右栏只有两三行的页照样是双栏，门槛抬到 3 会把这类页退回按 y 排、左右交错；
   而「右栏其实只有页码」的页（1 行）仍被 2 挡住。
2. 边界取 **P90 / P10**，不是 max/min。一两个越过栏线的行框（实测 python 第 7 页越了 19 px）
   就能让 max/min 判出「重叠」→ 整页退化单栏 → 交错，比不判列更糟。
3. **横跨整页的行不参与边界**（宽度 > 70% 页宽）：通栏标题/表格天然与另一栏重叠，参与进去同样翻盘。
4. 容差 `max(8 px, 页宽 2%)`：同一栏内个别行框会越界十几像素，容差要跟页宽一起放。

**验收必须遍历四组 `samples/*/twocol.pdf` 共 40 页**，逐页断言：不丢行、行数不膨胀、
被判双栏的页左右序列最多切换一次（整栏左 → 整栏右），只跑一组不算过。
三页右栏本来就空的样本由「每侧 ≥2 行」这条挡住，按单栏排才是对的。

**并发：已实测，裁定不做（2026-11-12）**

`component_proc` 是**每组件一个进程一把锁**，后端并发调只会排队。所以先测再定：

1. 实测单页识别时 `cairn-ocr.exe` 的 CPU：**1627%（20 核机器吃到 16 核）**。
   onnxruntime 默认按核数开 intra-op 线程，一个进程就已经把整机用满。
2. 按判据（>250% → 不做进程池），**不做并发**。
3. 性能口径（2026-11-13 最终裁决）：**不承诺固定秒数，只承诺行为** —— 上传 2 秒内返回、逐页报进度、可关页面、断点续跑、单页重试。理由：耗时随**每页字数**线性变化，试卷页（中位 348 字）3–7 秒、双栏讲义（中位 1560 字）**15.7 秒/页**（40 页 629 秒实测），早期「3.4 秒/页」只对稀疏页成立。需求 §8.2 / §12 已按这个改，并写清"不做并发"的理由。
4. 顺带实测到一条可选提速路线（**不在本卡范围**）：把每路 onnx 线程限到 4、开 3 路，
   可到 **1.88 秒/页**（30 页约 56 秒）—— 单路限 4 线程本身就比默认 16 线程快（3.0 vs 3.4 秒/页），
   因为默认线程数在这么小的张量上全是同步开销。记在台账 T9.13，要做得单独开卡 + 重打组件包。

**断点续跑**：开工前查 `item_page` 已有页号，跳过；重识别只针对失败页或用户点名的页。

**进度**：`item_file.ocr_status` + 已识别页数 / 总页数。前端每 1.5 秒轮询一次，别用 SSE（这里不需要逐 token）。

**坑**

- `pypdfium2` 的 `render(scale=)` 是相对 72dpi 的倍数，别把 150 直接当 scale 传（会得到 150 倍图）。
- 单页识别过慢时先看是不是渲染成了 300dpi 的图（文件大小会明显变大）。
- 页图统一 JPEG q85；用 PNG 会让 30 页占 100 MB+。
- 「识别出空页」不是失败：`source` 留 `ocr`、`text` 为空、`avg_conf=0`，前端标「这页没认出文字」。整份有 ≥1 页为空时 `ocr_status='partial'`。

```python
    pages: list[PageText]       # docx 单页；pptx 按 slide；xlsx 单页
    page_count: int
    has_text_layer: bool        # 非 PDF 恒 True
    meta: dict                  # 标题、作者、表数、是否截断
```

**各格式要点**

- **docx**：`python-docx` 取段落 + 表格 + 标题层级（`p.style.name` 以 `Heading` 开头）；同时用 `mammoth` 转 HTML。**必须禁掉内嵌图片的 base64 内联**（默认会转 data URI，一份带图讲义能到几十 MB）——验收断言 HTML 里不含 `data:image`。HTML 过后端 `bleach` 白名单（复用 `services/renderer.py` 那套）。
- **pptx**：`python-pptx`，每页收集 `shape.has_text_frame` 的文本 + `notes_slide.notes_text_frame.text`；**不做版式还原**，只出「第 N 页 / 标题 / 要点 / 备注」。
- **xlsx**：`openpyxl.load_workbook(read_only=True, data_only=True)`，只取**第一张工作表**转 Markdown 表；>200 行截断并在 `meta.truncated=True`（界面提示「只读了前 200 行」）。
- **txt/md**：直读，编码按 `utf-8 → gbk → utf-8-sig` 顺序试，全失败用 `errors="replace"` 并记 `meta.encoding_guess`。

**坑**

- `python-docx` 读不了 `.doc`（97-2003），别指望它兜底。
- `mammoth` 的图片回调 API 与版本有关，**先读装上的那个版本的 README**，不要照记忆写；不论怎么写，判据是「产物无 `data:image`」。
- xlsx 的 `read_only=True` 下 `ws.max_row` 可能不准，按迭代计数。
- 一份 docx 里若只有图片没有文字，`text` 会是空串 —— 这时 `kind` 设 `image` 语义不合适（它不是图片文件），保持 `material` 但界面提示「这份文件没有可读文字，图里的内容需要 L3」。

**实测补充（2026-11-13 落地时）**

- **图片要"不出"而不是"事后删"**：`mammoth.images.img_element(func)` 无论 func 返回什么都会输出 `<img>`，
  所以不能用它。直接给 `convert_to_html(..., convert_image=fn)` 一个**返回空列表**的回调，
  `<img>` 根本不会被生成（不是先生成 base64 再删，那样内存里已经躺着一份几十 MB 的字符串）。
  白名单净化仍然照做一遍兜底 —— `renderer.sanitize` 的 `_ALLOWED_TAGS` 里本来就没有 `img`。
- **正文必须按 `document.element.body` 顺序拼**：`document.paragraphs` 与 `document.tables`
  是两个独立列表，分开取会把所有表格堆到文末，"见表 3"就指到别处去了。
- **一份 docx 的表格与图注顺序由原文件决定**：样本里表格出现在「表 1 …」这句之前
  （生成器先插表后写图注），不是抽取排错，别照着"看着不对"去调顺序。
- **抽取是整份原子操作**，不做断点续跑：一次解析要么成要么败，失败时一页都不写。
  与识别共用 `ingest_file._finish()`，所以「每一页都有行才覆盖正文」这条不变量只有一份实现。
- **docx 的 HTML 落盘**在 `pages/<file_id>/0001.html`（与页图同目录，删内容时一起清），
  不入库：它是 T9.10 原文页签的渲染素材，检索用不到，进 SQLite 只会白白撑大。
- **`ocr_status` 从 T9.7 起是「这份原件读到哪一步」**，不再专指识别：上传后一律 `pending`，
  docx / pptx / xlsx / txt 由抽取链路推到 `done`，`partial` 的含义扩成「内容不全」
  （有页没认出来 / 表格按 200 行截断 / 超长文本截到 100 万字）。

## 6. 横切约定（每张卡都适用）

### 6.1 后台任务的写法

统一走 `services/tasks.py` 的 `submit(type, fn, input, pass_task_id=...)`：

```python
tasks.submit("ocr_pages", run_ocr, {"item_id": item_id, "file_id": file_id}, pass_task_id=True)
```

- `fn(input, task_id)` 里用 `repo.update_task(progress=pct)` 报进度。
- 入队**必须在事务提交之后**（否则任务读不到未提交的行）。
- 长任务要能被打断：每页检查一次「内容是否已被删除」，删了就停。
- 启动时 `recover_stale_tasks()` 会把残留 running 标 failed，所以失败是安全的、可重试的。

新增任务类型：`ocr_pages` / `extract_file` / `import_dir`。

### 6.2 错误码表

| code | HTTP | 触发 | 界面文案（禁止词已避开） |
|---|---|---|---|
| `FILE_TOO_LARGE` | 413 | >200 MB | 这个文件 235 MB，超过 200 MB 上限，先压缩或拆分再试 |
| `FILE_UNSUPPORTED` | 415 | 扩展名不在白名单 | 暂不支持 .doc，请另存为 .docx 再上传 |
| `FILE_EMPTY` | 422 | 零字节文件 | 这个文件是空的，换个文件再试（2026-11-12 实测：不拦就会变成「上传成功但读不出字」） |

### 6.4 数据迁移纪律

- 只允许追加：加表、加列、加索引。改既有列 = 新开一版并写回填方案。
- 每版一个 `.sql` 文件，`UPGRADES` 里登记起始版本号。
- 迁移脚本**不要求幂等**，但失败必须能"停在上一版"——每个版本单独 commit（`migrate.py` 已这么做）。
- 动了 schema 必须跑 `verify_m1`–`verify_m5`（跨里程碑回归都出在这）。

### 6.5 前端状态与轮询

- 识别进度：`GET knowledge/{id}/ocr`，每 1.5 秒一次，最多 20 分钟；离开页面停止轮询。
- 任务类进度（批量导入）：复用现有 `pollTask`。
- 所有轮询要有 `AbortController`，组件卸载时中止，否则切页后还在打接口。

## 8. 已知失败模式（踩过或必然踩）

### 8.1 环境类

| 现象 | 原因 | 处理 |
|---|---|---|
| `git push` 无限挂起、零输出 | PATH 里的 PortableGit 版 GCM 在等交互 | §1.3 注入临时 helper；不要设 `GCM_INTERACTIVE` |
| `'remote-https' is not a git command` | 用了精简版 git | 改用 `C:/Program Files/Git/cmd/git.exe` |
| Electron 起不来，报 `isPackaged` undefined | `ELECTRON_RUN_AS_NODE=1` 开着 | `env -u ELECTRON_RUN_AS_NODE` |
| `app.asar` EBUSY | 输出目录被占用/索引 | 换全新空目录输出 |
| npm 装 electron-builder 卡 19 分钟 | 直连官方源 | 用 npmmirror（§1.4） |

### 8.2 代码类

| 现象 | 原因 | 处理 |
|---|---|---|
| `load_dotenv(override=False)` 仍有上次的值 | dotenv 会写 `os.environ` | 严格模式用 `dotenv_values()` 纯解析；取 Key 走 `config.env_value()` |
| CSS 间距不生效、`getComputedStyle().gap` 是 `normal` | 令牌名写错（只有 `--space-1/2/3/4/6/8`） | 写错不报错，量计算值 |
| Playwright 点「待整理」跳去仪表盘 | 名字命中了「今日」条那个大容器 | 给按钮显式短 `aria-label` |
| 验收脚本在异步动作刚返回时断言失败 | 后台任务还没跑完 | `wait_until(predicate)`，不要放宽断言 |
| 文件类内容第二个就被判重复 | `content_hash` 都是空串的 hash | T9.3 的占位正文方案 |
| 同名不同内容的文件被并成一条 | 占位正文 `[文件] 原名` 相同 → hash 相同 | 撞了就加 sha 前缀重试（T9.3 `_create_item`） |
| `POST /api/files` 报 500 且栈里是 `multipart` 相关 | FastAPI 解析 multipart 要 `python-multipart`，不在默认依赖里 | 2026-11-12 已加入 `pyproject.toml`（纯 Python，约 40 KB） |

### 8.3 识别类（本项目特有，必看）

| 现象 | 原因 | 处理 |
|---|---|---|
| **双栏输出左右交错** | 引擎只给行框，按 y 排就是交错（实测必现） | `ocr_layout.order_lines` 判列（T9.6） |
| 双栏页被误判成单栏、整页交错 | 用 max/min 取栏边界，一两个越界框就翻盘 | 栏边界取 P90/P10，容差 `max(8px, 页宽 2%)`；横跨整页的行不参与边界（T9.6 实测 40 页零错行） |
| 30 页跑了 100 秒 | 不是渲染成了 300dpi，是 onnxruntime 把核吃满的正常量级 | 先量 CPU（实测 1627%）；要更快得限线程 + 多路，见 T9.13 |
| `cv2.imread` 返回 None | Windows 中文路径 | `Path.read_bytes()` + `cv2.imdecode` |
| 组件报 `DLL load failed` | opencv/onnxruntime 的 DLL 没进包 | `datas` 补；先打最小包验证（§2.2） |
| 识别结果全是方块/乱码 | 用了 PDF 文本层而不是识别 | 检查是否走了 `extract` 分支；PDF 只走 `ocr` |
| 30 页跑了 5 分钟 | 渲染成了 300dpi | 长边钳到 1600 px |
| 内存涨到 1 GB+ | 一次把 300 页都渲染了 | 单页流式：渲染→识别→落库→释放 |
| 认错但读起来通顺 | 模型"顺手润色" | 文字与页图并排；diff 编辑距离守卫 |
